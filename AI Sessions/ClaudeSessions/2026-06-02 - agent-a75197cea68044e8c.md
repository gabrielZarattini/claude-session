# Security Review — `disconnect_wordpress()` RPC + client `.insert()` switch

**Scope reviewed:** `supabase/migrations/20260602120000_wordpress_disconnect_rpc.sql` (new), `src/pages/SocialAccountsPage.tsx` (modified). Corroborated against `20260601000000_credential_encryption.sql`, `20260601000600_secure_definer_views.sql`, and `supabase/functions/publish-wordpress/index.ts`.

## Verdict: NO qualifying vulnerability (no finding ≥8 with a concrete attack path)

The change is safe as written. Below is the trace for each attack class, including the one path that warrants explicit attention (the `vault.secrets` DELETE), and why it does not clear the bar.

---

### The one path worth scrutiny: arbitrary `vault.secrets` deletion by planted UUID

This is the only candidate that could be a cross-tenant primitive, so I traced it fully.

- **The write primitive pre-exists.** The encryption trigger (`trg_encrypt_user_api_keys`, `20260601000000` lines 170-177) treats any UUID-shaped value written to `wp_app_password` as "already a Vault reference" and stores it **verbatim** (no `create_secret`). So an authenticated user can plant an arbitrary UUID string into their own `wp_app_password` via the view `.insert()`.
- **This migration newly weaponizes it.** `disconnect_wordpress()` reads that planted value into `v_pwd_ref` from the caller's own row, then runs `DELETE FROM vault.secrets WHERE id = v_pwd_ref::uuid` as owner `postgres` (which holds DELETE on `vault.secrets`, and `vault.secrets` has no tenant/owner column to scope on). Before this change a planted UUID was an inert dangling pointer; after it, it becomes a "delete this `vault.secrets` row by id" instruction. If an attacker knew a *victim's* secret UUID, they could delete it (DoS of the victim's credential).
- **Why it does NOT reach exploitable (the gate is UUID secrecy):** `vault.secrets.id` is a **v4 UUID (~122 bits)** and is **never exposed to any client.** Verified: the masked client views emit only `'••••••••••••'` for every secret column (`20260601000600` line 65; `20260601000000` lines 398-409); the `decrypted_*` views that resolve real pointers are `REVOKE ... FROM anon, authenticated` / `GRANT ... TO service_role` only (lines 625-632) and are read exclusively server-side by trusted edge functions (`publish-wordpress` uses the decrypted plaintext, never echoes the pointer). With no read surface for another tenant's secret id and the id being cryptographically unguessable, there is **no concrete attack path** to a *cross-tenant* deletion. The only secret a caller can deterministically destroy is **their own** WP password secret — which is exactly the intended behavior of a disconnect.

Confidence this is non-exploitable cross-tenant: **8/10.** It is a latent sharp edge (the function trusts that `wp_app_password` always points to a secret the caller owns, an invariant enforced only by UUID secrecy, not by a check). Worth a defense-in-depth hardening, noted below, but it does not meet the "concretely exploitable, newly introduced" bar for a HIGH finding.

### 1. Cross-tenant clear of another tenant's credentials — NOT possible
Both the `SELECT ... INTO v_pwd_ref` and the `UPDATE ... SET wp_* = NULL` are scoped `WHERE user_id = v_uid`, where `v_uid := auth.uid()` derives from the request JWT `sub` and is **not** a caller-supplied parameter. There is no spoofable input to steer either statement at another tenant's row. Safe.

### 2. Unauthenticated / anon invocation — NOT possible
Two independent gates: (a) `REVOKE ALL ... FROM PUBLIC, anon` + `GRANT EXECUTE ... TO authenticated` — anon role cannot call it at all; (b) inside the function, `IF v_uid IS NULL THEN RAISE EXCEPTION ... errcode 28000`. Even if a misconfigured token reached the function with no `sub`, it fails closed before any mutation. Safe.

### 3. SECURITY DEFINER hardening / search_path hijack — SAFE
`SET search_path = ''` is set on the function, and every object is schema-qualified: `public.user_api_keys_table`, `vault.secrets`, `auth.uid()`. The remaining operators (`~`, `now()`, `gen_random_uuid` n/a here) resolve from `pg_catalog`, which is implicitly searched first and cannot be shadowed by a non-superuser-owned object. No function-shadowing or relation-shadowing path exists. This is the correct CVE-2018-1058 hardening posture.

### 4. Steering the `vault.secrets` DELETE to an arbitrary/other secret — see top section
Value originates only from the caller's own row (`WHERE user_id = v_uid`); not directly attacker-supplied at call time. The indirect plant-a-UUID vector is real but gated by unguessable, non-exposed secret UUIDs (analysis above). The regex guard `^[0-9a-f]{8}-...$` also ensures only well-formed UUIDs reach the cast, so no cast-error or injection. No concrete cross-tenant path.

### 5. SQL injection — NOT present
No dynamic SQL, no `EXECUTE`. `v_pwd_ref` is `text` validated against a strict UUID regex then cast `::uuid`; all other values are typed. Nothing to inject.

### 6. Client `.insert()` change — no new server-side trust issue
The switch from `.upsert({onConflict})` to `.insert()` is a correctness fix (the masked view has no unique constraint for PostgREST `merge-duplicates`; the INSTEAD OF trigger does `INSERT ... ON CONFLICT (user_id) DO UPDATE` internally — `20260601000000` lines 502-526). Tenancy is enforced server-side by the definer view's `WHERE auth.uid() = user_id` filter and the trigger keying on `user_id`; the client-supplied `user_id: user!.id` is not a trust boundary. No new issue.

### 7. GRANT EXECUTE + SECURITY DEFINER escalation — bounded
The only capability granted to `authenticated` is "clear my own three WP columns and delete the Vault secret my own row points to." All statements are `auth.uid()`-scoped. No escalation beyond clearing one's own WP creds (modulo the latent invariant in the top section). Acceptable.

## Excluded / non-blocking observations (FYI, not findings under the rubric)

- **Defense-in-depth (recommended, not a vuln):** `disconnect_wordpress()` deletes a `vault.secrets` row by an id read from a client-writable column, relying solely on UUID secrecy to stay tenant-safe. Consider scoping the delete to secrets the function knows it owns — e.g. `DELETE FROM vault.secrets WHERE id = v_pwd_ref::uuid AND name = 'user_api_keys_wp_app_password_' || v_uid::text` (the deterministic name from the encryption trigger, `20260601000000` line 174). This converts the safety property from "UUID is secret" to "name binds to caller," eliminating the planted-pointer class entirely. Confidence this is a meaningful hardening: high; confidence it's currently exploitable: low (hence not a finding).
- **Law 2 (process) gate, not security:** the migration header references `docs/processes/credential-disconnect-clear.md`, which does **not exist** (verified `ls` → missing). Flagging only because the project's own SSP-01 Law 2 requires the SOP before the automation lands; it is not a security vulnerability.

Both are out-of-scope of the exploitability bar; I did not file a spawned task since the hardening is a judgment call for the Sovereign and the SOP is a process gate, not a defect.
