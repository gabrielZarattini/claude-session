- v3 (20260718200000:216, 220) wrote the subject's contact (phone/e-mail) into `mcorch_nodes.content` and `metadata.contact`. That node's insert also fires `trg_mcorch_embed_on_insert` (20260503120000), which ships the node to the `embed-mcorch-node` edge function and thence to an external embedding provider — i.e., v3 exfiltrated erased-subject PII to a third party and persisted it outside the cascade. v4's insert (lines 104-124) carries only the opaque lead uuid + row counts. Verified char-by-char: `name`, `content`, and every `metadata` key are uuid/counts only.
- The audit node sets `user_id = v_user_id` (line 123), which is NOT NULL (`leads.user_id NOT NULL`), so under `nodes_tenant_select` (20260425210000:35-37) it is visible only to the owning tenant — it does not become a system/global node.
- The return payload (lines 126-138) is uuid + counts, no PII.

**5. Atomicity:** the whole function is one transaction — a failure at any step (including the audit insert) rolls back all deletes, so there is no partial-erasure state that reports success.

**6. Carried-over quirk (not a finding):** `SELECT l.*, l.user_id INTO v_lead` (line 42) produces a record with a duplicate `user_id` field; PL/pgSQL resolves field access to the first match, both fields hold the same value, and the identical pattern is already live in v3 production. Cosmetic only.

## Informational residual notes (pre-existing, NOT introduced by this migration — listed because the header claims FM-CS-02 closure)

- **Storage media residue (OTD-CRM-017, tracked):** `crm-media/<uid>/` objects referenced by cascaded `messages.media_asset_path` are not removed (Storage objects are non-FK). Openly registered in 20260718230000:48-52 as a future slice. Severity MEDIUM as an LGPD-completeness gap, but pre-existing and documented — not a v4 regression.
- **`deals.name` PII:** the FMEA that motivates this migration (docs/bok/crm-suite/08-quality-metrics.md:57, FM-CS-02) names "PII em `deals.name`" in the failure mode. v4 counts deals as de-linked (by design, lines 67-70) but a deal named after the contact retains that name. Partial closure of FM-CS-02, acknowledged by the SET NULL-by-design comment (lines 20-22). LOW, pre-existing.
- **No in-function zero-residue verification SELECT:** FM-CS-02's prescribed action says "A RPC deve terminar com SELECT de verificação de zero resíduo"; v4 reports pre-delete counts instead of post-delete verification. Audit-integrity nuance (counts are a snapshot, not proof), not an exploitable vulnerability. LOW.

None of these three are exploitable by another tenant and none were added by this change; they are completeness debt already tracked in the BoK.

I found no authorization bypass, no injection surface, no privilege-escalation vector, and no new data-exposure path. Clean from a newly-introduced-vulnerability standpoint.
