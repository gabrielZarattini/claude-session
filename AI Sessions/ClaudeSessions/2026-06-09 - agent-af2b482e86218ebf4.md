## Review — Fix de segurança/estabilidade: incidente settings.password (2026-06-09)

### Racional (causa-raiz x fix)

O fix ataca a causa-raiz, não é band-aid, e as duas camadas são defense-in-depth corretas e bem motivadas. Confirmei o fluxo end-to-end no código:

- **Login** (`/home/gcrux-tradeux/tradeux/backend/src/controllers/authController.js:11`): `bcrypt.compareSync(password, settings.password)`. Se o hash for sobrescrito por um valor desconhecido, todo login falha em 401 — bate exatamente com o incidente (inclusive o agente, que loga via MCP `api.js`).
- **Sink único** (`/home/gcrux-tradeux/tradeux/backend/src/repositories/settingsRepository.js:51`): era `if (newSettings.password)` → qualquer string truthy re-hasheava. O autofill setava `settings.password` no state via `onInputChange`, e o handler mandava `settings` inteiro. Causa-raiz comprovada.
- **GET /settings já era seguro** (`/home/gcrux-tradeux/tradeux/backend/src/controllers/settingsController.js:9-10`): faz `delete plainSettings.password/secretKey`. Ou seja, o state React **nasce sem** esses campos; eles só passam a existir por digitação ou autofill. Isso é importante: significa que o fix do frontend (omitir quando vazio) cobre o caso comum, e o backend cobre o resto.

**Camada backend (a que realmente fecha o buraco):** `typeof === 'string' && trim().length > 0` é a guarda correta e *fail-safe por construção* — preserva o hash atual independentemente do que o navegador, o MCP, ou qualquer cliente HTTP mandem (vazio, whitespace, ausente, `null`, número). É a defesa que não depende da boa-fé do caller. Mesma guarda aplicada a `secretKey` (re-encrypt), o que também previne zerar a credencial Binance — risco gêmeo legítimo. O comentário ressalva corretamente que o **hash usa o valor BRUTO** (sem trim), preservando compatibilidade com o `compareSync` do login: uma senha legítima com espaço nas pontas continua autenticando. Bom detalhe, sem regressão de auth.

**Camada frontend (reduz a superfície + UX):** payload explícito que dá `delete` em password/secretKey vazios reforça a semântica "campo omitido = não alterar" no caller, e os `autoComplete="new-password"` / `"off"` mitigam o autofill na origem. As três camadas (autocomplete → omitir no payload → guarda no backend) são redundância saudável, não over-engineering.

### Regressão de auth / backward-compat

Nenhuma regressão introduzida. Analisei os caminhos:
- Trocar a senha de fato (digita New + Confirm iguais) → `payload.password` presente e não-vazio → re-hasheia. OK.
- Salvar qualquer seção sem mexer na senha → omitido no front E barrado no back → hash preservado. OK (o cerne do fix).
- Validação de confirmação agora só dispara se o usuário digitou algo (`newPassword.trim() || confirm.trim()`), corrigindo de quebra um bug latente: antes, com o state começando vazio, `settings.password` era `undefined` e a comparação `undefined !== ''` poderia barrar saves legítimos. A normalização `|| ''` elimina o `undefined.trim()`.
- O comportamento de "preservar quando não muda" está garantido pelo backend **independe do navegador** — é a propriedade que eu queria ver e ela está lá.

### Aderência a convenções

Boa. Comentários em pt-BR conforme o CLAUDE.md, com referência ao incidente (rastreável). Layering respeitado — o write fica no `repositories/`, o controller permanece fino (`settingsController.updateSettings` só repassa `req.body`), nada vazou para camada errada. Estilo dos arquivos preservado (o padrão `!== null && !== undefined` dos demais campos não foi tocado; a guarda nova é mais estrita de propósito, e isso é correto para um segredo). Zero toque em `beholder.js` ou em fluxo de ordem/dinheiro — blast radius baixo.
