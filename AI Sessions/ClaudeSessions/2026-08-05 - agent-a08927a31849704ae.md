Authz in the new `clips_spec` mode is fail-closed and owner-scoped (edge fn).** `assemble-master/index.ts:80-95`: each `{render_id}` item is validated with `.eq("id", renderId).eq("user_id", user.id).in("engine", ["motion","hyperframes"])` and any miss returns 422 (`invalid_clip_render`) — stricter than the legacy path, which silently skipped invalid keys. Each `{storage_key}` item goes through `resolveKey` (line 57-68): `${user.id}/` prefix check, `..` rejection, owner-scoped `creative_assets` spine lookup, and a `MEDIA_BUCKETS` allowlist, also fail-closed 422 in this mode. Project ownership (`vm_canvas_projects .eq user_id`) and JWT (`auth.getUser()` via anon client) are checked before any of this.

**2. The worker's trust in `composition` is justified by RLS.** `video_renders` has **no INSERT/UPDATE policy for authenticated** (migration `20260622040000`, lines 61-72: SELECT own-or-org + RESTRICTIVE no-delete only) — default-deny writes, and no later migration adds a write policy (grep across all 12 migrations touching the table). The only writer of `engine: "assemble"` rows anywhere in the codebase is the `assemble-master` edge fn itself (service role, after validation). So a client cannot forge or mutate a `clips_spec` to smuggle a foreign `render_id` or an arbitrary `{bucket, key}` into `processAssemble`.

**3. The dep→storage_key resolution cannot cross tenants.** `motion-bridge.ts:331-337` resolves `render_id → dep.storage_key` and pins `bucket = BUCKET` (`video-studio-assets`). `storage_key` on `video_renders` is only ever written by the service-role workers via `finalize_video_render`, always owner-prefixed (`${userId}/motion/${renderId}.mp4`, motion-bridge.ts:222), and the edge fn already proved `dep.user_id === assemble.user_id` at enqueue. No client write path exists to change either row afterward (no TOCTOU window with an attacker-controllable side).

**4. No new ffmpeg-arg injection surface.** The new code paths contribute only: storage keys resolved server-side (used solely as Supabase Storage download keys — local filenames are synthesized as `c000.mp4`, motion-bridge.ts:360, so keys never become local paths), and `loudnorm_lufs`/`fade_sec` coerced through `Number(...) || default` (edge fn lines 115-118) — a JS number cannot carry filter-graph or shell metacharacters, and `Bun.spawn` takes an argv array (no shell). `transition`/`aspect` are coerced to fixed literals. `comp.title` flows only into the `register_creative_asset` RPC, not ffmpeg.

**5. `assembleEligible` (motion-bridge.ts:431-439)** is a pre-claim state peek on server-written dep ids; its result is never exposed to a client and grants nothing.

### Below-threshold observations (defense-in-depth, not findings — no concrete exploit; noted per the established "server resolves from owned rows" doctrine)

- `motion-bridge.ts:332-333` — the dep lookup omits `.eq("user_id", userId)`; and `motion-bridge.ts:338-339` — the `{bucket, key}` passthrough re-checks neither the bucket allowlist nor the owner prefix. Both are currently unreachable with hostile data (invariant enforced at the single service-role write point, per items 2-3 above), but adding `.eq("user_id", userId)` to the dep query and an owner-prefix + `MEDIA_BUCKETS` assert in the worker would make the worker safe even if a future writer of `assemble` rows forgets the enqueue-time validation. Confidence as an exploitable vulnerability today: ~0.2 — excluded.
- Client-side (`master-clips.ts:49`, `useCanvasPipeline.ts`) passes `output.videoUrl` as `storage_key`; if that value is ever a signed URL rather than a bare key, the edge fn rejects it (prefix check) — fail-closed functional concern, not a security one.
