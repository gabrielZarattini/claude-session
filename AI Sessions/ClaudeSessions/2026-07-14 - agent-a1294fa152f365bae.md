# Security Review — Amendment 23 (FR-SPACES-081, server-side publish-time reframe)

**Verdict: no findings meet the >80% real-exploitability bar.** All six vectors were traced end-to-end against the actual deployed schema (migrations read, not assumed). Per-vector justification follows, then below-bar hardening notes.

---

## (a) Storage path traversal — NOT EXPLOITABLE

`supabase/functions/publish-space-asset/index.ts:119-120`:

- `slug = (s) => s.toLowerCase().replace(/[^a-z0-9_]/g, "_").slice(0, 40)` — the character class is a strict allowlist applied to *every* character after lowercasing. Output alphabet is exactly `[a-z0-9_]`: no `/`, no `.`, no `%`, no null bytes. Unicode edge cases (e.g. U+0130 → `i` + combining dot) decompose into chars that are either allowlisted ASCII or replaced by `_` — no path metacharacter can survive. `..` and `/` are unconstructible.
- `asset.id` comes from the owner-resolved DB row (`.eq("id", sourceAssetId).eq("user_id", user.id)`, line 70-72) and `creative_assets.id` is a `uuid` column (`20260625120000` line 21) — the Postgres type guarantees hex+dash only, regardless of what the client sent as `source_asset_id`.
- `user.id` is the canonical `auth.users` UUID from `auth.getUser()` (server round-trip, not a decoded claim).
- Result: `outKey` is structurally pinned inside `${user.id}/publish-reframe/` for the service-role upload at line 121-122. The in-code comment correctly identifies the path as the boundary; the sanitization is sufficient.

## (b) `.or()` PostgREST filter injection — NOT EXPLOITABLE

Line 99: `.or(\`user_id.is.null,user_id.eq.${user.id}\`)`. The interpolated value is the GoTrue-verified user UUID (uuid PK of `auth.users`, returned by a server-side `getUser()` call — not attacker-settable to a non-UUID string). The client-controlled `channel`/`surface` go through `.eq()` (lines 98), which supabase-js URL-encodes and PostgREST parses as a literal value for the `eq` operator — commas/dots there cannot break into the logic tree. Even in the hypothetical that the `.or` were injectable, the widest gain is reading extra `channel_profiles` rows (a config table whose system rows are already world-readable and whose per-tenant rows contain only format specs — `20260627140000` policy "read system or own"). No finding.

## (c) Direct `creative_assets` INSERT vs `register_creative_asset` RPC — NO INVARIANT WEAKENED

Compared against the deployed RPC (`20260710170000`, superseded list in `20260712120000`) and the table DDL (`20260625120000`):

- **Ownership/provenance**: `user_id: user.id` (JWT-derived, server-set), `parent_asset_id: asset.id` (owner-resolved row). No client body value reaches identity columns. Forgery impossible.
- **Allowlists the RPC enforces in plpgsql** (`kind`, `source_module`): the direct insert hardcodes `'image'`/`'spaces'`, both of which are ALSO enforced by table CHECK constraints (`creative_assets_source_module_check`, kind CHECK) — the belt survives even without the RPC's suspenders. `'spaces'` is present in the latest deployed CHECK (`20260712120000:17`).
- **The RPC's cross-tenant ON CONFLICT guard** (`WHERE user_id = EXCLUDED.user_id`): the direct path instead does select-first + plain INSERT. If a conflicting `(bucket,key)` row belonged to another tenant, the INSERT would fail 23505 (warn-logged, publish continues) rather than update it — equivalent or stricter, never an overwrite. And such a cross-tenant row is not constructible anyway: the key is owner-prefixed and only this code path writes under `publish-reframe/`.
- **`is_public`**: omitted → column default `false`. Correct for the private bucket.
- No triggers on `creative_assets` are bypassed (`20260703030000` force_server_id triggers are on `vm_canvas_projects`/`spaces` only; the insert doesn't set `id`).

**Factual defect in a comment, not a vuln** (`index.ts:124`): "creative_assets has no UNIQUE on key" is wrong — `creative_assets_uq_object UNIQUE (storage_bucket, storage_key)` exists (`20260625120000:48`). The consequence is benign (concurrent re-calls: second insert 23505 → warn → publish proceeds), but the comment should be fixed so a future editor doesn't build on the false premise. Also the select-first (line 126) filters `storage_key` but not `storage_bucket` — harmless today (key is owner-prefixed and bucket-unique in practice), worth tightening.

## (d) Decompression bomb — REAL, BUT DoS-ONLY (excluded per policy)

The 15MB cap is on the *compressed* blob (`index.ts:112`); zlib tops out near 1032:1, so a crafted 15MB PNG can declare/inflate to ~15GB raw (~3.9 gigapixels; `Image.decode` in imagescript allocates `width*height*4` from the IHDR before inflating — `_shared/reframe.ts:13`). A missing post-header pixel-count cap (e.g. reject `>26MP`) means a hostile source image OOMs the isolate. I verified it does **not** enable anything beyond DoS: the reframe block runs *before* any write (variant upsert at line 151, storage upload at 121 only after a successful encode), so an OOM abort leaves zero partial state; catchable allocation failures (RangeError) hit the fail-open catch at line 142 and publish-as-is. No memory-safety/RCE primitive in imagescript's pure JS/WASM decode is known to me, and the dependency+version is pre-existing (verbatim extraction — diff confirms the body is identical except `export`). Recommend adding `if (img.width * img.height > 26_000_000) throw` inside `reframeToJpeg` as hardening, but per the exclusion rule this is not reported as a finding.

## (e) FMEA-011 downstream — INVARIANT HOLDS

`auto-publish/index.ts:150-159` resolves the variant with a hard tenant bind (`.eq("id", variant_id).eq("user_id", post.user_id)`) and signs `asset_bucket`/`asset_key` from that row only. Both values are now either (i) the owner-resolved source row or (ii) the server-constructed `canvas-assets` key under the owner's own prefix (`index.ts:137-138`) — never a client body value. `space_publish_variants` has no authenticated INSERT/UPDATE policy (`20260710233000:57-62`), so a user cannot plant a foreign key into their own variant to get it signed. The `attachAsset` http(s) passthrough (`auto-publish:120`) is unreachable with attacker data for the same reason. Invariant intact.

## (f) Fail-open downgrade — NO SECURITY IMPACT

The endpoint requires the owner's JWT and the variant UNIQUE key includes `user_id`, so only the owner can touch their own variant — no cross-tenant trigger exists. On a crafted/induced reframe failure, the upsert (line 151-165) rewrites `asset_bucket/asset_key` back to the **original owner-resolved master** — a valid, owner-owned asset, never a stale foreign or attacker-chosen ref. `status`/`scheduled_post_id` are excluded from the upsert payload, so a scheduled variant is never un-scheduled. Self-inflicted downgrade of your own variant to your own master is a UX behavior, not a vulnerability.
