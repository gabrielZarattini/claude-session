I'm tracing through the security implications of this change, particularly how user IDs and credentials are resolved through different code paths. The service-role path trusts the caller to provide the user ID directly, while the user-JWT path derives it from an authenticated session. I need to examine where the WordPress credentials come from to ensure they're properly scoped to the right user.

For the flip operation itself, I'm checking whether a caller could bypass authorization and modify posts they shouldn't have access to. In the user-JWT path, the WordPress credentials used come from that specific user's stored API keys, and the site URL is their own WordPress instance, so they can only flip posts on their own site using their own application password—which is the same authorization model the create path already uses. WordPress itself enforces the actual post-level permissions based on the application password's capabilities.

In the service-role path, a trusted internal caller could specify any user ID and flip posts on that user's site, but that's not a new attack surface since the create path already allows service-role callers to create posts as any user. The authorization model is consistent.

I'm also examining the `post_id` parameter for injection vulnerabilities. It's URL-encoded with `encodeURIComponent`, which converts special characters like `/`, `?`, and `#` into percent-encoded sequences, preventing path traversal or query parameter injection. The `.` character isn't encoded, but the `/` characters that would make `..` traversal work are encoded, so path traversal isn't possible.

The `wpPostType` is derived from a fixed enum check rather than user input, and since `apiBase` is a fixed prefix with `post_id` appended after the path, there's no way to inject a full URL or change the host. The secret header `X-MCORCH-Publish` is only attached when the hostname matches the configured secret host, and this gating happens before the flip branch reuses the same auth headers, so the protection is consistent.

There's a potential redirect-based secret leakage if the WordPress server responds with a 3xx redirect to a different host — `fetch` would follow it and forward the secret header. But this isn't new to the flip; the existing create path and tag-resolution fetches already use raw `fetch` with the same auth headers and follow redirects, so it's a pre-existing pattern rather than something introduced here.

The real question is whether the flip creates a new surface to reach that secret-bearing fetch. The create path only triggers the WP fetch after `title` and `content` are provided, so I need to think through whether the flip changes the attack surface.

With the flip, you can trigger a fetch with just `post_id`, but the secret only attaches when the host matches the trusted origin. For a tenant whose `wp_site_url` points to that trusted origin, the flip would attach the secret — but the fetch target is still the trusted origin itself, so the only leakage vector remains a redirect from there, which is the same as the create path. But now I'm wondering: could a malicious tenant actually set their own `wp_site_url` to match the trusted origin in their decrypted credentials?

If they did, the host-gate would match and the secret would attach, but they'd be authenticating with their own basic auth credentials — which wouldn't be valid for the MCORCH origin. The CF-skip secret bypasses the WAF, but WordPress would still reject the invalid basic auth. So they can't flip MCORCH's posts, and even though they could use the CF-skip secret to hit the MCORCH `/wp-json/*` endpoints, they still don't leak the secret itself.

Actually, thinking through this more carefully — could a tenant exfiltrate the secret? The secret gets placed in a request header sent to the host, and it's only sent when the host matches `WP_PUBLISH_SECRET_HOST`. If a tenant sets their `wp_site_url` to the MCORCH origin, the secret goes to MCORCH, not back to them. Since they don't control the MCORCH server, they can't read the header, so there's no exfiltration happening.

The auth check happens before the flip branch, so there's no bypass there. The relaxed title/content requirement when `post_id` is present doesn't circumvent authentication — it just changes validation logic. And the error messages returned from the flip operation mirror what the create path already does, so that's not introducing anything new.

For the `status` field, it's user-controlled but WordPress validates it against an enum of allowed values like publish, draft, pending, private, and future. Passing an arbitrary string just triggers a WP validation error, so there's no injection risk there. The real question is whether a user could flip any post on their own site — they could theoretically publish a draft another author created, but WordPress enforces that through the application password's user role permissions, which the MCORCH function doesn't override.

In the service-role path, a trusted caller holding the secret key can flip posts on any user's site, but that's the intended behavior for service-role access. The authorization check is straightforward — only requests with the correct Bearer token reach that branch, so there's no new bypass for non-service-role callers.

Looking at the overall change, I don't see any high-confidence, newly-introduced vulnerabilities. The cross-tenant isolation holds because credentials and API base are resolved per user ID. The post ID encoding prevents injection attacks. And the header-based access control for the publish header matches the same pattern as the create endpoint. The security model is consistent. The `post_id` parameter gets safely converted to a string and URL-encoded, so even if it's an array or object, it won't cause injection issues. I'm satisfied the change is secure and ready to document.
