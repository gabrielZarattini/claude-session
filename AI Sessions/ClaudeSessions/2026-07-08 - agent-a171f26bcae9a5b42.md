## Verdict: False positive

I read both `tiktok-login-init/index.ts` and the shared `oauth-state.ts`. This is a hardening/best-practice observation, not a concretely exploitable vulnerability.

**Analysis of each claimed exploit path:**

- **(a) "future oracle / telemetry echoes signing material"** — Purely speculative ("any future code path"). In the code as written, `signState`/`verifyState` use HMAC-SHA256 via WebCrypto. HMAC is a PRF: its outputs never reveal the key, and `verifyState` returns only a boolean/parsed-payload with a constant-time compare (`timingSafeEqual`). No current path turns this into an oracle, and no telemetry logs the key or raw HMAC inputs in a key-recovering way. A vuln that requires hypothetical future code is not exploitable today.

- **(b) "key rotation invalidates in-flight states"** — This is an availability/operational consequence, not a security exploit. Explicitly out of scope (DoS/operational).

- **(c) "shared key across social-auth and tiktok-login, intent is the only separation"** — An attacker still cannot mint *any* valid state without `SB_SECRET_KEY`, which is server-only env (trusted, never leaves the server). Cross-flow confusion would at most let a user replay their *own* legitimately-minted state into the wrong flow, and the `intent` field plus fail-closed `maxAgeMs`/`ts` checks guard that. There is no untrusted input that produces a forged or cross-tenant state.

The finding reduces to "don't reuse the master secret as an HMAC key (crypto domain separation)" — a legitimate defense-in-depth improvement, but it falls under lack-of-hardening with no concrete attack path driven by untrusted input. The service-role key is never disclosed, and the actual CSRF/account-linking vector the signing was designed to close is properly handled (signed state, constant-time verify, fail-closed replay bounds).

**Fix (hardening, if pursued):** derive a dedicated signing key, e.g. `HKDF(SB_SECRET_KEY, info="oauth-state-v1")` or a separate `OAUTH_STATE_HMAC_KEY` env secret, so the master secret is not directly used for client-visible token signing.
