I walked each category against the sanctioned sibling.

### 1. Cross-tenant / RLS — SAFE
- RLS enabled (line 42), policy `FOR ALL USING (auth.uid() = user_id) WITH CHECK (auth.uid() = user_id)` (lines 45-46) — byte-identical semantics to meta_config lines 48-49.
- PK is `user_id` (line 23), so the row IS the tenant boundary; no separate `id` to spoof, no cross-tenant enumeration path. One row per tenant is structurally enforced by the PK (stronger than meta_config's `UNIQUE(user_id)`, which achieves the same).
- Default-deny holds: RLS enabled + single restrictive-by-effect policy, no permissive gaps. `service_role` bypass is by design (trusted).

### 2. Secret exfiltration (FM-HF-03) — SAFE
- `REVOKE SELECT (refresh_token, access_token, pending_code_verifier) FROM anon, authenticated` (line 56) blocks PostgREST readback of all three token-class columns. `select=*` fails for these roles; clients must whitelist safe columns. Identical mechanism to meta_config line 58.
- On the **UPDATE-not-blocked** concern (per `reference_profiles_column_guard_mint_hole`): a client CAN update their own `refresh_token`/`access_token` via RLS `WITH CHECK (auth.uid() = user_id)`. But this is **self-scoped only** — the PK + WITH CHECK confine any write to the attacker's own row. Writing garbage into your own OAuth tokens is self-sabotage (breaks your own Higgsfield connection), not a cross-tenant read, not a mint, not privilege escalation. The profiles mint-hole was exploitable specifically because the sensitive column (`mco_balance`) was an economic asset whose self-update = free minting. There is **no economic or trust asset** here that self-writing a token grants — you cannot forge another tenant's session, and you cannot read back what you wrote (SELECT still revoked). This exactly mirrors meta_config, where clients likewise self-write `long_lived_token` on BYOK paste. **Not a finding.**

### 3. `pending_state` not revoked — SAFE (correct by design)
`pending_state` is the CSRF state token echoed to the client inside `authorization_url` by design (comment line 33). It is client-visible by construction; the security property of `state` is that the callback compares the returned value against the stored one server-side — its confidentiality from its own owner is irrelevant. Leaving it client-readable is correct and matches OAuth PKCE practice. The genuinely secret half of PKCE, `pending_code_verifier`, IS revoked (line 56). Correct split.

### 4. Missing hardening vs meta_config — NONE material
Line-by-line, higgsfield_oauth has every control meta_config has for the credential table:
- RLS enabled ✓, owner-only FOR ALL policy ✓, updated_at trigger ✓, column-REVOKE on token columns ✓, one-row-per-tenant ✓, `ON DELETE CASCADE` to `auth.users` ✓.
- meta_config's second table (`meta_posts` + its indexes) has no counterpart here, but that's a history/log table, not a security control — its absence is scope, not a gap.
- The only at-rest-encryption gap is explicitly the project-wide OTD-META-ENCRYPT, which the prompt excludes and which meta_config shares identically (both plaintext + REVOKE).

The `id_token` claim column is named `clerk_sub` (line 28) — the OAuth flow validating that `id_token` signature/issuer lives in the later `higgsfield-oauth-callback` edge fn, out of scope for this migration. Nothing in the migration is unsafe; just flagging that the token-validation trust boundary is deferred to code not reviewed here.
