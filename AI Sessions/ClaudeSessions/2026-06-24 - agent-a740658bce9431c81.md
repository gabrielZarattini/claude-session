## Security Review: Billing-Accuracy Fix (`refund_autopilot_video_enqueue`)

**Verdict: NO concrete, exploitable HIGH/MEDIUM vulnerability introduced by these changes.** The mint, cross-tenant, and idempotency surfaces are sound. Detail per threat below, with material citations.

### 1. Mint — NOT exploitable (confidence 9/10)
- **Reachability is gated to service_role.** The RPC has `REVOKE ALL ... FROM PUBLIC, anon, authenticated` + `GRANT EXECUTE ... TO service_role` (migration lines 87–88). Neither anon nor authenticated can call it directly via PostgREST.
- **The downstream credit primitive is itself locked down.** `add_mco_coins(uuid, integer)` was originally granted to `authenticated` (migration `20260505100000:41`) but was later **REVOKED from authenticated and GRANTed to service_role only** (`20260520150000:17-18`). No later migration re-grants it (grep confirmed none). So even reasoning past the RPC, the credit path is service-role-only. `SECURITY DEFINER` on `refund_autopilot_video_enqueue` is irrelevant for privilege escalation here because the caller is already service_role.
- **Amount cannot be inflated.** Two independent backstops: the RPC guard `p_amount <= 0 OR p_amount > 100` raising `22023` (lines 68–69), and the table `CHECK (amount > 0 AND amount <= 100)` (line 25). The caller hardcodes `p_amount: VIDEO_COST` = `12` (orchestrate-step:412,456) — not client-controlled. Worst case an attacker who somehow obtained service-role could credit ≤100/run, but service-role compromise is out of this change's threat model (and already implies total control).
- **Repeated calls cannot mint.** `INSERT ... ON CONFLICT (run_id) DO NOTHING` + `GET DIAGNOSTICS ROW_COUNT` gates the `add_mco_coins` call to the single transaction that actually inserted the marker (lines 73–79). Second call for the same `run_id` → `v_rows = 0` → no-op `{refunded:false}`.

### 2. Cross-tenant — NOT exploitable (confidence 9/10)
- `p_user_id` is `run.user_id`, loaded server-side from the `pipeline_runs` row by primary key (`orchestrate-step:147-151`, `.eq("id", run_id).single()`). It is never read from the request body. The only client input is `run_id` (body, line 136).

There is no path where a caller names an arbitrary beneficiary. No cross-tenant credit.

### 3. Idempotency / double-credit race — NOT exploitable (confidence 8/10)
The `INSERT ... ON CONFLICT (run_id) DO NOTHING` serializes on the unique PK index: under concurrent inserts of the same `run_id`, exactly one transaction inserts (ROW_COUNT=1 → credits once) and the other conflicts (ROW_COUNT=0 → no credit). The `add_mco_coins` call is inside the same transaction guarded by `v_rows > 0`, so the credit is bound to the winning insert. No double-mint.

### 4. orchestrate-step refund-path reachability — confined to cron (confidence 9/10)
