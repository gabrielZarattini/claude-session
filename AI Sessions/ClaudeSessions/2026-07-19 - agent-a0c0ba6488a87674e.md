# Security Review — `supabase/functions/form-submit/index.ts`

## Verdict: NO FINDINGS

No HIGH-confidence (≥8), concretely-exploitable, newly-introduced vulnerability was found. The endpoint is correctly designed for anonymous public submission with a server-resolved tenant boundary.

## Assessment by requested concern

**Tenant/identity — SAFE.** The owning `user_id` is never taken from the request. The request body is destructured as `{ form_id, payload, source }` only (index.ts:28); there is no `user_id` field read from the visitor. `user_id` is resolved server-side from the `forms` row (`select("user_id, is_active, redirect_url").eq("id", formId)`, index.ts:46-47) and passed as `p_user_id: form.user_id` (index.ts:57). A visitor can only ever write to the tenant that owns the `form_id` they submit — there is no path to inject an arbitrary `user_id` or write cross-tenant. Even a `user_id` key smuggled inside `payload` is ignored: the RPC derives the lead's owner exclusively from `p_user_id`, reading only `email`/`phone`/`name` from the payload (migration:44-47).

**Authorization — SAFE.** `crm_capture_lead` has `REVOKE ALL ... FROM public/anon/authenticated` and `GRANT EXECUTE ... TO service_role` (migration:90-93). It is reachable only through this edge function's service-role client (index.ts:40-41). No other privileged operation is exposed; the only other DB touch is the service-role `forms` lookup (by id) and a fire-and-forget `infra_health_logs` insert.

**Injection — SAFE.** `payload` travels as a bound `jsonb` RPC parameter via `admin.rpc(...)` (index.ts:56-58) — the PostgREST/supabase-js path parameterizes it; it is never string-concatenated into SQL. Inside the SECURITY DEFINER function, `search_path = ''` is set and all reads (`p_payload->>'email'`, etc.) and all writes are parameterized jsonb/text operations (migration:42-68). No SQL or JSON-operator injection path exists. `source` is length-capped and bound as a text param.

**Data exposure — SAFE.** The 200 response returns only `lead_id` (a UUID) and the form's own `redirect_url` (index.ts:62) — the redirect_url is the form owner's public config, not another tenant's data. The idempotent upsert can return the id of a pre-existing lead for the same `(user_id, contact)`, but a bare UUID grants nothing (no endpoint here consumes a lead_id to read lead data, and UUIDs are unguessable). The 500 path echoes `rpcErr.message` (index.ts:59) — a minor internal-detail leak, but it is scoped to the form owner's own tenant (all RPC operations are constrained to `p_user_id`), reveals no cross-tenant data, and is not concretely exploitable; below the reporting bar (hardening-class, excluded).

**Active-form gate — ENFORCED.** `if (!form || !form.is_active) return 404` (index.ts:49). Inactive/nonexistent forms are rejected before any lead is written.

**IDOR/enumeration — SAFE.** `form_id` is validated against a UUID regex (index.ts:34) and UUIDs are unguessable per scope. A valid `form_id` grants only the intended public submission; the deal-creation branch re-verifies the pipeline/stage belong to `p_user_id` (migration:78-83), so there is no cross-tenant side effect even with a known form id.

## Notes (not reportable)
- A public form inherently lets any anonymous visitor create/update a lead for the owning tenant (including overwriting `name`/`email` on an existing `(user_id, contact)` via the `ON CONFLICT DO UPDATE`, migration:59-63). This is the intended semantics of public lead capture and is confined to the form's own tenant — it falls under the excluded spam/abuse category, not a privilege or tenancy defect.
- `rpcErr.message` leakage on 500 is a low-severity hardening item, not a concrete exploit.
