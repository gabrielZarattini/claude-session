## Finding 1 — `lead_events` allows cross-tenant lead linkage (FK does not co-scope tenant)

- **Severity:** MEDIUM

**Description.** `lead_events.user_id` is denormalized "for RLS" (line 53). The INSERT policy is `WITH CHECK (auth.uid() = user_id)` (line 64-65), so a caller must set `user_id` to their **own** uid. But the FK `lead_id uuid NOT NULL REFERENCES public.leads(id)` (line 52) references the bare primary key — **not** a composite `(id, user_id)`. The FK existence check fires regardless of who owns the lead. There is no policy clause and no constraint asserting that the referenced `leads` row is also owned by `auth.uid()`. The two checks are therefore independent: RLS proves "the event's `user_id` is mine"; the FK proves "the `lead_id` exists somewhere"; nothing proves "the lead is mine."

**Concrete exploit scenario.** Tenant A learns/guesses tenant B's `lead_id` (a `gen_random_uuid()` v4 — not trivially enumerable, but UUIDs leak through logs, URLs, webhook payloads, the `idx_lead_events_lead` join surface, support exports, or a prior shared-row history). A executes:

```sql
VALUES ('<B_lead_uuid>', auth.uid(), 'web', 'converted', '{"forged":true}');
```

RLS WITH CHECK passes (`user_id = auth.uid()`). The FK passes (B's lead exists). A row now exists binding **A's tenant** to **B's lead id**. Consequences:

1. **Integrity pollution of B's lead graph** — any "Customer 360 / events-per-lead" view that joins `lead_events ON lead_id` (the table's stated purpose, line 48) and is run by a *service-role* aggregator (cron scoring, analytics rollups, the future `lead-score` edge fn) will see A's forged events attached to B's lead, skewing B's score/attribution/revenue. Note B's own RLS-filtered read will NOT see A's row (it's `user_id = A`), so the corruption is invisible to B but live to any cross-tenant/service-role reader — the worst kind.
2. **`erase_lead()` zero-residue control is defeated for this row.** When B erases their lead, `erase_lead()` deletes events with `WHERE lead_id = p_lead_id AND user_id = v_uid` (line 136) — i.e., only B's own events. A's forged event has `user_id = A`, so it is **not** deleted by B's erasure. The parent-lead `ON DELETE CASCADE` (line 52) *will* clean it when `DELETE FROM public.leads` runs (line 145), so there's no dangling FK — but if any future path soft-deletes or the cascade is ever loosened, A's forged PII-adjacent payload survives B's LGPD erasure. The forged `payload jsonb` (line 56) is attacker-controlled and uninspected.

**Why MEDIUM not HIGH:** no confidentiality breach of B's data (A cannot *read* B's lead or events — A only writes a row A owns), and exploitation needs a victim `lead_id` (a random UUID, not sequential). It is a genuine write-side IDOR / integrity hole, not a read leak. Contrast with the canonical `disconnect_meta()` (`20260602160000`), which is fully tenant-safe precisely because it name-binds to the caller's own row id and never trusts a foreign-supplied reference — `lead_events` here trusts a foreign-supplied `lead_id`.

- **Alternative — strengthen the RLS WITH CHECK** to assert ownership of the referenced lead:

- **Tenant guard is real and correct:** it `SELECT user_id INTO v_owner` for the target lead, returns a benign `{erased:false, reason:not_found}` when the lead doesn't exist (line 129-131, no cross-tenant existence oracle beyond not_found), and `RAISE '42501'` when `v_owner <> v_uid` (lines 132-134). A tenant **cannot** erase another tenant's lead. Every DELETE/UPDATE inside is additionally `AND user_id = v_uid`-scoped (lines 136, 142, 145) — defense-in-depth, so even the cascade/consent updates can't reach across tenants.
- **EXECUTE grants are least-privilege:** `REVOKE ALL ... FROM PUBLIC`, `FROM anon`, `GRANT EXECUTE ... TO authenticated` (lines 156-158). Anon/PUBLIC cannot call it; and even if they could, the null-uid guard blocks them. Matches `disconnect_meta`/`disconnect_social` exactly.
- No over-deletion: it removes only the caller's events + the caller's lead, and de-grants (not deletes) the consent. Returns counts, not other tenants' data.

**RLS coverage (default-deny) — complete on all three PII tables.** `leads` (line 30), `lead_events` (line 60), `marketing_consents` (line 90) all `ENABLE ROW LEVEL SECURITY`. With RLS enabled and no permissive catch-all, the default is deny. Every policy is correctly `auth.uid() = user_id` scoped, with matching `USING` + `WITH CHECK` on UPDATE (lines 37, 97) — so a tenant cannot UPDATE a row into another tenant's ownership. The deliberate omission of DELETE policies on `leads` and `marketing_consents` (lines 38, 98) is intentional and correct: client DELETE is fully denied, routing erasure through the definer and retaining consent proof. No over-permissive policy (nothing like the old `FOR ALL` on `whatsapp_leads:24` that would also grant client DELETE).

**Backfill `INSERT...SELECT` (lines 165-181) — safe.** Runs as migration owner (RLS bypassed), which is appropriate for a one-time data absorption. It preserves `wl.user_id` verbatim, so each migrated lead stays owned by its original tenant — no cross-tenant reassignment. No user input is interpolated (pure table-to-table SELECT), so no SQL-injection vector. `ON CONFLICT (user_id, contact) DO NOTHING` (line 181) is idempotent and respects the `uniq_leads_user_contact` constraint — a re-run won't clobber or merge across tenants. The `jsonb_build_object` provenance tag is constant. Sound.

**`marketing_consents` retention / `ON DELETE SET NULL` (lines 78, 87) — no leak, no forgery.** When a lead is erased, the consent's `lead_id` is nulled (de-linking it from the deleted contact PII) while `user_id` remains the original tenant's, and RLS still gates reads to that owner — so the de-linked proof is never exposed to another tenant. `UNIQUE (lead_id)` permits multiple NULL `lead_id` rows in Postgres (NULLs are distinct in a unique index), so retained/erased consents don't collide. Consent forgery across tenants isn't possible: INSERT/UPDATE are `auth.uid() = user_id`-scoped (lines 94-97), so a tenant can only write consent rows it owns. `granted`/`granted_at`/`source_proof` are self-attested per-tenant (same trust model as every per-user table here) — not a cross-tenant issue.
