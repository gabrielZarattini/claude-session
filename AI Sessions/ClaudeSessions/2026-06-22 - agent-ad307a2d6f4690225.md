## Question 1: Does the fix fully close the original finding?

The original finding was: a tenant-controlled `wp_site_url` causes the shared `WP_PUBLISH_SECRET` to be sent to an attacker host. The fix gates header attachment on:

```ts
new URL(apiBase).hostname.toLowerCase() === wpPublishSecretHost.toLowerCase()
```

Walking each bypass vector against `new URL().hostname` semantics (WHATWG URL, which Deno implements):

- **userinfo trick** (`https://www.mcorch.com@attacker.com/...`): `new URL()` parses `www.mcorch.com` as `.username` and `.hostname` resolves to `attacker.com`. Comparison `attacker.com === www.mcorch.com` → **false → secret NOT sent**. SAFE. (This is the key case flagged in the prompt and it resolves correctly.)
- **host:port** (`https://www.mcorch.com:8443`): `.hostname` strips the port (port lives in `.port`), so it yields `www.mcorch.com` → matches. Port is irrelevant to which host receives the secret — the secret still only goes to the legit host. A tenant cannot point the hostname elsewhere while keeping `.hostname` matching. Not a leak. SAFE.
- **trailing dot** (`https://www.mcorch.com./...`): `.hostname` returns `www.mcorch.com.` (with the dot). Comparison vs `www.mcorch.com` → **false → secret NOT sent**. Fail-closed; not a leak. SAFE.
- **case** (`WWW.MCORCH.COM`): both sides `.toLowerCase()` → matches the legit host only. No cross-host leak. SAFE.
- **IDN / punycode**: `new URL()` normalizes Unicode hostnames to ASCII punycode in `.hostname`. A homograph host normalizes to a *different* punycode string than the real host → mismatch → not sent. There is no normalization that maps an attacker-registrable Unicode host onto the legit ASCII host. SAFE.
- **malformed URL**: `new URL()` throws → `catch` block → secret never attached. Fail-closed. SAFE.
- **The fetch itself**: all 3 `fetch()` calls (`/tags?search`, POST `/tags`, POST `/posts`) spread `{ ...wpAuthHeaders }`, and `X-MCORCH-Publish` only exists in that object when the host matched. The connection target is `${apiBase}/...` — same `apiBase` whose `.hostname` was checked, so the host the header is sent to is exactly the host that was validated. There is no TOCTOU gap (`apiBase` is computed once, immutable, checked and used in the same scope).

The one residual nuance is the **redirect** path: `fetch()` defaults to `redirect: "follow"`. If the legit host (matching `WP_PUBLISH_SECRET_HOST`) issues a 30x to an attacker host, Deno/the fetch standard would forward the request. However, that requires the *legit MCORCH-operated origin* to be attacker-controlled to issue such a redirect — which is outside the tenant's control and outside the original threat model (tenant-controlled `wp_site_url`). A tenant cannot set `wp_site_url` to their own host and have it match `WP_PUBLISH_SECRET_HOST`, so they cannot use a redirect to relay the secret. Not a reintroduction of the finding. (Worth noting the code even detects redirect-downgrade behavior at lines 154–168, though that's for method-drop, not secret protection.)

**Conclusion Q1: The original finding is fully closed.** No tenant-controllable input causes the secret to be sent to a host the tenant controls.
