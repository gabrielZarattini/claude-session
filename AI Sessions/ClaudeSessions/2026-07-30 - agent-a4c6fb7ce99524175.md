# Security Review: `public_app_settings` (public auth-visibility flags)

## Verdict: no HIGH or MEDIUM findings

The write path is correctly closed. Below is the verification of each hypothesis raised, then the one LOW-severity item.

---

## Verified as NOT vulnerable

**1. RLS policy interaction (`FOR SELECT USING (true)` vs `FOR ALL` admin) — `20260730120000_public_app_settings.sql:52-62`**
Permissive policies are OR'ed *within the same command*, but the world-readable policy is `FOR SELECT` only, so it is not in the applicable set for `UPDATE`/`DELETE` (USING) or `INSERT` (WITH CHECK). Those commands are gated exclusively by the `FOR ALL` admin policy. An authenticated non-admin issuing `PATCH /public_app_settings?key=eq.auth_signup_visible` gets 0 rows affected — and `useAdminAppSettings.setFlag` (`src/hooks/usePublicAppSettings.ts:79-81`) correctly treats a silent 0-row result as failure rather than success. No bypass.

**2. Anon write path — line 66-68**
`GRANT SELECT ... TO anon` plus an explicit `REVOKE INSERT, UPDATE, DELETE ... FROM anon` neutralizes Supabase's `ALTER DEFAULT PRIVILEGES ... GRANT ALL ... TO anon`. Anon writes fail at the grant layer before RLS is even consulted.

**3. `has_role` reachability — line 22, 61**
The migration comment is correct and load-bearing: `has_role(app_role)` is `REVOKE ALL ... FROM PUBLIC` / `GRANT EXECUTE ... TO authenticated` (`20260414154016:29-30`). Because the anon-facing SELECT policy is a plain `USING (true)` and the `has_role` policy is scoped `TO authenticated`, anon never evaluates a function it cannot execute. No permission-denied fail-open, no fail-closed lockout.

**4. `SECURITY DEFINER` audit trigger — lines 76-110**
`SET search_path = ''` is present and every reference is schema-qualified (`public.audit_logs`, `auth.uid()`, `jsonb_build_object` from `pg_catalog`). `user_id` comes from `auth.uid()`, never from a caller-supplied column, so a forged `user_id` in `audit_logs` is impossible. Non-admins cannot reach the trigger at all (the RLS write gate rejects them before the AFTER trigger fires). The `REVOKE ALL ON FUNCTION` is harmless: PostgreSQL checks `EXECUTE` on a trigger function at `CREATE TRIGGER` time, not at fire time. Matches the hardening of `trg_instead_of_social_app_config` in the reference migration.

**5. CHECK allowlist on `key` — lines 37-39**
A real server-side control, not cosmetic: it is a table constraint enforced on every `INSERT`/`UPDATE` regardless of role, including `service_role`. Even a compromised admin cannot turn this world-readable table into a secret store under a new key without a migration. `foldFlags` (`src/lib/public-app-settings.ts:61`) re-filters client-side as defense in depth — the test at `src/test/public-app-settings.test.ts:44` proves an injected `is_admin` key is dropped.

**6. Free-form `value` jsonb + world-read**
Only admins can write it, and `coerceFlag` (`src/lib/public-app-settings.ts:51-55`) is genuinely fail-closed (`=== true` or the literal string `"true"`). No `dangerouslySetInnerHTML` anywhere in `AuthVisibilityPanel.tsx`; the DB-sourced `description` is fetched but never rendered (the panel renders the hardcoded `PUBLIC_APP_FLAG_META` instead). No stored XSS.

**7. `auth_signup_visible` and `handleSignup` — `src/pages/Auth.tsx:49-69, 244`**
The flag is UI-only. It does not touch GoTrue's `disable_signup` setting, so it does not bypass any server-side control — external signup is already enabled at the API level, and `supabase.auth.signUp` is reachable via the public anon key with or without the tab rendered. `handle_new_user()` (`20260402014040:356`) assigns role `viewer`, not an elevated role, so there is no privilege-escalation-by-registration path. This is a discoverability/product decision, not a new vulnerability.

**8. Client fail-open**
`usePublicAppFlags` (`src/hooks/usePublicAppSettings.ts:53`) returns `PUBLIC_APP_FLAG_DEFAULTS` (all false) while loading, on error, and on a denied read. Correctly fail-closed, and per review precedent, client-side gating is not the control anyway.

## LOW (below the HIGH/MEDIUM reporting bar — noted, not a blocker)

# Vuln 1: Anonymous exposure of an admin's `auth.users` UUID via `updated_by`: `supabase/migrations/20260730120000_public_app_settings.sql:66`

* Severity: Low
* Category: Data Exposure
* Confidence: 0.85 (exposure certain; meaningful downstream impact not demonstrated)
* Description: `GRANT SELECT ON public.public_app_settings TO anon` is table-wide, and the RLS policy is `USING (true)`. The table carries `updated_by UUID REFERENCES auth.users(id)` (line 35). After the first admin toggle, that column holds a real admin user id and becomes readable by unauthenticated clients. This deviates from the house pattern for anon-reachable relations containing sensitive columns, which uses **column-level** grants — see `20260414150946:14` (`GRANT SELECT (id, user_id, plan, ...) ON public.subscriptions TO authenticated, anon`) and `20260531193000:24` (`meta_config`). The application only ever selects `key, value, description, updated_at` (`src/hooks/usePublicAppSettings.ts:28`), so `updated_by` is exposed without being needed. The SOP's G4 gate (`docs/processes/public-auth-visibility-flags.md:56`) asserts `updated_by` is written but does not note it is world-readable.
* Exploit Scenario: An unauthenticated attacker with the publishable anon key (present in the shipped frontend bundle) issues `GET /rest/v1/public_app_settings?select=updated_by` and recovers the internal UUID of the admin account. This does not by itself grant access — every RLS policy in the codebase keys off `auth.uid()` rather than a client-supplied id — but it hands an attacker a confirmed high-value account identifier for targeted follow-on attacks and removes any guessing cost.
* Recommendation: Replace the table-wide grant with a column-level one, matching the existing precedent:
  ```sql
  REVOKE SELECT ON public.public_app_settings FROM anon, authenticated;
  GRANT SELECT (key, value, description, updated_at) ON public.public_app_settings TO anon, authenticated;
  GRANT SELECT (updated_by) ON public.public_app_settings TO authenticated; -- if the admin UI ever needs it
  ```
  No client change is required — the hook already selects only the four safe columns. Optionally add a `COMMENT` noting that any future column on this table is world-readable by default.

And `update_updated_at_column()` (`20260530210000:16-22`) is `SECURITY INVOKER`, so attaching it to this table introduces no definer surface.
