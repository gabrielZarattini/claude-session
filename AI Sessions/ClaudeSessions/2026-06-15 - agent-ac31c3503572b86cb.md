## Security Review — vision-mcp Fatia 2 uncommitted changes

### Finding 1 — Redirect-follow SSRF bypasses the host allowlist in `analyze_video` (direct-fetch path)

- **File:line:** `packages/vision-mcp-core/src/tools/analyze-video.ts:80-87` (the `fetchInlineVideo` bare `fetch(url)`), guard at `analyze-video.ts:50-73`.
- **Severity:** MEDIUM (HIGH reachability, bounded impact — blind/low-bandwidth-exfil GET SSRF into the Sovereign Mesh / cloud metadata range).
- **Category:** SSRF (host/protocol-controlling — in scope).
- **Description:** `assertSafeVideoUrl()` validates only the *initial* URL's hostname against the private/loopback/link-local denylist and enforces `https:`. The subsequent `fetchInlineVideo` calls `fetch(url)` with default options, and Node/undici's `fetch` follows HTTP redirects automatically (`redirect: "follow"`, up to 20 hops) **without re-validating the redirect target**. An attacker-controlled public host can return `302 Location: http://169.254.169.254/...` or `http://mcorch_chroma:8001/...`, and the container will fetch the internal/metadata target. The redirect also downgrades the protocol gate (initial `https` passes; the `http://` redirect is followed). This is the same container that holds `SB_SECRET_KEY` and sits on the internal Docker mesh network (chroma/claude_mem/daemon) on cloud infra.
- **Concrete exploit scenario:** Any authenticated tenant (free if they have a BYOK `google_api_key`, since cost is 0; otherwise 2 mco, refunded on the downstream Gemini failure) calls `vision_analyze_video` with `video_url=https://attacker.com/v.mp4`. `attacker.com` responds `302 → http://169.254.169.254/opc/v1/instance/` (OCI IMDS) or an internal mesh service. The container fetches the internal resource, base64-encodes the body, and sends it to Gemini; Gemini's natural-language *description of the fetched bytes* is returned to the attacker — a low-bandwidth read-exfil of internal/metadata responses, plus blind GET reachability to any internal service. The fatia2 tests (`fatia2.test.ts:41,55`) only assert the *initial-URL* denylist, so this bypass is untested.
- **Fix recommendation:** Disable redirect-following and re-validate on each hop: pass `{ redirect: "manual" }` to `fetch`, and if a `3xx` with a `Location` is returned, re-run `assertSafeVideoUrl` (including the `https:`-only check) against the resolved `Location` before re-fetching (loop with a hop cap). Alternatively, resolve the hostname to its IPs and reject if any resolved address is private/link-local/loopback (defeats DNS-rebinding too), and reject non-`https` redirect targets. Apply the same hardening anywhere the container itself fetches a user-supplied URL.
- **Confidence:** 8/10 that the redirect-follow bypass is real and reachable; ~6/10 that a high-value internal target (IMDS/secret) is actually reachable+exfiltratable end-to-end from this specific deployment (depends on OCI IMDS version/header requirements and what internal services answer a plain GET) — hence MEDIUM overall.
