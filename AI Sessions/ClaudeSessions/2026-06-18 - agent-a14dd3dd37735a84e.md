## FLAGGED GOTCHAS FOR IMPLEMENTATION

1. **Daily-profit job uses cash flow, not realized PnL.** A daily-loss cap CANNOT use the same logic. Must snapshot equity at UTC midnight and compare current equity.

2. **TRADING_HALT is loaded once at module init.** To make it a true hot-switch, refactor to read from MEMORY or a polled file at request time, not `process.env` at load.

3. **Mid-day restart preserves halt state via disk file, but only clears on next UTC rollover.** If the cap triggers at noon and the server restarts at 1pm, the flag stays until UTC midnight (day boundary). Plan for this in the UX (manual reset endpoint).

4. **Beholder MEMORY is volatile.** Persist daily-cap state to disk (`logs/daily_cap_state.json`) to recover on restart.

5. **getUTCDate() is day-of-month only (1–31).** Month boundaries work (30 → 1), but the string `"lastCheckDay"` pattern is not timezone-safe for systems running non-UTC. Use `new Date().toISOString().split('T')[0]` (YYYY-MM-DD) for global safety.

6. **No realized-PnL helper exists.** To compute true PnL for audits, iterate orders by cost-basis (getFarmPosition + getTrendPosition give you the scaffold, but you must compute matching buys→sells).

7. **Exchange.js is the chokepoint, but MCP tools are gated at the tool level** (`tradingEnabled()` check, `TRADEUX_ALLOW_TRADING` env). The hot-halt in exchange.js is backend-only; if the MCP gate is open but exchange.js halts, the agent sees an error (good fail-closed behavior, but coherence for the operator depends on both being in sync).
