**Category:** Broken access control / RLS cross-tenant read (claim vector)

### Description
The new policy grants `SELECT` on a `canvas-assets` object when:
```sql
EXISTS (SELECT 1 FROM public.vm_canvas_projects p
        WHERE p.id::text = (storage.foldername(storage.objects.name))[1]

```
This trusts `vm_canvas_projects.id` as a proof of ownership of the object folder prefix. But `vm_canvas_projects` **does not** force a server-side `id`:

Canvas objects are stored under a `<uid>/` prefix (`canvas-execute/index.ts:494` → `fileName = \`${user.id}/${execution.id}.${ext}\``), and the folder prefix is compared against `p.id`. An attacker can mint a project row whose `id` equals a victim's folder prefix.

### Concrete exploit
Attacker is any authenticated tenant B; victim is tenant A with uid `A_UID`.

1. Attacker sends a raw insert (RLS allows it — only `user_id` is checked):

   `WITH CHECK (auth.uid() = user_id)` passes. No id trigger rewrites it. No PK collision (no real project has `id == A_UID`, since project ids are random UUIDs, not user uids).
2. The new Branch C now evaluates TRUE for every object named `A_UID/<...>`:
   `p.id::text = foldername[1] = 'A_UID'` and `p.user_id = auth.uid()`.
3. Attacker calls `supabase.storage.from('canvas-assets').list('A_UID/')` → RLS returns the victim's objects (full enumeration), then `createSignedUrl(...)` on each → downloads the victim's private images.
