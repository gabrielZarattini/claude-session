## 0. Princípio-mestre do modelo (não-negociável)

| Regra | Fonte | Consequência no schema |
|-------|-------|------------------------|
| **NADA de mídia de terceiro na spine `creative_assets`** | OTD-CI-001 · FM-CI-01 | O cache de mp4 mora em **bucket isolado próprio** (`content-intel-cache`) + tabela **`media_cache`** dedicada. `creative_assets` (com `provenance_*`) serve **só derivados OWNED** — contaminá-la corromperia a marcação AI Act Art.50. |
| **O byte expira em 30d; a estratégia nunca** | §5 · OTD-CI-005 | `media_cache` tem `expires_at`+`purged_at`; **`content_strategy` NÃO tem `expires_at`**. O purge zera `storage_key`/`bytes` mas preserva a linha de estratégia. |
| **Idempotência por hash da URL** | §5 | `url_hash = sha256(normalize(url))` é a chave de dedup/idempotência (cache-hit ⇒ sem baixar, sem cobrar). |
| **Isolamento per-tenant é sacrosanto** | CLAUDE.md · FM-CI-14 · API Tenancy Model | Cache e estratégia são **per-user** (RLS `auth.uid()`). Cache **não** é global-compartilhado: um tenant não pode free-ride no download que outro pagou (seria o anti-pattern "compartilhar quota/revenue" — fraude por design). **Decisão de modelagem:** `url_hash` continua sendo o eixo de idempotência, mas a PK física é **composta `(user_id, url_hash)`** — preserva idempotência *por-tenant* E isolamento. Refina OTD-CI-005. |

## 1. Conceptual Data Model

```
                          (paga só no miss · deduct_mco_coins)
[auth.users] ──1:N──▶ [media_cache] ═══1:1(url_hash)═══▶ [content_strategy]
     │  (tenant)        (EFÊMERO 30d)   fonte da verdade   (PERSISTENTE ∞)
     │                       │                                    │
     │                       │ storage_key → bucket PRIVADO       │ ANALYZED_INTO
     │                       ▼   isolado `content-intel-cache`     ▼
     │              [storage.objects]                     [mcorch_nodes]
     │              (byte purgado no sweep)          observation (auto-embed)
     │                                                        │
     └────────────────────────────────────────────── INFORMS ─┘
                                                  (loop → geração paga)

  ✗ NUNCA:  media de terceiro ──▶ [creative_assets]  (spine OWNED · OTD-CI-001/FM-CI-01)
```

**Entities:**
- **`media_cache`** — índice do cache **EFÊMERO** de mídia de terceiro (a *linha* vive; o *byte* expira em 30d). Uma linha por `(tenant, url normalizada)`. Aponta para o objeto no bucket privado isolado enquanto não purgado. Nunca re-servida ao cliente.
- **`content_strategy`** — o **ARTEFATO TEXTUAL de 1ª classe** e **PERSISTENTE**: posicionamento, taxonomia de gancho, cadência (só se houver métrica oficial), diferenciação. Sobrevive ao purge do mp4. É o que a UI mostra e o que alimenta a geração.
- **`mcorch_nodes` (observation)** — nó de conhecimento inserido por análise; o trigger `AFTER INSERT` embeda sozinho (NÃO chamar `embed-mcorch-node` manual — §6). Liga o intel ao GraphRAG e ao loop de geração.
- **`creative_assets` (referência negativa)** — a spine OWNED com `provenance_*`. **Fora deste modelo por design** — citada só para cravar a fronteira.

**Cardinalidades:** `media_cache` 1:1 `content_strategy` por `url_hash` (a análise é o resultado único daquela mídia+tenant); `media_cache` 1:N `mcorch_nodes` (reanálises geram observations distintas); `user` 1:N ambas.

```sql
-- ── Erase RPC do purge (Storage via API, NUNCA DELETE em storage.objects) ───
-- Molde: 20260615200000 (OTD-VM-026). SECURITY DEFINER service-role-only;
-- retorna storage_paths p/ o worker chamar storage.remove — SQL não deleta o byte.
CREATE OR REPLACE FUNCTION public.erase_content_intel_expired(p_batch int DEFAULT 100)
RETURNS TABLE (user_id uuid, url_hash text, storage_key text)
LANGUAGE sql SECURITY DEFINER SET search_path = '' AS $$
  SELECT mc.user_id, mc.url_hash, mc.storage_key
  FROM public.media_cache mc
  WHERE mc.expires_at < now()
    AND mc.purged_at IS NULL
    AND mc.storage_key IS NOT NULL
  LIMIT p_batch;
$$;
REVOKE ALL ON FUNCTION public.erase_content_intel_expired(int) FROM public, authenticated, anon;
-- GRANT só service_role (o worker de sweep). O UPDATE purged_at ocorre APÓS remove OK.
```

> **Gate FM-CI-06:** o purge do byte é **sempre** `storage.remove(storage_key)` via Storage API, disparado pelo worker a partir dos `storage_paths` que a RPC retorna. **Nunca `DELETE` SQL em `storage.objects`** (orfaniza o byte — oposto da economia). O `UPDATE ... SET storage_key=NULL, bytes=0, purged_at=now()` só ocorre **depois** do remove OK ⇒ falha reentra no próximo sweep (idempotente).
