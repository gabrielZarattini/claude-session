A RPC de estorno\n\n```sql\nCREATE OR REPLACE FUNCTION public.reverse_mco_topup(\n  p_session_id text, p_event_id text, p_reason text   -- 'refund' | 'dispute'\n) RETURNS jsonb LANGUAGE plpgsql SECURITY DEFINER SET search_path = ''\nAS $$\nDECLARE v_t public.mco_topups%ROWTYPE; v_bal numeric; v_debit int; v_unrec int;\nBEGIN\n  SELECT * INTO v_t FROM public.mco_topups WHERE session_id = p_session_id FOR UPDATE;\n  IF v_t.session_id IS NULL THEN\n    RETURN jsonb_build_object('reversed', false, 'reason', 'topup_not_found');\n  END IF;\n  IF v_t.reversed_mco > 0 THEN                       -- idempotente\n    RETURN jsonb_build_object('reversed', false, 'reason', 'already_reversed');\n  END IF;\n  IF v_t.status <> 'credited' THEN                   -- nunca creditou ⇒ nada a debitar\n    UPDATE public.mco_topups SET status='reversed', updated_at=now() WHERE session_id=p_session_id;\n    RETURN jsonb_build_object('reversed', true, 'debited', 0, 'reason', 'never_credited');\n  END IF;\n\n  SELECT mco_balance INTO v_bal FROM public.profiles WHERE id = v_t.user_id FOR UPDATE;\n  v_debit := LEAST(v_t.mco_amount, GREATEST(0, floor(coalesce(v_bal, 0))::int));\n  v_unrec := v_t.mco_amount - v_debit;               -- a dívida que NÃO dá para recuperar\n\n  IF v_debit > 0 THEN\n    UPDATE public.profiles SET mco_balance = GREATEST(0, mco_balance - v_debit), updated_at = now()\n     WHERE id = v_t.user_id;\n    INSERT INTO public.mcoin_transactions (user_id, action, amount, context)\n    VALUES (v_t.user_id, 'topup_reversal', -v_debit,\n            jsonb_build_object('session_id', p_session_id, 'event_id', p_event_id,\n                               'reason', p_reason, 'unrecovered_mco', v_unrec));\n  END IF;\n\n  UPDATE public.mco_topups\n     SET status = CASE WHEN p_reason='dispute' THEN 'disputed' ELSE 'reversed' END,\n         reversed_mco = v_t.mco_amount, unrecovered_mco = v_unrec, updated_at = now()\n   WHERE session_id = p_session_id;\n\n  RETURN jsonb_build_object('reversed', true, 'debited', v_debit, 'unrecovered', v_unrec);\nEND;\n$$;\nREVOKE ALL ON FUNCTION public.reverse_mco_topup(text,text,text) FROM PUBLIC, anon, authenticated;\nGRANT EXECUTE ON FUNCTION public.reverse_mco_topup(text,text,text) TO service_role;\n```\n\n**Por que UPDATE direto e não `deduct_mco_coins`:** o `deduct` levanta exceção quando o saldo é insuficiente (aqui queremos débito **parcial**, não falha) e recusa conta congelada (aqui queremos reverter **mesmo** congelada). O UPDATE é provavelmente seguro porque `v_debit ∈ [0, mco_amount]` e `mco_amount ≤ 5000` pelo CHECK, com `GREATEST(0, …)` impedindo saldo negativo. Passa pelo trigger `trg_profiles_block_privileged_client_update` porque este só barra `current_user IN ('authenticated','anon')` (`20260701010000:31-43`).\n\n---\n\n## 7. Chargeback e disputa\n\n### 8.1 O que acontece hoje\n\n**Nada.** O `switch` do `stripe-webhook:107-124` tem exatamente 4 `case` (três de assinatura + `checkout.session.completed`) e **nenhum `default`**. `charge.refunded` e `charge.dispute.created` caem no vazio e a função responde 200.\n\n### 8.2 A política proposta\n\n> **Débito reverso até zero. Sem bloqueio automático. Dívida irrecuperável registrada, não escondida.**\n\n1. **Resolver** a compra por `payment_intent_id` → `mco_topups`.\n2. **`reverse_mco_topup`** debita `LEAST(mco_da_compra, saldo_atual)` — nunca deixa o saldo negativo. Nunca `add_mco_coins` com negativo (proibido pela lei anti-mint).\n3. **A diferença é gravada** em `unrecovered_mco` e emitida como telemetria. Ela não é apagada nem arredondada para zero.\n4. **Bloqueio:** enquanto `status='disputed'`, novas recargas são recusadas para aquele usuário. **Congelar a conta (`is_frozen`) é ação MANUAL do Sovereign** — o precedente `admin_set_frozen` existe. Congelamento automático puniria disputa legítima (cobrança duplicada do banco, por exemplo) e, com duas usuárias reais e conhecidas, o falso positivo custa mais que a fraude.\n5. **Prevenção**, que é a parte que de fato protege: teto de **3 recargas por 24h por usuário** (FR-MON-023) + Radar do Stripe ligado. Sem KYC.\n\n### 8.3 O que é impossível recuperar — sem eufemismo\n\n**O mco já gasto virou trabalho consumido.** Um vídeo gerado queimou chamada de provedor, CPU do host, storage, e provavelmente já foi publicado. Não existe \"des-gerar\". O débito reverso recupera **saldo**, não **custo**.\n\nTrês cenários, honestamente:\n\n| Cenário | Recuperado | Perdido |\n|---|---|---|\n| Estorno com saldo intacto | 100% | R$0 (fora a taxa do Stripe) |\n| Estorno com metade gasta | 50% do saldo | 50% do mco + o custo real da produção |\n| Estorno com saldo zero | **0** | 100% — e é o cenário do fraudador competente |\n\nSob a política BYOK nova, a perda MÁXIMA por fraude é limitada e conhecida: o maior pacote (3.000 mco = R$967) e o custo de infra correspondente é nosso (fila e storage), porque **o provedor foi pago com a chave do próprio fraudador**. Isso é uma consequência boa e não-óbvia do BYOK: **a fraude fica barata para nós**.\n\n---\n\n## 9.
