`planIsHighImpact` fails *open* when `row.plan` is not a JSON array: `_shared/intent-policy.ts:30` is `Array.isArray(tasks) && tasks.some(...)`, so a non-array `plan` (e.g. a JSON object `{"0": {...high-impact...}}`) evaluates to `false`. Because `intent_plans` RLS lets the owner UPDATE their own row with no status-transition CHECK (`20260603250000:26`), a plan owner could, via direct PostgREST, set `plan` to an object **and** `status='auto_approved'`, then call `intent-execute` with `decision='execute'` and reach `status='executed'` while skipping HITL.

Why this is **not** a reportable vuln today:
- **No privilege/tenant boundary is crossed** — the attacker is the plan's own owner acting only on their own row; nothing here grants access to another tenant or to a capability they couldn't otherwise self-authorize.
- **No material effect.** `executed` has no downstream consumer: there is no trigger, no `pg_net`, and no outward dispatch on `intent_plans` (confirmed — the only references to the table are the two edge functions; `intent-execute/index.ts:100-104` explicitly returns `outward_dispatch: "gated"` and performs no send, matching the gated-sends posture of `nurture-dispatch`). So the worst outcome is a mislabeled state-machine row in the owner's own tenant.

Hardening suggestion (cheap, future-proofs the gate before real dispatch is wired in): make the gate fail *closed* on malformed input, e.g. treat a non-array `plan` as high-impact in `planIsHighImpact` (`return !Array.isArray(tasks) || tasks.some(...)`), and/or add a status-transition CHECK/trigger on `intent_plans` so only `intent-execute` (service role) can move a row to `approved`/`executed`. This matters specifically once the "gated" outward dispatch at `intent-execute/index.ts:100` is replaced with a real campaign-run/nurture send.
