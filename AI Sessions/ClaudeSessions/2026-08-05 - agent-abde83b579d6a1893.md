## Perguntas do escopo — veredito
1. **Cross-tenant delete:** NÃO. Todo DELETE carrega `.eq("user_id", user.id)` (`spaces-queue-cancel:73`, `cleanup:106,108`); `storage.remove` só recebe keys de linhas `creative_assets` owner-scoped + prefixo `<uid>/` forçado; client não pode INSERT/UPDATE `creative_assets` nem `video_renders` (default-deny), então `storage_key` é sempre server-authored; posse do projeto verificada antes dos dois sweeps. Keys de Storage são nomes literais no DB — `../` não atravessa.
2. **Escalada via body:** NÃO. `render_id` é owner+engine+state-scoped no SELECT **e** no DELETE; `candidate_keys` passam por `isDraftKey(k, uid)` com o uid **autenticado** (`cleanup:55`) e nunca alimentam o `remove()` — só probe/echo.
3. **Bypass da allowlist:** masters/vozes/Veo genuinamente fora (prefixo/bucket); **mas o SFX pago está DENTRO** — F1.
4. **Abort induzido por terceiro:** NÃO. `cancelledRenders` só arma quando o UPDATE `eq(id).eq(state,'running')` afeta 0 linhas **sem** erro; a linha só some/flipa por rotas service-role owner-verified; RLS nega UPDATE/DELETE ao client; org members só SELECT. UUIDs de render não são adivinháveis/escolhíveis.
