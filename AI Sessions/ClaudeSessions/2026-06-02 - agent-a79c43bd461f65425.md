### 1. Guard correctly prevents cross-tenant credential writes (INSERT + UPDATE)

The guard `auth.role() IS DISTINCT FROM 'service_role' AND NEW.user_id IS DISTINCT FROM auth.uid()` is applied to both INSERT and UPDATE on both triggers.

- **INSERT (the gap being closed):** Previously, the masked view granted INSERT to `authenticated` and the INSTEAD OF trigger runs SECURITY DEFINER (bypassing base-table RLS). Postgres does not apply a view's `WHERE` to INSERT, so a caller could insert with a spoofed `NEW.user_id` (a victim's) + fresh `id`, committing a victim-owned credential row with attacker-controlled tokens — a service-role publisher iterating `decrypted_*` rows would then use the injected credential (content redirection / credential confusion). The guard now rejects this with `42501`. Correct fix.
- **NULL semantics:** `IS DISTINCT FROM` is the right operator (not `<>`). If a malicious client sends `NEW.user_id = NULL`, then `NULL IS DISTINCT FROM auth.uid()` is **TRUE** → the guard fires and rejects. (A plain `<>` would have returned NULL → treated as not-true → bypass. The chosen operator closes that.) `user_id` is also `NOT NULL` on both base tables, so a NULL would fail anyway.
- **UPDATE:** Same guard. A non-service-role caller cannot set `NEW.user_id` to anything other than its own `auth.uid()`.

### 2. `SET search_path = ''` with `auth.uid()` / `auth.role()`

No break and no bypass. ### 3. UPDATE branch — `WHERE id = OLD.id` vs guard on `NEW.user_id` (the subtle one)

This is the most important thing to get right, and it is safe:

- In an INSTEAD OF UPDATE trigger on a view, the trigger fires **once per row the view's SELECT produces** under the statement's predicate. The view is `WHERE (auth.uid() = user_id OR auth.role() = 'service_role')`. So for a non-service-role caller, the **only** `OLD` rows that can ever materialize are rows where `user_id = auth.uid()`. A caller cannot conjure an `OLD.id` pointing at a victim's row, because the victim's row is not visible through the view to that caller — PostgREST `?id=eq.<victim-uuid>` simply matches zero view rows and the trigger never fires for it. So `WHERE id = OLD.id` is implicitly tenant-scoped by the view predicate that produced `OLD`.

The legitimate client (`useMetaConfig.upsertConfig`) never sends `user_id` in the UPDATE payload at all → `NEW.user_id` defaults to `OLD.user_id` (= self) → guard passes. A non-service-role caller cannot move their own row to a victim (would set `NEW.user_id = victim` → blocked) nor pull a victim's row to themselves (victim row invisible as `OLD`). Both directions are closed.
- **service_role:** service_role can update any visible row to any `user_id` — that is the intended, legitimate OAuth-callback/cron behavior, identical to the established pattern.

One honest note (not a vuln, and **pre-existing**, not introduced here): the guard validates `NEW.user_id` but the function does not re-assert `OLD.user_id = auth.uid()` independently — it relies on the view predicate to scope `OLD`. This is the same trust model as the verbatim prior code and the sibling `user_api_keys` trigger, and it holds because the view is SECURITY DEFINER with the `auth.uid() = user_id` filter baked in. No exploit path exists for a non-service-role caller.
