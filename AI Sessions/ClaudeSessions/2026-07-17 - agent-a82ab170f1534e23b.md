### 4. O que NÃO consegui sustentar (⚠️ could_not_verify)

- ⚠️ **Percentual numérico de "success rate" de IP de datacenter** (ex.: "X% de sucesso"): **nenhuma fonte** — nem primária nem vendor — publicou um número quantificado. Todas as fontes descrevem em termos binários/qualitativos ("blocked instantly", "first request", "usual failure point"). A proxies.sx foi consultada explicitamente para isso e **não traz percentuais** (confirmado no fetch). Não fabrico o número.
- ⚠️ **Oracle Cloud (AS31898) especificamente**: as fontes citam AWS/GCP/DigitalOcean nominalmente; Oracle **não é nomeada** em nenhuma fonte pública encontrada. Porém o mecanismo descrito é **bloqueio por ASN de datacenter genérico** (blocklists de ASN de hosting), o que inclui Oracle por classe — e é consistente com a nota do próprio CLAUDE.md deste repo (WordPress CF: challenge por reputação do IP de datacenter Oracle AS31898). Marco como inferência-por-classe, não como fonte que nomeia Oracle.

### 5. Síntese acionável para o blueprint content-intel

**Fato de projeto (sustentado):** ingest de mídia externa (Reels/TikTok) via yt-dlp/instaloader **não funciona a partir do host Oracle do MCORCH** sob acesso anônimo — o IP de datacenter é bloqueado na primeira requisição (Instagram) / antes do render (TikTok). Os dois caminhos de mitigação documentados:
1. **Sessão autenticada** (`--cookies`/login instaloader) — atenua Instagram, mas amarra a uma conta real (risco de ban da conta, não só do IP).
2. **Proxy residencial/móvel rotativo** — requisito para TikTok e para volume no Instagram; **custo USD recorrente** → colide com a doutrina open-source-first / USD=0 do MCORCH.

**Recomendação de materialidade:** este gap tem sub-item que permanece aberto e deve virar OTD →
