The issue is real—when an admin clicks the `/auth` link, it opens in a new tab but immediately redirects to `/dashboard` because they're already authenticated, so they never see the login screen. But functionally nothing breaks: the flag toggle still works and the public `/auth` endpoint reads the flag correctly. The only person affected is the admin using this panel, and there's no material harm to the system.

The label itself already instructs the admin to verify in an anonymous window, so the copy mitigates the confusion. If an admin clicks the link and sees the dashboard instead, they'll be briefly confused but then follow the parenthetical instruction and open an incognito window. There's no wrong state, no exposure, no data loss—just a few seconds of confusion. And realistically, there's no way for any in-app link to show a logged-in admin the anonymous view anyway; that's inherent to how the app's SSO routing works, not a defect introduced here.

I'm also questioning whether this is really a P2 issue. In this codebase, P2 typically means a real user-visible defect worth fixing soon, but this is more of a cosmetic UX polish item—a link that behaves slightly differently from its label, with mitigating copy right next to it. That feels more like P4 or P3 at most, so calling it P2 might be inflated by a couple of levels.
