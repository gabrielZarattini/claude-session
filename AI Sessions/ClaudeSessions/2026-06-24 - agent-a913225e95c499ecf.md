## VEREDITO DE REVISÃO ADVERSARIAL

**DECISÃO: APPROVE_COM_SUGESTOES**

---

### 1. O HIGH (re-trim-loop) está FECHADO? **SIM**

A lógica de `Math.min(floor(TRIGGER*0.8), env_value)` **garante invariante**: `KEEP_BYTES ≤ 0.8 × TRIM_TRIGGER_BYTES` sempre, independentemente de env-overrides. Após trim, arquivo ≈ 12MB < 16MB (80% de 20MB default), logo próximos appends não triggam novo trim até dias depois. **Impossível re-trim-loop.**

---

### 2. Perda-de-dado nova? **SIM, MAS CONTROLADA**

**Vulnerabilidade real encontrada:**
- `readSync(offset, buffer)` pode ler buffer terminando no meio de char UTF-8 multibyte
- `toString('utf8')` descarta bytes órfãos silenciosamente, substitui por U+FFFD (`�`)
- Código (linhas 48–50) descarta a **primeira** linha parcial, mas **não valida o último byte**

**Cenário:**
- Arquivo termina com emoji (🤖 = `F0 9F A4 96`, 4 bytes UTF-8)
- readSync lê apenas `F0 9F A4` (faltando `96`)
- toString converte para `"test\uFFFD"` (replacement character invisível)
- Último record fica gravado com `U+FFFD` embutido no JSON

**Mitigação parcial:**
- Leitores fazem `try/catch` em JSON.parse (ignoram linhas corrompidas)
- agentHeartbeatJob já descarta linhas com replacement char (indretamente)
- recentOwnerNotifications() usa readFileSync full-file (sem problema)

**Severidade: MEDIUM** — silencioso, último record pode conter Unicode destrutivo/invisível, mas falha não é catastrófica (é descartado na leitura).

---

### 3. KEEP_BYTES cobre os 3 leitores? **SIM**

Validado:
- **agentController.js** (/agent/runs): precisa ~5000 linhas = ~7.5MB. KEEP_BYTES=12MB → **cobre com 60% margem**
- **agentHeartbeatJob.js**: tail-read 1MB + fallback full-read. 12MB >> 1MB. **Seguro**
- **recentOwnerNotifications()**: readFileSync inteiro (~5 records). **Sem limite, full-file seguro**

---

### 4. Crash/race entre writeFileSync(tmp) e renameSync? **SEGURO**

- Linux rename atômico: backend :ro vê **inode antigo inteiro OU novo inteiro, nunca pela metade**
- Crash entre write e rename: tmp fica órfão, sobrescrito na próxima trim (sem vazamento)
- **Sem corrupção.**

---

### 5. Regressão vs versão por-linhas? **NÃO**

Versão antiga (c008375): append-only, cresce ilimitado (~2–4MB/dia).
Versão nova: trim raro (a cada dias), arquivo capped ~12MB.

Benefício: less I/O, mais estável. Último `cycle_end` preservado, últimos `notify_owner` intactos. **Melhoria limpa.**
