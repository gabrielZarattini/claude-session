async function deployStrategy(strategyName, symbol, regime) {
  // 1. Busca recipe do StrategyLibrary
  const recipe = strategyLibrary.getRecipe(strategyName);
  
  // 2. Cria templates + automações idempotentes
  for (const tpl of recipe.templates) {
    await ensureTemplate(tpl);

    }
  }
}

      await updateAutomation(auto.id, { conditions: newCondition });
    }

### (E) RISCOS, GOTCHAS E CONHECIDOS

#### **1. BRAIN CACHEIA ORDER TEMPLATES**

**Risco**: Atualizar orderTemplate via `PATCH /ordertemplates/:id` NÃO re-compila BRAIN imediatamente.

**Manifestação**: 
- Você edita "Trend Buy" template (ex: muda limitPrice)
- A automação id6 segue usando a versão **velha** em memória
- Até que alguém `PATCH /automations/:id` (ou start/stop/delete)

**Mitigação**:
- Em `orderTemplatesController.updateOrderTemplate()`, adicione:
  ```javascript
  // Acha automações que usam este template
  const actions = await actionsRepository.getActionsByTemplateId(id);
  for (const action of actions) {
    const auto = await automationsRepository.getAutomation(action.automationId);
    if (auto.isActive) {
      beholder.deleteBrain(auto);
      beholder.updateBrain(auto); // Recompila com novo template
    }
  }
  ```

---

#### **2. AUTOMAÇÕES RUNTIME NÃO-SEEDADAS SOMEM EM `make nuke`**

**Risco**: Scripts setup-* criam automações isActive=false; você ativa via UI, depois `make nuke` (down -v) deleta volume → tudo reseta.

**Manifestação**:
- `node scripts/setup-trend.js` → cria id6/id7 INATIVAS
- `node scripts/activate-trend.js` → ativa id6/id7 + edita id2/id3
- `make nuke` → volume postgres deletado
- Nas próximas automações, id6/id7 voltam INATIVAS (seeders são idempotentes)

**Mitigação**:
- Adicionar seeder de "automations ativas por regime" que rodeia no boot
- Ou persistir estado de regime/activation numa tabela config

---

#### **3. INDEXES FAIL-SAFE OPCIONALMENTE NÃO-ENFORÇADO**

**Risco**: Se você esquecer de adicionar um índice crítico (ex: REGIME) nas automações, elas ficam "fail-open" (disparam mesmo com regime desconhecido).

**Manifestação**:
- id2 (Farm Buy) condition: `RSI<35 && REGIME!=='bear'`
- Mas **REGIME não está em indexes**
- No boot, antes do regime job popular, isChecked = true (índice ausente não é validado)
- Farm compra mesmo com regime=undefined

**Mitigação**:
- Validação em `automationsController.insertAutomation()`:
  ```javascript
  const missingIndexes = findMissingIndexesInCondition(conditions, indexes);
  if (missingIndexes.length) {
    return res.status(400).json(`Missing indexes: ${missingIndexes}`);
  }
  ```

#### **4. CONDIÇÕES INVERTIDAS (EDGE vs LEVEL TRIGGER)**

**Risco**: A function `invertCondition()` [beholder.js:139] re-inverte a condição para evitar multi-fire (anti-empilhamento), mas **nem sempre é segura**:

**Manifestação**:
- Condição original: `MEMORY['SYM:BOOK'].current.bestBid > 50000` (level-trigger: sempre true enquanto bestBid>50k)
- Invertida: `MEMORY['SYM:BOOK'].previous.bestBid <= 50000` (edge-trigger: só na cruzamento 49999→50000)
- **Problema**: Se o preço oscila 49.9k ↔ 50.1k, a inversão previne re-fire correto

**Mitigação**: Consulte `shouldntInvert()` [beholder.js:825]:
```javascript
function shouldntInvert(automation, memoryKey) {
  return ['GRID', 'TRAILING'].includes(automation.actions[0].type)
    || automation.schedule
    || automation.conditions.indexOf('HARVEST_SELLING') !== -1  // Harvest = level
    || memoryKey.indexOf(':LAST_ORDER') !== -1                 // LAST_ORDER = edge
    || memoryKey.indexOf(':LAST_CANDLE') !== -1;               // Candles = discrete
}
```

**Gotcha**: Farm/Harvest venda **são** level-triggers (disparar enquanto bestBid>alvo), então estão blindadas de inversão. Se você criar um no-loss **customizado** sem incluir `:HARVEST_SELLING` ou `:FARM_SELLING` na condition, sofrerá inversão indevida.

---

#### **5. MEMORY KEYS MULTIUSO SEM NAMESPACE**

**Risco**: `MEMORY['BTCUSDT:LAST_ORDER']` é compartilhado por **todas** as automações do símbolo. Farm compra, Trend lê a mesma LAST_ORDER.

**Manifestação**:
- Farm compra → LAST_ORDER = Farm
- Trend venda dispara → calcQty usa TREND_QTY (não LAST_ORDER)
- Se Trend buy tiver disparado antes de Farm, LAST_ORDER=Trend
- Farm sell usa LAST_ORDER_QTY → acaba vendendo quantidade errada

**Mitigação**:
- Farm: usa `LAST_ORDER_QTY` (OK, cobre caso acima)
- Trend: força `TREND_QTY` (não LAST_ORDER)
- Harvest: força `HARVEST_QTY` (bucket isolado)
- **Regra**: Se compartilhar símbolo, não misture keywords que dependem de LAST_ORDER em múltiplas automações (ou use buckets tipo FARM_DCA/HARVEST/TREND_QTY)

---

#### **6. OCO ANTIPILHAMENTO: TRAVA ABERTA vs FECHADA**

**Risco**: OCO é "uma lista por automação+símbolo" (line 341 beholder.js: `getOpenOcoOrders(automation.id)`). Mas se OCO parcialmente preencher, a trava fica "stuck".

**Manifestação**:
- OCO abre (TP + SL)
- Uma perna executa (ex: TP), outra cancela (Binance automático)
- Automação re-dispara → `getOpenOcoOrders()` retorna vazio (ambas resolvidas)
- Automação re-cria OCO (OK, anti-empilhamento funcionou)

**Gotcha**: Se getOpenOcoOrders() returnar 1 perna *parcial* (em raro edge case de API flake), trava impede re-colocação até que seja reconciada (problema menor, quase nunca acontece).

---

#### **7. FARM_SELLING / HARVEST_SELLING: MUTEX VOLÁTIL**

**Risco**: Travas `FARM_SELLING` e `HARVEST_SELLING` em MEMORY[**'SYM'**] são **voláteis** (resetam no restart). Se servidor cair **após** place mas **antes** do status terminal no DB, a venda fica órfã.

**Manifestação**:
- Ordem de venda Farm é enviada à Binance
- FARM_SELLING é setado em MEMORY
- Servidor crasheia
- Restart: MEMORY zerada, FARM_SELLING = undefined
- Se bestBid ainda > alvo, a automação re-dispara e coloca **2ª venda** (oversell)

**Mitigação Parcial**:
- `app-em.js:469` **checks** FARM_SELLING para anti-empilhamento
- Mas a trava é **liberada** apenas no estado terminal (app-em:307: match orderId)
- Solução: Persistir travamento de venda na DB (tabela lockState ou campo em automation)

---

#### **8. MIN_NOTIONAL BACKSTOP SÓ PARA COMPRAS**

**Risco**: Backstop de $5 (beholder.js:290) **só aplica a `quantity='MIN_NOTIONAL'`**, não a outras keywords.

**Manifestação**:
- Template Harvester: quantity='HARVEST_QTY' (lê bucket), quantityMultiplier=0.5
- Se o bucket tem 0.00001 BTC (~$0.60 a $60k), calcQty returna 0.00001 × 0.5 ≈ $0.30
- Ordem colocada é rejeitada com **-1013 (NOTIONAL)**, não retorna erro, falha silenciosa

**Mitigação**:
- Validar **todo** quantidade contra symbol.minNotional em calcQty (antes de returnar):
  ```javascript
  const notional = qty * parseFloat(price);
  if (notional < symbol.minNotional) {
    throw new Error(`Ordem ${qty}@${price}=$${notional} abaixo de minNotional $${symbol.minNotional}`);
  }
  ```

---

#### **9. REGIME JOB CACHEADO (PRESERVA ÚLTIMO REGIME EM STALE)**

**Risco**: Se regimeJob der erro ou Binance cair, o último regime **persiste em MEMORY** (não é zerado). Gate continua operando com regime **velho**.

**Manifestação**:
- regimeJob falha (ex: Binance timeout)
- MEMORY['BTCUSDT:REGIME'] = 'bear' (do último sucesso, 1h atrás)
- Mercado virou bull (em dados reais mainnet)
- Sua automação acha que é bear, **não compra**
- STALE logger avisa (regimeJob.js:91), mas operador pode não ver

**Mitigação**:
- regimeJob implementa stale-check (MAX_AGE=default ~5min)
- Se dado ficar velho, avisa em log
- Você deve **monitorar logs** ou adicionar alerta no Telegram (sugerido em regimeJob.js:116-120 para FASE4_MACRO_SYMBOL)
