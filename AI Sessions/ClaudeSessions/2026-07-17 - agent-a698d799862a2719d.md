> ## Cache-Aside Pattern Overview
> 
> The Cache-Aside pattern, also known as Lazy Loading, is a widely-used and simple approach to caching. In the Cache-Aside pattern, the application code is responsible for loading data into the cache on demand.
> 
> ## How It Works
> 
> The pattern operates in two phases:
> 
> **Read Path:** The application first checks the cache. If the data is not in the cache (a cache miss), it fetches it from the underlying data store (e.g., Azure SQL Database or Cosmos DB), stores it in the cache, and returns the result. If the data is in the cache (a cache hit), it is returned immediately.
> 
> **Write Path:** When an application updates information, it writes the change to the data store and then invalidates the corresponding item in the cache.
>

> ## How Content-Addressable Storage Works
> 
> Content-addressable storage (CAS) is a storage paradigm where data is identified and retrieved based on its content rather than its location or file name, using a cryptographic hash function to generate a unique identifier for each piece of data.
> 
> ## The Core Principle: Same Content = Same Key
> 
> The identifier (hash) is deterministic, meaning the same content will always produce the same hash, enabling deduplication. This principle is fundamental to how CAS achieves automatic deduplication: identical content always produces the same hash, and if the same file exists in multiple places, they all map to the same identifier, and the system stores only one copy.
> 
> ## Idempotency and Automatic Deduplication
> 
> Deduplication is not a separate feature the administrator configures — it is a direct product of how addressing works. The system's behavior is inherently idempotent: hash the content and use the hash as the key, ensuring same content produces the same hash and storage location.
> 
> ## Data Integrity
> 
> Any change to the content produces a different hash, so you cannot silently modify a stored object and have it retrieved under the old address—either the modified content is stored as a new object with a new address, or the modification is detected when the hash fails to match.

# Frente 3 — Arquitetura de Cache Efêmero + Retenção 30 Dias para Mídia Reanalisada

## Veredito (TL;DR)
O padrão canônico para "baixar mídia pesada → analisar → descartar o arquivo, reter só o resultado leve" é a combinação de três padrões maduros e documentados:

1. **Cache-aside (lazy loading) com TTL** — a mídia pesada é um *cache transiente* com expiração; a análise é a *fonte da verdade persistente*.
2. **Object Lifecycle Management** — o mecanismo nativo de S3/GCS que expira objetos por idade (ex.: 30 dias). **Supabase Storage NÃO tem esse mecanismo nativo** → tem que ser emulado por **sweep via cron/worker**.
3. **Idempotência por chave** — `url_hash` (hash do link normalizado) como chave de dedup/idempotência, na mesma família conceitual do *idempotency key* (Stripe) e do *content-addressable storage*.

---

## 1. Cache efêmero = padrão Cache-Aside (Lazy Loading) com TTL

O modelo "baixar sob demanda → popular cache → expirar" é literalmente o **Cache-Aside Pattern** do Azure Architecture Center:

> "the application is responsible for loading data into the cache on demand" — no *miss*, busca na fonte, popula o cache e retorna; **"Always set expiration times for cache keys to prevent stale data buildup"** e "ensure that the expiration policy matches the pattern of access".
> Fonte: https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside

Aplicado ao seu caso, a inversão-chave é: **o objeto caro (mp4 do reel, 5–50MB) é o item de cache descartável; o barato (JSON de análise) é o dado durável.** Isso é a economia central — você trata a mídia pesada como *derivada regenerável* (basta re-baixar o link) e nunca como estado primário. A regra "TTL casado com o padrão de acesso" justifica a janela de 30 dias: dentro dela, reanálise = cache hit (grátis); fora dela, o link provavelmente já mudou/expirou e re-baixar é aceitável.

⚠️ Nota de materialidade: o cache-aside clássico assume um cache tipo Redis. Aqui o "cache" é um *bucket de Storage* com linha de índice no Postgres — a mecânica de TTL é a mesma, mas a expiração não é automática (ver §3).

---

## 2. Object Lifecycle Management — o padrão de referência dos storages

Os grandes storages implementam retenção-por-idade **nativamente**. Vale citar como o "padrão-ouro" que estamos emulando:

**AWS S3 — Lifecycle / Expiration actions:**
> "S3 Lifecycle helps you store objects cost effectively... deleting expired objects on your behalf." "**Expiration actions** – These actions define when objects expire. Amazon S3 deletes expired objects on your behalf." E o detalhe de billing: "**you won't be charged for storage after the expiration time**" — a cobrança para no momento da elegibilidade, mesmo antes do delete físico (que é assíncrono, "days or even weeks later").
> Fonte: https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lifecycle-mgmt.html
> Config: https://docs.aws.amazon.com/AmazonS3/latest/userguide/how-to-set-lifecycle-configuration-intro.html

Exemplo de regra de expiração por N dias (`"Expiration": { "Days": 90 }`):
Fonte: https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-configuration-examples.html

**Google Cloud Storage — Object Lifecycle Management:**
> Delete action + condition `age` (dias desde a criação): `"rule":[{"action":{"type":"Delete"},"condition":{"age":365}}]`. Execução é **assíncrona**: "there can be a lag between when the conditions are satisfied and when the action is taken" e "may still perform actions based on the old configuration for up to 24 hours".
> Fonte: https://docs.cloud.google.com/storage/docs/lifecycle
> Exemplos: https://docs.cloud.google.com/storage/docs/lifecycle-configurations

**Lição arquitetural transferível:** a expiração é *eventual/assíncrona* mesmo nos storages nativos — nenhum sistema promete delete no instante exato do vencimento. Isso valida um sweep diário (não precisa ser de minuto-a-minuto) e valida separar **`expires_at` (semântica: quando para de valer)** de **delete físico (quando o byte some)**.

## 3. Supabase Storage NÃO tem lifecycle nativo → sweep por cron/worker (decisão material)

Confirmado em fonte primária que o Supabase **não expõe** Object Lifecycle:

> Feature request aberto (#20171), não implementado: "When uploading a file to s3 you have the option to add lifecycles to expire the object after a set period. This API should be exposed to the storage side of supabase." — permanece sem entrega.

**Portanto, o TTL tem que ser emulado.** O caminho documentado é **pg_cron + pg_net → Edge Function** que varre e deleta:

> Supabase Cron usa a extensão pg_cron; "Create Jobs to call Database Functions, Supabase Edge Functions, and even remote webhooks"; caso de uso explícito: "**Maintenance: delete or archive old data**". Para chamar Edge Function no schedule, usa-se pg_cron + pg_net (HTTP de dentro do Postgres).

> "**Deleting objects via a SQL query will not remove the object from the bucket and will result in the object being orphaned.**" → deletar SEMPRE via Storage API (`remove`), nunca `DELETE FROM storage.objects`.

Ou seja: o sweep **não pode** ser um `DELETE` SQL puro na linha do `media_cache` + na `storage.objects`. Isto se encaixa exatamente no molde de worker que vocês já têm (`provenance-bridge`/`video-bridge`: sweep de fila + ação via API + fail-soft).

## 4. Idempotência — `url_hash` como chave (não re-baixar, não re-cobrar)

Dois padrões grounded convergem para a chave `url_hash`:

**(a) Content-Addressable Storage (CAS)** — a idempotência é uma *consequência do endereçamento*, não uma feature à parte:
> "The identifier (hash) is deterministic... the same content will always produce the same hash, enabling deduplication." "hash the content and use the hash as the key" → comportamento "inherently idempotent".
> Fontes: https://en.wikipedia.org/wiki/Content-addressable_storage · https://lab.abilian.com/Tech/Databases%20&%20Persistence/Content%20Addressable%20Storage%20(CAS)/

No seu caso a chave natural é o **hash da URL normalizada** (não do conteúdo — você não quer baixar o byte só para descobrir se já analisou). `url_hash = sha256(normalize(url))` vira a PK de lookup: se existe linha com `analyzed_at` e `now() < expires_at` → **cache hit, retorna o `analysis` sem baixar nem cobrar**.

**(b) Idempotency Key (Stripe)** — o contrato de "mesma chave ⇒ mesmo efeito uma vez":
> Idempotência = endpoint "can be called any number of times while guaranteeing that side effects only occur once". Em retry com a mesma chave o servidor "simply replies with a cached result of the successful operation" em vez de repetir a operação.
> Fonte: https://stripe.com/blog/idempotency

Detalhes do contrato Stripe que valem como guardrails de design (via docs Stripe):
- Chave deve mapear sempre a **mesma intenção**: mesma chave + parâmetros diferentes → erro (400). ⚠️ (número "400" e a regra vêm do resumo de https://docs.stripe.com/error-low-level; não fiz fetch full dessa página — trate como "documentado pela Stripe", não verbatim conferido por mim.)
- ⚠️ Stripe documenta expiração das chaves "after 24 hours" — mas essa é a janela *da Stripe*; a **sua** janela de idempotência é justamente os **30 dias** do `expires_at`. Não copie o 24h; ele só ilustra que idempotency key tem TTL próprio.

**Regra de cobrança idempotente (aplicação ao mcoCoins):** cobre a análise **só no miss** (quando efetivamente baixa+analisa). Hit dentro da janela = HTTP 200 com o `analysis` cacheado e **débito zero**. Isso espelha "side effects only occur once" — o custo é o side-effect que não pode duplicar.

## 5. Esquema de dados proposto (fundamentado)

Separação estrita **cache efêmero** vs **verdade persistente** (o coração da Frente 3):

```
media_cache                       -- índice do cache EFÊMERO (a linha vive, o byte expira)
  url_hash      text  PK          -- sha256(normalize(url)) — idempotência/dedup (§4)
  source_url    text              -- link original (auditoria)
  storage_key   text  NULL        -- caminho no bucket privado; NULL após sweep físico
  bytes         bigint            -- tamanho baixado (telemetria de economia)
  analyzed_at   timestamptz       -- quando a análise concluiu
  expires_at    timestamptz       -- analyzed_at + interval '30 days'  (o TTL — §2/§3)
  purged_at     timestamptz NULL  -- quando o byte pesado foi removido via Storage API
  -- índice: (expires_at) para o sweep varrer "WHERE expires_at < now() AND purged_at IS NULL"

media_analysis                    -- resultado LEVE, PERSISTENTE (sobrevive ao purge)
  url_hash      text  FK→media_cache(url_hash)
  analysis      jsonb             -- o JSON leve (o que você realmente guarda)
  model/version text              -- proveniência da análise
  created_at    timestamptz

```

Ponto crítico de design: **`media_analysis` não tem `expires_at`.** O purge da §3 zera `storage_key`/`bytes` (some o mp4) mas **preserva `media_analysis`** — exatamente o "descartar o arquivo pesado, manter só o resultado leve". Uma reanálise pós-expiração é uma *decisão explícita* (re-baixa + nova cobrança), não um efeito colateral do sweep.

## 6. Retention Sweep 30 dias — mecânica concreta

**Job diário (pg_cron), fail-soft, molde `provenance-bridge`:**

1. `SELECT url_hash, storage_key FROM media_cache WHERE expires_at < now() AND purged_at IS NULL LIMIT <batch>` (paginado — S3/GCS também operam em lote/assíncrono; ver §2).
2. Para cada linha: **`storage.remove(storage_key)` via Storage API** (nunca SQL — §3 gotcha).
3. `UPDATE media_cache SET storage_key = NULL, bytes = 0, purged_at = now()` **só após** o remove retornar OK (idempotente: se o remove falhar, a linha reentra no próximo sweep).
4. `media_analysis` intocado.
5. Telemetria em `infra_health_logs` (`service='media-cache-sweep'`, bytes liberados) — casa com o mandato de mesh/watchdog do CLAUDE.md.

**Por que sweep diário e não "no instante do vencimento":** os próprios storages nativos deletam de forma **assíncrona/eventual** (S3: "days or even weeks later"; GCS: "up to 24 hours" de lag) — a semântica correta é *"expirou" (para de valer / para de contar) ≠ "byte deletado"*. `expires_at` governa a idempotência/cobrança (imediato); o purge físico é eventual (diário). Fontes: S3 e GCS docs (§2).
