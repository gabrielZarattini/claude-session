A tensão obrigação fiscal × direito de erasure é real → **OTD-MON-007** (revisão jurídica).\n\n### 4.5 Retrofits obrigatórios (mesma migration)\n\n```sql\n-- O ledger canônico é a ÚNICA tabela financeira da casa sem no-delete restritivo.\nCREATE POLICY \"mcoin_transactions_no_client_delete\"\n  ON public.mcoin_transactions AS RESTRICTIVE FOR DELETE USING (false);\n```\n\n> ⚠️ Esta policy **não** protege contra `soft_reset_account`, que é SECURITY DEFINER e faz `DELETE FROM mcoin_transactions WHERE user_id = p_user_id` (`20260527005036:52`) — RLS é integralmente bypassada por definer/owner. A RPC de estorno\n\n```sql\nCREATE OR REPLACE FUNCTION public.reverse_mco_topup(\n  p_session_id text, p_event_id text, p_reason text   -- 'refund' | 'dispute'\n) RETURNS jsonb LANGUAGE plpgsql SECURITY DEFINER SET search_path = ''\nAS $$\nDECLARE v_t public.mco_topups%ROWTYPE; v_bal numeric; v_debit int; v_unrec int;\nBEGIN\n  SELECT * INTO v_t FROM public.mco_topups WHERE session_id = p_session_id FOR UPDATE;\n  IF v_t.session_id IS NULL THEN\n    RETURN jsonb_build_object('reversed', false, 'reason', 'topup_not_found');\n  END IF;\n  IF v_t.reversed_mco > 0 THEN                       -- idempotente\n    RETURN jsonb_build_object('reversed', false, 'reason', 'already_reversed');\n  END IF;\n  IF v_t.status <> 'credited' THEN                   -- nunca creditou ⇒ nada a debitar\n    UPDATE public.mco_topups SET status='reversed', updated_at=now() WHERE session_id=p_session_id;\n    RETURN jsonb_build_object('reversed', true, 'debited', 0, 'reason', 'never_credited');\n  END IF;\n\n  SELECT mco_balance INTO v_bal FROM public.profiles WHERE id = v_t.user_id FOR UPDATE;\n  v_debit := LEAST(v_t.mco_amount, GREATEST(0, floor(coalesce(v_bal, 0))::int));\n  v_unrec := v_t.mco_amount - v_debit;               -- a dívida que NÃO dá para recuperar\n\n  IF v_debit > 0 THEN\n    UPDATE public.profiles SET mco_balance = GREATEST(0, mco_balance - v_debit), updated_at = now()\n     WHERE id = v_t.user_id;\n    INSERT INTO public.mcoin_transactions (user_id, action, amount, context)\n    VALUES (v_t.user_id, 'topup_reversal', -v_debit,\n            jsonb_build_object('session_id', p_session_id, 'event_id', p_event_id,\n                               'reason', p_reason, 'unrecovered_mco', v_unrec));\n  END IF;\n\n  UPDATE public.mco_topups\n     SET status = CASE WHEN p_reason='dispute' THEN 'disputed' ELSE 'reversed' END,\n         reversed_mco = v_t.mco_amount, unrecovered_mco = v_unrec, updated_at = now()\n   WHERE session_id = p_session_id;\n\n  RETURN jsonb_build_object('reversed', true, 'debited', v_debit, 'unrecovered', v_unrec);\nEND;\n$$;\nREVOKE ALL ON FUNCTION public.reverse_mco_topup(text,text,text) FROM PUBLIC, anon, authenticated;\nGRANT EXECUTE ON FUNCTION public.reverse_mco_topup(text,text,text) TO service_role;\n```\n\n**Por que UPDATE direto e não `deduct_mco_coins`:** o `deduct` levanta exceção quando o saldo é insuficiente (aqui queremos débito **parcial**, não falha) e recusa conta congelada (aqui queremos reverter **mesmo** congelada). O UPDATE é provavelmente seguro porque `v_debit ∈ [0, mco_amount]` e `mco_amount ≤ 5000` pelo CHECK, com `GREATEST(0, …)` impedindo saldo negativo. Passa pelo trigger `trg_profiles_block_privileged_client_update` porque este só barra `current_user IN ('authenticated','anon')` (`20260701010000:31-43`).\n\n---\n\n## 7. Chargeback e disputa\n\n### 8.1 O que acontece hoje\n\n**Nada.** O `switch` do `stripe-webhook:107-124` tem exatamente 4 `case` (três de assinatura + `checkout.session.completed`) e **nenhum `default`**. `charge.refunded` e `charge.dispute.created` caem no vazio e a função responde 200.\n\n### 8.2 A política proposta\n\n> **Débito reverso até zero. Sem bloqueio automático. Dívida irrecuperável registrada, não escondida.**\n\n1. **Resolver** a compra por `payment_intent_id` → `mco_topups`.\n2. **`reverse_mco_topup`** debita `LEAST(mco_da_compra, saldo_atual)` — nunca deixa o saldo negativo. Nunca `add_mco_coins` com negativo (proibido pela lei anti-mint).\n3. **A diferença é gravada** em `unrecovered_mco` e emitida como telemetria. Ela não é apagada nem arredondada para zero.\n4. **Bloqueio:** enquanto `status='disputed'`, novas recargas são recusadas para aquele usuário. **Congelar a conta (`is_frozen`) é ação MANUAL do Sovereign** — o precedente `admin_set_frozen` existe. Congelamento automático puniria disputa legítima (cobrança duplicada do banco, por exemplo) e, com duas usuárias reais e conhecidas, o falso positivo custa mais que a fraude.\n5. **Prevenção**, que é a parte que de fato protege: teto de **3 recargas por 24h por usuário** (FR-MON-023) + Radar do Stripe ligado. Sem KYC.\n\n### 8.3 O que é impossível recuperar — sem eufemismo\n\n**O mco já gasto virou trabalho consumido.** Um vídeo gerado queimou chamada de provedor, CPU do host, storage, e provavelmente já foi publicado. Não existe \"des-gerar\". O débito reverso recupera **saldo**, não **custo**.\n\nTrês cenários, honestamente:\n\n| Cenário | Recuperado | Perdido |\n|---|---|---|\n| Estorno com saldo intacto | 100% | R$0 (fora a taxa do Stripe) |\n| Estorno com metade gasta | 50% do saldo | 50% do mco + o custo real da produção |\n| Estorno com saldo zero | **0** | 100% — e é o cenário do fraudador competente |\n\nSob a política BYOK nova, a perda MÁXIMA por fraude é limitada e conhecida: o maior pacote (3.000 mco = R$967) e o custo de infra correspondente é nosso (fila e storage), porque **o provedor foi pago com a chave do próprio fraudador**. Isso é uma consequência boa e não-óbvia do BYOK: **a fraude fica barata para nós**.\n\n---\n\n## 9. But there's a potential race condition with concurrent `INSERT ... ON CONFLICT (session_id) DO NOTHING` statements — in READ COMMITTED isolation, the second transaction will wait on the uniqueness constraint, then execute DO NOTHING once the first commits, returning zero rows affected.

The real vulnerability though is that the webhook calls `credit_mco_topup` via RPC, and if each RPC call is its own transaction rather than part of the parent transaction, a failure in one doesn't roll back the other — the topup insert could succeed while the coin credit fails, leaving the system inconsistent. The webhook event insert returns a 200 duplicate response without ever checking the `handled` flag, so if the function crashes between inserting the event and actually crediting the account, the payment is silently lost forever—the retry gets poisoned by the dedupe layer. This is a genuine P1 hole: money taken but never delivered, and the `mco_topups` primary key would've caught it if the event-dedupe hadn't short-circuited the flow first.

There's a second failure mode with async payments: when `checkout.session.completed` arrives first (pending state), it writes a row with the event ID, then `async_payment_succeeded` tries to credit via an insert-on-conflict that returns zero rows because the pending row already exists—so it returns `already_processed` and never actually credits the account. The design has no update path from pending to credited in the RPC, leaving the payment stuck forever. The same Stripe session can trigger two different events, which I've already covered. On refunds and chargebacks, if `reverse_mco_topup` gets called for a partial refund, it debits the full MCO amount instead of the partial amount — that's user harm and a P2 issue. There's also a potential mint vector around disputes, but the thought cuts off there. The metadata can be updated via the Stripe API with the secret key, so that's not directly exploitable. The real vulnerability angle is cross-mode confusion — a session created in test mode getting delivered to the live webhook, but that fails because the signing secrets differ. The design also needs to handle the signature verification properly for webhook authenticity. anyone can create a Stripe account and trigger test webhooks, but they'd need our endpoint secret to forge a valid signature. The real vulnerability is that we never verify the event's `livemode` flag matches our environment or that the session actually belongs to our account — the signature only proves it came from Stripe, not that it's ours. There's also a potential issue where if the secret key mode (test vs. live) doesn't match the event mode, the session retrieval fails and triggers infinite retries. I'm also considering an attack where someone replays an old session ID from months ago.

The `award_mco_coins` function was properly secured in the migration that revoked access, and even though `CREATE OR REPLACE` preserves existing grants, the ordering works out because the hardening migration ran first before the revocation. But there's a critical design issue lurking with how `credit_mco`

This means an attacker could call the function with arbitrary parameters like a fresh session ID and large amounts, potentially exploiting the gap between the old and new signatures.

The real vulnerability is that `credit_mco_topup` is a mint primitive protected only by database grants, and this codebase has a documented history of grant-drift bugs causing live mints. The migration log shows a past incident where a REVOKE removed `authenticated` access but left `anon`/PUBLIC exposed, resulting in unauthorized minting. The design needs defense-in-depth—either an internal `auth.role()` check within the function itself, or better yet, having the RPC verify the payment actually occurred instead of blindly trusting the caller's `p_amount_cents` parameter.

The strongest mitigation would be requiring the caller to be `service_role`, adding a `session_id` format guard (like `cs_live_%`), ensuring the row doesn't already exist, and critically—verifying the event exists in `stripe_webhook_events` before processing.
