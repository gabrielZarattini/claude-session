## Security review — `scripts/host-upload-server.ts` + `useVideoRepurpose.ts`

**No HIGH-confidence, concretely-exploitable vulnerability found in the in-scope categories (arbitrary-file-write outside inbox, auth bypass, admin-gate bypass).** Nothing to report at confidence ≥7. Details per scrutiny point below.

### 1. Auth bypass / admin-gate bypass — NOT exploitable
The write at `host-upload-server.ts:80` is unreachable without passing BOTH gates, and both fail closed:
- **JWT gate (L52–64):** rejects missing/`non-Bearer` (401), and `admin.auth.getUser(token)` hits GoTrue which validates signature+expiry server-side; invalid/expired → `{user:null}`/error → 401. The `try/catch` also closes on thrown malformed-token cases. `userId` is taken from the verified `user.id` (server-trusted), never from the client.
- **Admin gate (L67–68):** service-role query on `user_roles` for `role='admin'`; `!adminRow` → 403. On a `.maybeSingle()` error (e.g. duplicate rows) `data` is null → still 403 (fail-closed; worst case is a false-negative for a legit admin, not a bypass).
- No early-write path exists; every failure `return`s before line 80. Spoofing `Authorization`/`X-Filename` at the edge is useless because the JWT is cryptographically verified server-side.

### 2. Path traversal / arbitrary write outside inbox — NOT exploitable
`sanitize` (L36–38) replaces every char outside `[a-zA-Z0-9._-]` with `_`, so `/` and `\` are stripped → the result is always a single path component with no separator; `..` sequences survive only as literal `.._..` text, never as a traversal. I simulated the real `sanitize`+`join`+`resolve` containment against 12 payloads (`../../../etc/passwd`, `/etc/passwd`, `..\..\win`, `foo/../../../root/.ssh/authorized_keys`, long-prefix+`../`, etc.): **every one stays inside `repurpose-inbox/<uid>/` (`contained:true`).** The only inputs producing `contained:false` are bare `..` and `.` (resolving to the inbox parent / the inbox dir itself) — both correctly rejected by the trailing-slash containment check at L74 (400 `bad_path`), and a directory write would fail anyway. `userId` is JWT-derived, so no cross-user path injection. `slice(-120)` is applied last, to the already-sanitized string, so it cannot reintroduce forbidden chars or a prefix. Overwriting `dist/*.js`, `.env`, systemd units, or ssh keys is not reachable.

### 3. In-inbox overwrite — acceptable
A filename collision overwrites the caller's own `repurpose-inbox/<uid>/<name>` file. Since `userId` is from the JWT, there is no cross-user overwrite. Own-data overwrite is not a vuln.

### 4. Body streaming — NOT an injection vector
`Readable.fromWeb(req.body)` → `createWriteStream(dest)` writes raw bytes to a file the worker later ffprobes (realpath-contained per prior review). Bytes are never executed/interpreted at this layer.

### 5. Public exposure (Cloudflare + nginx) — no header-spoof bypass
`Authorization` is verified via the Supabase JWT, so a forged bearer is rejected. `X-Filename` only influences the sanitized filename within the caller's own inbox. No trust is placed in client headers beyond that.

### Sub-threshold observations (noted, not findings; do NOT meet ≥7 or are out of scope)
- **Info disclosure (low, ~3):** the 500 path returns `detail: e.message` (`host-upload-server.ts:88`), which can leak host filesystem paths — but only to an already-authenticated admin. Consider dropping `detail` from the client-facing body.
- **DoS (explicitly excluded):** `maxRequestBodySize: 6GB` + `proxy_request_buffering off` allow large writes filling host disk — but the endpoint is admin-gated and DoS/resource-exhaustion is out of scope.
