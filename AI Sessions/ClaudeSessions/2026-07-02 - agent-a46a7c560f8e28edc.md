# Canonical atomic ledger/billing RPC patterns (MCORCH) — for the Spaces Fase 1b generations ledger

## 1. The canonical pattern (three reference implementations)

### 1a. Service-role-only enforcement = GRANT SURFACE, not in-body check
For system-only RPCs the codebase does **NOT** write an `auth.role()` check inside the body. It relies exclusively on:
```sql
REVOKE ALL ON FUNCTION public.finalize_vision_job(uuid, text, int, int, jsonb, jsonb) FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION public.finalize_vision_job(uuid, text, int, int, jsonb, jsonb) TO service_role;
```
(`supabase/migrations/20260615160000_vision_mcp_jobs.sql:105-106`; identical trailer in `20260620120200_begin_autopilot_cycle.sql:107-108`, `20260620120300_finalize_autopilot_cycle.sql:69-70`, `20260624140000_autopilot_video_enqueue_refund.sql:87-88`.)
The rationale is explicit in `20260701030000_revoke_anon_execute_privileged_rpcs.sql:17-20`: an internal `auth.role()` guard would wrongly block a legitimate call made from *inside another* service-role-only SECURITY DEFINER function (auth.role() stays the original JWT role); a role without EXECUTE simply cannot reach the fn via PostgREST. That same migration documents the **grant-drift lesson**: a past REVOKE removed `authenticated` but not `anon`/PUBLIC, letting an unauthenticated caller mint (`20260701030000:3-10`). Convention: always `REVOKE ... FROM PUBLIC, anon, authenticated` in the SAME migration that creates the fn (Postgres grants EXECUTE to PUBLIC by default). Drift guard: `scripts/qa/audit-privileged-rpc-grants.sh` (`20260701030000:20`).

In-body `auth.role()` checks appear ONLY on client-callable RPCs: `deduct_mco_coins` Guard 2 and `admin_set_frozen` (`20260701010000:111-113,148-150`), both using the NULL-safe form `auth.role() IS DISTINCT FROM 'service_role'` ("codebase standard — see 20260602150000", fails CLOSED on NULL).

All money RPCs are `LANGUAGE plpgsql SECURITY DEFINER` returning `jsonb` (finalize/begin/refund) or `void`/`integer` (deduct/add).

### 1b. Advisory lock (begin only — anti-TOCTOU on aggregates)
`20260620120200_begin_autopilot_cycle.sql:48-49`:
```sql
-- Serialize concurrent cycles for THIS tenant (anti-TOCTOU on the daily-cap aggregate). Transaction-scoped.
PERFORM pg_advisory_xact_lock(hashtext(p_user_id::text));
```
Used ONLY where a cap check reads an **aggregate** (daily SUM at `:77-85`) that a concurrent tx could race. Order inside the lock: cap checks → soft-abort returns (`jsonb ('ok',false,'reason',...)` WITHOUT debiting, `:61-85`) → INSERT cycle row → `PERFORM public.deduct_mco_coins(...)` in the SAME transaction (`:91-99`), so a deduct RAISE rolls the INSERT back ("atomic, no orphan debited cycle", `:95-97`). Finalizers do NOT use advisory locks — they use the claimed-UPDATE idempotency guard instead (1c). Per-row races are covered by deduct's own `FOR UPDATE` row lock.

### 1c. Idempotent finalize = single guarded UPDATE claim + RETURNING
`finalize_vision_job` (`20260615160000:75-93`):
```sql
IF p_state NOT IN ('done','partial','failed') THEN
  RAISE EXCEPTION 'finalize_vision_job: terminal state required, got %', p_state USING errcode = '22023';
END IF;
UPDATE public.vision_jobs
   SET state = p_state, ...
 WHERE id = p_job_id
   AND state IN ('queued','running')
 RETURNING user_id INTO v_uid;
IF v_uid IS NULL THEN
  RETURN jsonb_build_object('finalized', false);   -- already terminal → no-op (no double refund)
END IF;
```
"Exactly the FIRST finalizer wins (worker OR poll lazy-reconcile OR future sweep)" (`:55-57`). `finalize_autopilot_cycle` mirrors it with `AND status = 'running'` (`20260620120300:41-52`). **Key tenant-safety nuance: the finalize RPC never accepts user_id from the caller — it resolves `user_id` from the claimed row via RETURNING** and credits that uid. The no-row variant (`refund_autopilot_video_enqueue`, `20260624140000:72-83`) replaces the state guard with a PK idempotency anchor: `INSERT ... ON CONFLICT (run_id) DO NOTHING; GET DIAGNOSTICS v_rows = ROW_COUNT;` → credit only when `v_rows > 0`.

### 1d. Refund = POSITIVE credit via add_mco_coins, same transaction
Never a negative deduct — `deduct_mco_coins` Guard 1 rejects `<= 0` "so there is no negative-deduct path anywhere" (`20260620120200:12-13`). `finalize_vision_job:95-98`:
```sql
-- Guard write (above) + balance credit commit in the SAME transaction.
IF p_amount > 0 THEN
  PERFORM public.add_mco_coins(v_uid, p_amount);
```
`finalize_autopilot_cycle` computes `v_refund := GREATEST(0, v_spend - p_actual_mco)` (clamped, `:44,54`) and additionally inserts the **symmetric positive ledger row** (`20260620120300:56-61`):
```sql
PERFORM public.add_mco_coins(v_uid, v_refund);
INSERT INTO public.mcoin_transactions (user_id, action, amount, context)
VALUES (v_uid, 'autopilot_refund', v_refund, jsonb_build_object('cycle_id', p_cycle_id, ...));
```
(the spend row was `-projected`, written by deduct). Comment doctrine: "never money-without-guard nor guard-without-money" (`20260615160000:57`).

### 1e. CHECK constraints (defense-in-depth on ledger tables)
- `vision_jobs` (`20260615160000:21-27`): `state CHECK (state IN ('queued','running','done','partial','failed'))`, `planned_units >= 1`, `delivered_units >= 0`, `charged_mco >= 0`, and the anti-mint cap `refunded_mco IS NULL OR (refunded_mco >= 0 AND refunded_mco <= charged_mco)`; `refunded_at` = the once-per-job stamp.
- `autopilot_cycles` (`20260620120100:20-31`): status enum CHECK; `spend_mco/refunded_mco/planned_units >= 0`; named constraint `CONSTRAINT autopilot_cycles_refund_le_spend CHECK (refunded_mco <= spend_mco)` — "refund can NEVER exceed what was committed (defense-in-depth vs a negative-refund mint)".
- `autopilot_video_refunds` (`20260624140000:25`): `amount int NOT NULL CHECK (amount > 0 AND amount <= 100)` — a hard anti-mint ceiling mirrored by an early in-fn guard (`:68-69`).
- Input guards RAISE with `USING errcode = '22023'` (invalid param) / `'P0002'` (not found) / `ERRCODE = '42501'` (privilege).

### 1f. Tenant guards
- Begin: tenant-scoped load — `WHERE id = p_plan_id AND user_id = p_user_id; IF NOT FOUND THEN RAISE ... 'P0002'` ("cross-tenant attempt → not found", `20260620120200:51-58`).
- Schema-level: **composite tenant-scoped FK** `FOREIGN KEY (plan_id, user_id) REFERENCES autopilot_plans (id, user_id)` + `UNIQUE (id, user_id)` anchor for downstream composite FKs (`20260620120100:33-37,55-69`) — "a cycle can never point at another tenant's plan".
- Finalize: uid comes from the row (RETURNING), never from the caller (1c).

## 4. RLS pattern for user-visible ledger tables (the canon to copy)
From `vision_jobs` (`20260615160000:35-42`), `autopilot_cycles` (`20260620120100:39-45`), `autopilot_video_refunds` (`20260624140000:29-37`):
1. `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`
2. Exactly ONE permissive policy: `FOR SELECT USING (auth.uid() = user_id)`.
3. **NO INSERT/UPDATE policy for authenticated → default-deny**; the ONLY writer is service-role (bypasses RLS) / SECURITY DEFINER RPCs. Rationale: "a tenant can never forge nor mutate a job (...cannot fabricate a 'done' job... nor zero its own charge)" (`20260615160000:11-13`).

6. Indexes: `(user_id, state)`-style + retention/audit indexes.
7. If clients CAN update own rows on a table with server-owned money columns → SECURITY INVOKER column-guard trigger keyed on `current_user IN ('authenticated','anon')` (`20260701010000:26-47`, sweep pattern `20260701020000:21-76`). REVOKE UPDATE(col) is a no-op under table grants.

### 2.3 New RPCs (service-role-only, SECURITY DEFINER, `SET search_path = ''`, fully-qualified refs — 20260603210500:10-14 de-facto rule)

1. **`begin_space_generation(p_owner_id, p_space_id, p_node_id, p_node_run_id, p_model_key, p_output_type, p_amount, p_context)`** — INSERT `generations` row `status='running'`, `mco_charged=p_amount` with `ON CONFLICT (node_run_id) DO NOTHING` + `GET DIAGNOSTICS ROW_COUNT`; if 0 rows → return `{ok:false, reason:'duplicate'}` (idempotent, zero second debit — FMEA-SPACES-002 08:47); else `PERFORM public.deduct_mco_coins(p_owner_id, p_amount::numeric, 'spaces.node.run', p_context)` in the same tx (rollback on RAISE — no orphan row). Advisory lock `pg_advisory_xact_lock(hashtext(owner_id::text))` only if the daily-cap aggregate is checked inside the RPC (pattern 20260620120200:48-49); if the cap stays in the edge fn (as live canvas-execute does at index.ts:176-217), the lock is optional — **OPEN** which side owns the cap check.
2. **`finalize_space_generation(p_node_run_id or p_generation_id, p_status, p_refund, p_asset_id, p_usd_cost, p_latency_ms)`** — guarded claim `UPDATE … WHERE status IN ('pending','running') RETURNING owner_id` (first finalizer wins — 20260615160000:75-93); require terminal status (`done|error`); clamp refund `GREATEST(0, LEAST(p_refund, mco_charged))`; credit via `PERFORM public.add_mco_coins(v_uid, refund)` + symmetric `mcoin_transactions` row (D7); uid always from the claimed row, never from the caller (tenant safety — patterns reader 1c). Bring its own refund bound: nothing downstream catches an oversized credit (`add_mco_coins` has no ceiling/tenant guard — 20260505100000:11-38).
