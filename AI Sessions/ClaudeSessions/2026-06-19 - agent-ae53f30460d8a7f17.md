> 217	  let below = 0, n = 0; const adxs = [];

> 240	  const adx = adxs.length ? mean(adxs) : 0;

> 249	  return 'mixed';

> 252	// ---------- walk-forward: janelas OOS; regime ex-ante (janela anterior) escolhe a estratégia ----------

> 260	  while (start + test <= candles.length) {

> 262	    const reg = regimeWindow3(ind, a - test, a);          // regime da janela ANTERIOR (ex-ante)

```

  ↓
exchange.js miniTickerStream() / bookStream() / userData()
  ↓
app-em.js startMiniTickerMonitor()
  ↓ (para CADA market tick)
beholder.updateMemory(symbol, 'MINI_TICKER', null, converted)
  ↓ (MEMORY atualizada; trava LOCK_MEMORY)
beholder.BRAIN_INDEX (índice por chave de reação)
  ↓ (acha automações cujas `indexes` matcham o tick)
findAutomations('BTCUSDT:MINI_TICKER') → [id2, id3, ...]
  ↓ (evalua condition de CADA automação em paralelo, sem garantia de ordem)
automação.conditions → evaluator (ex.: "MEMORY['BTCUSDT:RSI_14'].current < 30 && ...")
  ↓ (se dispara)
execAction → calcPrice, calcQty, assertWithinRisk
  ↓
exchange.buy() / exchange.sell() / exchange.oco()
  ↓ (volta executionReport ou erro)
app-em.updateMemory('BTCUSDT:TREND_QTY', qty, false) [async, fire-and-forget]
  ↓
WebSocket broadcast ({ notification: {...} }) → UI
```

**Onde fica a latência:**
1. **Rede WebSocket**: mini-ticker da Binance a cada 1000ms (ou 500ms em bulk), depois 1ms+ de reconexão por símbolo
2. **Beholder.updateMemory**: O(número de automações) no worst-case — se 100 automações com wildcard, CADA tick da Binance re-avalia as 100. **MAS** há cache por índice (BRAIN_INDEX), então na prática é O(automações ativas para esse símbolo).
3. **Cálculo de ordem** (calcPrice, calcQty): ~0-5ms, mostly sync
4. **REST placeOrder**: Binance responde em 10-100ms típico (depende do datacenter)
5. **reconhecimento do fill**: Binance envia `executionReport` via userData stream (10-30ms depois do REST response, **não garantido**)
6. **OCO reconciliation delay**: hardcoded em `OCO_RECONCILE_DELAY_MS = 4000` (4s) para wait antes de fazer REST check de status
7. **Broadcast WebSocket**: negligível (<1ms)

**Total hot path (decisão até REST placeOrder)**: ~15-35ms no melhor caso; 100-200ms no pior (se a conexão está "fria").

- **Conexão única**: 1 conexão WebSocket pode ligar múltiplas streams; a Binance limite é ~100 subs por ws ou ~40 conexões por IP (undocumented, mas Binance quebra acima disso).

- **4→30 símbolos**: +26 CANDLES (1h ou 15m, não 1m cada) = ~30 streams. **Ainda OK para 1 conexão.**

- **Key API**: `ANTHROPIC_API_KEY` ou `OPENROUTER_API_KEY` (obrigatória, exceto em --check)

### (b) Viabilidade e Custo de Expandir Universo de Símbolos

**4→15 símbolos (+11 alts):**
- **Viável**: sim, sem problema
- **Custo**: +500KB memória, +10 streams WebSocket, +0-30 weight/min REST
- **Risco**: negligível; ator-limitante é **sintonização de parâmetros** (quantas alts você vai farmar eficientemente?)

**15→30 símbolos (+15):**
- **Viável**: sim, mas demanda atenção
- **Custo**: +800MB+ heap, latência beholder.updateMemory sobe a 50-100ms picos, ~30 streams
- **Risco**: **OPERACIONAL** — 30 símbolos com a mesma RSI/SMA/regime não faz sentido (cada alt tem microestrutura distinta). Modelar regimes por símbolo é arquitetura pesada (3 classificadores em vez de 1).

**Recomendação**: manter **universo core ~10-15 símbolos** (4 trend + 4-8 farm) bem calibrados. Se expandir além, usar **múltiplas estratégias por cluster** (alts voláteis vs. estáveis).

### (c) Caminho de Baixa Latência Atual e Inserção do Scanner

**Hot path hoje (decisão até REST):**
- Binance tick (miniTicker) → app-em.updateMemory → beholder (O(n automações ativas)) → calcPrice/Qty → exchange.buy → **~15-100ms**
- **Gargalo**: se 50+ automações wildcard, updateMemory fica O(50) avaliações = 30-50ms por tick. Mitigado por BRAIN_INDEX.

**Onde plugar o "scanner cross-símbolo de baixa latência":**
1. **OPÇÃO 1 (REATIVA)** — `ScannerJob` que dispara a cada tick do MINI_TICKER:
   - Lê MEMORY de todos os símbolos (batch: 1ms)
   - Calcula oportunidades de correlação/spread (ex.: BTC up 2%, ETH up 1% → relative strength buy ETH)
   - SEM colocar ordens (só sinaliza ao agente via `tradeux_notify_owner`)
   - **Risco**: +10-20ms por tick se rodar a cada miniTicker; usar `throttle(500ms)` ou agenda 1× por 5s

2. **OPÇÃO 2 (AGENDADO, recomendado)** — `OpportunityScannerJob` que roda a cada 30-60s:
   - Menos contention com hot path
   - Calcula correlações, volatility clusters, regime changes across symbols
   - Agente lê o resultado e sugere ações
   - **Custo**: zero impacto no latency de beholder, 0ms adicionado ao hot path
   - **Implementação**: padrão `regimeJob`/`funnelJob` em `backend/src/jobs/`

**Inserção sem poluir hot path:**
- Criar `opportunityScannerJob.js` separado (não no `updateMemory` crítico)
- Usar `LOCK_SCANNER` (analógico ao `LOCK_MEMORY`, evita leitura durante refresh)
- Publicar resultado via broadcast (`sendMessage({ opportunities: [...] })`) para UI + agente
- Agente lê via `tradeux_get_scanner_state()` a cada ciclo (não é urgente)
