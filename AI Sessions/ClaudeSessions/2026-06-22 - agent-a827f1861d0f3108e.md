## Security Review: `publish-wordpress/index.ts` diff

### FINDING 1 — Server-side shared secret exfiltrated to user-controlled hosts

- **File:line:** `supabase/functions/publish-wordpress/index.ts:85-87` (header construction), exfiltrated at the fetch calls `:99-101`, `:107-111`, `:133-137`
- **Severity:** HIGH
- **Category:** Sensitive data exposure / secret mishandling
- **Confidence:** 9/10

**Description**

The diff introduces `WP_PUBLISH_SECRET`, a single server-side environment secret shared across the entire deployment (all tenants). It is attached as the `X-MCORCH-Publish` header to every `fetch()` targeting `apiBase`. But `apiBase` is derived from `wpSiteUrl`, which resolves from `decrypted_user_api_keys.wp_site_url` — a **per-user-controlled** value (line 57). There is no allowlist, host validation, scheme check, or redirect guard on `wpSiteUrl`. As a result, the function sends a global shared secret to whatever host the user (or anyone who can set a user's WP config) puts in `wp_site_url`.

This is a classic credential-leak-to-attacker-host pattern. The secret is global, not per-tenant, so a single malicious or curious tenant can capture it and then use it against the legitimate target.

**Exploit Scenario**

1. Tenant A (any authenticated user) sets their WordPress config `wp_site_url` to `https://attacker.example.com` via the normal Settings → WordPress flow (writes to `user_api_keys`).
2. Tenant A invokes `publish-wordpress` (directly, or via the orchestration pipeline).
3. The function builds `wpAuthHeaders` including `X-MCORCH-Publish: <WP_PUBLISH_SECRET>` and POSTs to `https://attacker.example.com/wp-json/wp/v2/posts` (and the tag-search/create endpoints).
4. The attacker's server logs the inbound request and reads the global `X-MCORCH-Publish` value.
5. The attacker now possesses the shared secret that the Cloudflare WAF "Skip" rule trusts. They can replay it to `https://<legit-wp-host>/wp-json/*` to bypass the Cloudflare managed challenge on the real WordPress origin — the exact protection the secret exists to gate. Combined with any other WP-layer weakness reachable on `/wp-json/*` (e.g. user enumeration via `/wp-json/wp/v2/users` if the Skip rule is broader than intended, brute-forcing Basic Auth without the CF challenge slowing it), this defeats the WAF hardening for the legitimate site.

The code comment at line 82-84 explicitly relies on the secret to keep `/wp-json/*` from being "opened wide to the public internet." Leaking it to any tenant-chosen host collapses that assumption.

Note the existing `Authorization: Basic` header has the same per-user-host exposure, but that credential is the *same user's own* WP password (self-exfiltration, not a cross-tenant/global secret) — so the **newly introduced** secret is materially worse: one tenant's action burns a secret that protects *every* tenant's WordPress origin.

**Fix**

Do not attach the global secret to requests bound for arbitrary user-supplied hosts. Options, in order of robustness:

1. Only attach `X-MCORCH-Publish` when `apiBase`'s host matches an allowlist of MCORCH-operated WordPress origins (e.g. compare against `WP_SITE_URL` env / a configured hostname set). For genuinely self-hosted per-user WP sites the CF-Skip secret is meaningless anyway (it's *our* Cloudflare rule), so it should never be sent off-platform:
   ```ts
   const allowedHost = new URL(Deno.env.get("WP_SITE_URL") ?? "").host;
   const targetHost = new URL(apiBase).host;
   if (wpPublishSecret && targetHost === allowedHost) {
     wpAuthHeaders["X-MCORCH-Publish"] = wpPublishSecret;
   }
   ```
2. Validate `wpSiteUrl` scheme is `https:` and the host is on an allowlist before any fetch.
3. Make the secret per-tenant rather than a single global value, so a leak is contained to the leaking tenant.
