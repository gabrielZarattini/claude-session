## Analysis

I read all three files. The candidate claims the OAuth `state` nonce is not tracked single-use, allowing state replay within the 10-minute window.

**Verification of the mechanism (accurate):**
- `tiktok-login-init` mints `{ intent: "login", nonce: crypto.randomUUID(), ts: Date.now() }`, HMAC-signs it (index.ts:50-53).
- `verifyState` (oauth-state.ts:43-61) enforces only HMAC integrity + a 10-min `ts` window. The `nonce` is never persisted or consumed. So yes — the same signed state string will pass `verifyState` repeatedly for 10 minutes. That part of the description is technically correct.

**But there is no concrete exploitable impact:**

1. **The callback requires a valid TikTok `code`, not just a state.** `tiktok-login-callback` (lines 41, 70-86) rejects with `exchange_failed` unless a live authorization `code` exchanges successfully at TikTok. The TikTok auth code is single-use at the provider. Replaying a captured `(state, code)` pair fails at the token exchange (code already consumed) → no identity, no login code minted. Replaying `state` alone does nothing.

2. **The state has no user/tenant binding in the login flow.** Unlike the connect flow (which the `oauth-state.ts` header describes, binding `userId`), the login state deliberately carries no `userId` — "a login has none yet" (index.ts:48). So there is no privilege embedded in the state to replay. Single-use tracking would grant no additional protection.

3. **`init` is public (`verify_jwt=false`).** Any attacker can trivially obtain a fresh valid state on demand by calling `init`. Enforcing nonce single-use would not deny an attacker anything they can't already get for free. The "widens the login-CSRF window" argument collapses: the attacker's supply of valid states is already unbounded regardless of nonce tracking.

The candidate itself concedes "Direct impact is bounded because the TikTok authorization code is single-use at TikTok's side." That concession is the whole finding — the anti-replay work is done by TikTok's single-use code, and the state is only a lightweight CSRF/integrity marker for an unauthenticated login. This is a defense-in-depth / hardening observation with no concrete attack path where untrusted input yields a security-relevant outcome (no session forgery, no cross-tenant linking, no auth bypass).

This falls squarely under the excluded "lack-of-hardening" / "theoretical replay without concrete exploit" categories.
