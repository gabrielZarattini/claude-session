### 1. Original login-CSRF is CLOSED — confirmed

Walking the attack: attacker completes OAuth in their browser (secret `binding_A` in their sessionStorage; code `C` minted with `binding_hash = sha256(binding_A)` at `tiktok-login-callback/index.ts:128`), then lures the victim to `/auth/tiktok/callback?code=C`.

The atomic UPDATE filters `.eq('binding_hash', sha256(X))` (`session/index.ts:54,58-66`). The single UPDATE is simultaneously the replay guard and the anti-CSRF gate.

The secret lives only in the initiating browser's sessionStorage and is **never transmitted** — only its SHA-256 hash travels (init body → signed state → code row). Preimage resistance means the committed hash is useless to redeem.

### 2. Binding cannot be bypassed — all four vectors fail

- **(a) Inject binding into victim's request:** No. sessionStorage is origin-scoped + per-tab; the attacker controls only the `?code` URL param. The SPA *reads* binding from sessionStorage and only ever *writes* it in `createTikTokBinding()` on the login-button path (which would generate the victim's own unrelated secret). No cross-origin/URL/cookie route writes sessionStorage.
- **(b) Tamper in transit:** No. `bh` is HMAC-SHA256-signed into the state with server-only `SB_SECRET_KEY` (`oauth-state.ts:34-38`, verify `timingSafeEqual` at `:52`) and re-validated `^[0-9a-f]{64}$` in the callback (`callback:61`) before storage.

- **(d) Store an attacker-chosen `bh` for a code the victim will redeem:** No. The victim can only successfully redeem a code whose `binding_hash = sha256(a secret in the victim's sessionStorage)` — i.e., a flow the *victim* initiated, whose `user_id` the attacker cannot control.
