Exit code = nº de FAILs (4 no cenário acima). Rodando com `HARNESS_JSON_ENGINE=awk` (simulando máquina sem jq/python3/node) o veredito é idêntico, exceto que a validade do JSON vira `WARN NÃO VERIFICÁVEL` em vez de PASS — Lei 1 aplicada ao próprio kit.

## Contratos que os demais arquivos do kit precisam respeitar

1. **`probe_run` devolve 3 para ausência declarada, nunca 0.** Colapsar "ausente" em "pass" é o falso-verde que o kit existe para matar. `4` = parser degradado não resolveu.
2. **`cfg_kind` é o discriminador** entre `""` (não entrevistado → FAIL) e `null` (ausente e declarado → neutro). `cfg` sozinho não distingue os dois.
3. **Resolva caminhos contra `HARNESS_ROOT`, não `repo_root`.** `repo_root` é o toplevel git (pode ser um monorepo acima); `HARNESS_ROOT` é o diretório que possui `.harness/`.
4. **Todo regex lido do config passa por `ere_portable`** antes de chegar ao grep — `\s` é extensão GNU e não existe no grep -E do macOS.
5. **O caller é dono de `HARNESS_PROBE_LOG`** e precisa apagá-lo (o doctor faz via `trap`).
6. **Restrição para quem escrever `.claude/rules/`, `.claude/skills/**/SKILL.md` e `.claude/agents/`:** todo caminho citado entre crases ou em link markdown **tem que existir no disco**, senão a §4 do doctor fica vermelha. Placeholders (`<slug>`), globs (`*`), URLs e caminhos absolutos são ignorados pela varredura — use-os quando o alvo não for um arquivo real.

Nenhum caminho absoluto, nome de produto/stack, comando presumido ou versão de runtime pinada nos dois arquivos (auditado por grep; o único `1.0.0` é o `kit_version` do próprio contrato). `declare -A` foi eliminado em favor de tally por arquivo temporário — bash 3.2 do macOS não tem array associativo, e gate que morre no laptop do revisor é gate que ninguém roda.
