## Verdict: No exploitable vulnerabilities (nothing at confidence ≥7)

The new `sign_upload` branch (`supabase/functions/ingest-external-asset/index.ts:61-80`) is correctly hardened. Details per attack surface:

**Cross-tenant / path control — SAFE.**
- `user.id` (line 64) comes from `userClient.auth.getUser()` (line 51), which verifies the JWT against Supabase. The client has zero control over this segment.
- The only client-influenced input is `body.filename → safe` (line 63). The regex `[^a-zA-Z0-9._-]` strips every path separator: `/` is not in the allowlist, so it is replaced with `_`. Path traversal to escape the `${user.id}/repurpose-masters/` prefix requires a `/`, which cannot survive sanitization. `..` can survive (`.` is allowed), but `..` without a `/` cannot form a new path segment, and Supabase Storage keys are opaque flat strings anyway (no filesystem `..` semantics). No prefix escape possible.
- `slice(-120)` runs on `safe` *before* the prefix is prepended (line 64), so it can never truncate away the `${user.id}/` prefix. The key provably always starts with the verified user's UUID.

**Bucket — SAFE.** `video-studio-assets` is a hardcoded string literal at both the `.from(...)` call (line 70) and the response (line 75). No `body.*` field reaches the bucket selector in this branch.

**Secret leakage — SAFE.** Response returns only `signed.token` + `signed.signedUrl` (lines 77-78), which are a capability scoped to that single owner-namespaced key — the intended upload grant. The `SB_SECRET_KEY` used to construct `admin` (line 67) is never serialized into the response.

**Auth — SAFE.** `sign_upload` is reached only after the `Bearer` check (line 44) and the `getUser()` null-guard (line 52), both of which `return json(401,...)` first. An unauthenticated caller cannot reach line 61.

**Injection / SSRF — SAFE.** No user field reaches a host, protocol, or URL. `createSignedUploadUrl(key)` receives only the sanitized owner-scoped key.

**Client hook (`src/hooks/useVideoRepurpose.ts`) — SAFE.** `uploadToSignedUrl(sign.storage_key, sign.token, file)` (line 32) merely consumes the server-minted grant; the backend is authoritative for the key. Per project doctrine, client-side authz is out of scope and the backend enforces the owner prefix on both the sign and register paths.

**Page (`VideoRepurposePage.tsx`) — SAFE.** Confirmed no `dangerouslySetInnerHTML`, `eval`, `innerHTML`, or `new Function` (grep returned `NO_DANGEROUS_SINKS`).

One defense-in-depth observation (not a vulnerability, and already tracked by the authors' inline note at lines 22-24 → OTD-VR-006): the Fatia-2 worker that later reads `(bucket, key)` from the registered row must itself re-validate the `${user.id}/` prefix at download/sign time. That worker is outside this changeset, so it's not a finding here — just flagging that the comment's forward-note is the correct place that follow-up belongs.

No findings to report.
