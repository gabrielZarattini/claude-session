### 8. **EXISTING DAG RUNNER REFERENCE**

**Files:**
- `/src/hooks/useOrchestrationGraph.ts` (lines 27–103)

**Pattern:**
```typescript
const runPipeline = useCallback(async (topic, platforms, affiliateUrl, publishNow) => {
  const store = useOrchestrationStore.getState();
  store.setRunning(true);
  store.resetNodeStatuses();
  store.updateNodeStatus('trigger-campaign', 'running');
  
  // Call orchestrate-content edge function with full payload
  const { data, error } = await supabase.functions.invoke('orchestrate-content', {
    body: { topic, platforms, affiliate_url: affiliateUrl, wp_status: publishNow ? 'publish' : 'draft' },

  // Parse result steps and update store node statuses
  for (const step of resultSteps) {

      const status = step.status === 'done' ? 'done' : 'error';

    }
  }
}, []);
```

**This is NOT a DAG runner.** It's a **single-call orchestrator** — one function invocation handles the entire pipeline server-side. No node-by-node scheduling or dependency resolution occurs in the frontend.

**Canvas Studio's approach is different:**
- `CanvasEditorPage.handleRunAll()` (line 394) manually:
  1. Filters runnable nodes
  2. Separates nodes into `toRunImmediately` vs. `toRunImmediately` (for video nodes with running parents)
  3. Calls `runSingleNode()` for each, which invokes `canvas-execute` per node
  4. Relies on a reactive effect (line 340) to check parent statuses and unblock queued children

**Diagnostic:** Canvas Studio **does NOT replicate the Orchestration pattern** because it's node-level execution, not orchestration-level. The two systems are fundamentally different architectures. The Canvas approach is **correct for its domain**, but it needs explicit handle routing and proper DAG traversal for pipeline mode.

### **One-paragraph summary of architectural gap:**

Canvas Studio's frontend **lacks explicit handle routing in the graph layer**. Edges are created without port IDs (`sourceHandle` / `targetHandle`), causing downstream nodes to resolve upstream images via fragile edge-list traversal that ignores port topology. The "Run All" and reactive scheduler logic **work for linear pipelines** (single input, single output) but **fail for branching DAGs** (multiple outputs or inputs). Additionally, the video model tier whitelist is **incorrectly set to all 5 models** instead of the Phase 4.2c SOP's `dop-standard-5s`-only restriction. To fix: (1) assign handle IDs when edges are created, (2) validate handle routing in DAG traversal, (3) narrow the tier allowlist, (4) refactor the scheduler into a reusable `useCanvasPipeline` hook with proper topological ordering and async parent-wait logic.
