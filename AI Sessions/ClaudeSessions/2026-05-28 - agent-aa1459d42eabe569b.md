## PORTABILITY ASSESSMENT

### 1. **What Can Be Lifted DIRECTLY**

- **Zustand store structure** (`useOrchestrationStore.ts`): Node/edge state management, status tracking, `updateNodeStatus()` pattern
- **Status sync useEffect** (OrchestrationCanvas.tsx:45–53): Exact same pattern syncs store → ReactFlow
- **Error blocking logic** (runPipeline line 72–81): Upstream error → downstream blocked
- **Handle positioning** (all node files): Left=target, Right=source works for linear chains
- **Reset/animation patterns** (store.resetNodeStatuses, edge.animated flip)

### 2. **What Needs ADAPTATION**

- **Run trigger location:** Orchestrator has Trigger node button; Canvas needs Top-bar integration (already exists at TopBar.tsx:122–144)
- **Status enum labels:** Map Canvas `queued → pending`, `success → done`, `failed → error`
- **DAG traversal:** Visual Orchestrator delegates to backend; Canvas needs **client-side topological sort + parallel Promise.all** (not present in Orchestrator)
- **Output wiring:** Orchestrator does NOT pass outputs; Canvas needs field like `node.data.inputs = { inputNodeId: outputValue }` + consumption logic

### 3. **What Needs WRITTEN FRESH**

- **Topological sort function:** Given nodes + edges, find root nodes, execute in layers, track "all upstreams done"
- **Canvas-specific node executor:** Call canvas-execute edge function per node (Orchestrator calls single backend function)
- **Output-to-input binding:** Traverse edges at execution time; pass `upstream.data.output → downstream.data.inputs[handleId]`
- **Multi-input handle IDs:** If sceneCompose needs `{ imageHandle, styleHandle }`, update node component + edge.sourceHandle/targetHandle
- **Parallel execution wrapper:** Promise.all() for nodes with no dependencies, await before unlocking dependents

### 4. **Critical Risk: Non-Translation Pattern**

**Visual Orchestrator assumes a SINGLE BACKEND EXECUTION CALL** (`orchestrate-content` with `body` containing topic + platforms). The DAG is **logical only** — backend owns the actual parallelism + data flow.

**Canvas Studio requires CLIENT-SIDE DAG execution:**
- Each node runs independently via canvas-execute
- Output of node A becomes input to node B
- Parallel branches (if GenerateImage + CharacterReference have no edge) must run Promise.all()
- Multi-input nodes (sceneCompose aggregating image + character) must wait for ALL upstreams before running

**Risk if not adapted:** Porting Orchestrator's `runPipeline()` directly will:
- Call canvas-execute once per node sequentially (no parallelism)
- Not pass upstream outputs to downstream inputs (nodes run in isolation)
- Block on multi-input nodes waiting for unconnected upstreams

---

**Final summary:** Visual Orchestrator is a **backend-delegated DAG** (status sync + error blocking only). Canvas Studio needs a **client-side DAG runner** with topological discovery, parallel execution, and data flow. Reuse the **state management + sync patterns**; build the **traversal + execution logic** from scratch.
