**(3)** Yes — if and only if `REGIME_INTERVAL != '1h'`. `classifyRegime` computes ADX-14 on whatever interval's candles it gets (`regimeClassifier.js:42`), and ADX magnitude is timeframe-dependent, so a 4h chart at ADX>=25 ('trend') can coincide with the same-wall-clock 1h chart at ADX 22–24.9 ('mixed', the intermediate else-branch at `:73`). Cache keys include the interval, so they never reconcile.

**(4)** Caching exists (`regimeService.js:22-23`, TTL 120s) but it caches *candles*, not the classification, and the key includes the interval — so it cannot make 1h and a non-1h converge. It can only add up-to-120s same-interval skew.

**Verdict: expected-but-confusing, not a bug.** Two distinct mechanisms reproduce cockpit=trend / get_regime(1h)=mixed:
- If `REGIME_INTERVAL` is set to something other than `1h` → genuine two-different-timeframes (expected by design).
- Even at an identical `1h`, there is a real asymmetry worth flagging: **regimeJob classifies WITH hysteresis** (passes `prev=LAST[symbol]`, so exit threshold `trendAdxExit=22`), while **get_regime classifies WITHOUT hysteresis** (`prev=null` default; the controller never forwards `prev`, `regimeService.js:44`). With ADX in [22,25) and a prior 'trend' state, the sticky job stays 'trend' while the stateless endpoint recomputes to 'mixed'. That, plus the 5-min job refresh vs 120s endpoint cache, fully explains the divergence without any defect.

One thing the code's own comments already acknowledge this divergence as intended: `analysisController.js:32-33` notes the panel deliberately exposes "a divergência display×gate." So the design anticipates the snapshot (endpoint) and the gate (job/MEMORY) differing.
