### 5. SECURITY CONSIDERATIONS FOR AIOS-SQL-BRIDGE

#### **A. Access Gate Options**

| Option | Pros | Cons | Recommendation |
|--------|------|------|---|
| **Admin role only** | Strictest; uses existing `has_role(auth.uid(), 'admin')` pattern | AIOS agent likely not admin-user; would need special service account | ⚠️ Consider for Phase 2 |
| **Service-role only** (Edge Function using SUPABASE_SERVICE_ROLE_KEY) | Matches existing RPC caller pattern; AIOS backend calls function with JWT | Requires backend → Edge Function → Supabase chain (no direct agent db call) | ✅ **Recommended** |
| **Per-user RLS** (SELECT with `auth.uid() = user_id`) | User can query own mcoin_transactions | AIOS needs cross-user aggregate (pipeline_runs revenue, user activity summaries) — breaks semantics | ❌ Not suitable |

**Minimum guard:** Function callable only by Edge Function caller with valid JWT (pattern: orchestrate-content, rescue-video).

#### **B. Table/Operation Whitelist**

**Select-only tables (zero mutation risk):**
- `mcoin_transactions` — read ledger
- `pipeline_runs` — read job history (schema: id, user_id, topic, status, steps, mco_cost, started_at, completed_at)
- `profiles` — read user metadata (schema: id, mco_balance, created_at, updated_at)
- `vm_canvas_executions` — read execution records (schema: id, user_id, provider, status, credits_charged, operation_id, webhook_received_at)

**Forbidden:**
- INSERT, UPDATE, DELETE on any table
- SELECT on auth tables, secrets, user_api_keys
- TRUNCATE, DROP, ALTER

#### **C. SQL Injection Prevention**

**Current codebase pattern: Supabase JS SDK uses parametrized queries by default.**
- `.from(table).select(...).eq('column', value)` — SDK escapes all values
- `.rpc('function_name', {...})` — named parameter binding in PostgreSQL

**For aios-sql-bridge:**
- **Option 1 (recommended):** Accept only SELECT queries as **Supabase Filter Objects** (JSON `{column: 'eq', value}`) — transpile to `.select().eq()` chain. Zero raw SQL.
- **Option 2 (safer but limited):** Accept **table + filter + limit** only; build query in function code (hard-coded tables, validated filters).
- **Option 3 (avoid):** Accept raw SQL strings — even with regex whitelist, exponential risk (e.g., time-based blind SQLi via CASE/WHEN in SELECT target list).

**Recommendation:** **Option 1** — Mimic `award-mco-coins` pattern: function receives `{ table: 'mcoin_transactions', filters: [...], limit: 100 }` → validates whitelist → builds Supabase query client-side → returns results. **Zero raw SQL.**
