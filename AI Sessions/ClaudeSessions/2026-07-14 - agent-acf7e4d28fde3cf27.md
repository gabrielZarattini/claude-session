## Security Review — Veo 3.1 engine (uncommitted)

# Vuln 1: SSRF: `supabase/functions/canvas-execute/index.ts:1006`
* **Severity:** Medium
* **Description:** `fetchVeoImage()` is a **new server-side fetch sink for fully caller-controlled URLs** (`body.input_asset_url` and `body.reference_image_urls[]`, straight from the `canvas-execute` request body). It correctly calls `assertPublicHttpUrl(url)` — but that guard only validates the **initial** URL string (https, port 443, non-private literal, DNS-resolve check). The subsequent `await fetch(url)` uses Deno's default `redirect: "follow"`, so the guard's decision is discarded the moment the remote host answers with a `3xx`. The final request the isolate actually issues is never re-validated against the private-address policy — which is precisely the "internal-network primitive" the shared helper's own header comment claims to kill.
* **Exploit Scenario:** An authenticated tenant POSTs to `canvas-execute` with `node_type: "image_to_video"`, `provider: "google"`, `model: "veo-3.1-lite"`, a `node_run_id` (to enter the ledger branch), and `reference_image_urls: ["https://attacker.tld/r"]`. The guard passes (public host, https, port 443). `attacker.tld/r` responds `302 Location: http://169.254.169.254/latest/meta-data/` (or any internal `http://10.x`/`127.0.0.1:PORT` endpoint). Deno follows the redirect and issues the GET from inside the Supabase Edge isolate. The `references_used` counter in the 202 response acts as a boolean oracle (host reachable + served `image/*`), giving a blind internal-network probe primitive. Response bytes are not returned to the caller, and each probe costs the attacker the ledger debit (89–712 mco), so this is a blind/limited-rate primitive rather than a data-read — but the guard is bypassed, and the redirect target is unbounded (including plain `http://` and non-443 ports, both of which the guard explicitly rejects on the first hop).
* **Recommendation:** Pin the fetch to a single validated hop:
  ```ts
  const validated = await assertPublicHttpUrl(url);
  const r = await fetch(validated.toString(), { redirect: "manual" });
  // 3xx → follow at most N times, re-running assertPublicHttpUrl on each Location
  ```
  Or, cheaper and stronger for this use case: since the references are always MCORCH assets, restrict the host to the Supabase storage origin (`new URL(supabaseUrl).host`) before fetching. Note the same redirect gap exists in `publish-social` (pre-existing, out of scope) — fixing it centrally inside `assertPublicHttpUrl` (return a `fetchSafe()` wrapper) would close both.

## Controls verified — no other exploitable issue found

I traced every sink flagged in the objective and found the following controls genuinely in place:

**(b) Cross-tenant / FMEA-011 — clean.**
- `veo-poll` resolves the row with `admin.from("generations")...eq("owner_id", user.id)` *before* any other predicate; a foreign `generation_id`/`node_run_id` returns 404 without confirming existence. Every subsequent value (`node_run_id`, `operation_id`, `storage_key`, `mco_charged`, `result.provider_key_id`) is read **from that owner-scoped row**, never from the request body.
- Storage write key is `${user.id}/veo/${row.id}.mp4` — the prefix comes from the JWT, the suffix from the owner-scoped row. No caller string reaches the path; `upsert: true` can only overwrite the caller's own object. Matches the `canvas-assets` owner-prefix policy.
- BYOK: `resolveProviderKey(admin, user.id, "google", result.provider_key_id)` — the helper re-validates the key id with `.eq("user_id", userId)`, so even a forged `provider_key_id` cannot select another tenant's key (and here it isn't even client-supplied — it's server-written into `result`).

**(c) Money — clean.** `veoCost()` is a server-side catalog function; `duration` is `Number.isInteger`-checked and clamped to 4–8, `resolution`/`aspect_ratio` are coerced to a closed set, and an unpriced combination 422s *pre-debit*. `effectiveCost` (= `videoCost`) is what `begin_space_generation` debits — the client's `coinCost`/`dynamicCost` are display-only and never reach the RPC. Refunds are single-shot by construction: `finalize_space_generation` only transitions from `pending|running` and clamps `refund ≤ mco_charged`; the two refund callers (`refundNow` on submit failure, `finalizeError` on poll failure) both pass the row's own charge, and the poll returns early on an already-terminal row. Replays with the same `node_run_id` hit `ON CONFLICT DO NOTHING` → `credits_charged: 0`, no second debit, no re-submit. The legacy (non-ledger) branch still rejects `veo-*` via `ALLOWED_VIDEO_MODELS`, so the cheap `|| 10` legacy cost path cannot be used to buy a Veo render.

**(d)/(e) Key leakage — clean.** `keys.gemini` is used only as an `x-goog-api-key` header, server-side. What reaches the client / the owner-readable `result` jsonb is `gemini_label`, `gemini_key_id` (a uuid of the caller's own `user_provider_keys` row) and `gemini_source` — the `keyTelemetry` allowlist, never the secret. The provider error body is echoed into `message`/`result.error`, but the key travels in a header (not the URL or body), so Google's error text cannot echo it. `infra_health_logs` is admin-only-SELECT since migration `20260701040000`, so the `provider_key_id`/`generation_id` pulses are not cross-tenant readable.

**(f) `operation_id` → poll URL — clean.** `generations` has RLS enabled with **SELECT-own only and no INSERT/UPDATE policy** for `authenticated` (verified across all migrations), so `operation_id` and `result` are exclusively service-role-written. The value comes from Google's `predictLongRunning` response `name`, and it is interpolated **after** a fixed `/v1beta/` path segment, so it cannot alter the authority component (no host takeover, no key-header redirection). The `result.engine !== "veo"` gate additionally prevents a Higgsfield-originated `operation_id` from being fed to the Google poll URL. `videoUri` (line 192) is likewise provider-supplied, not caller-supplied.

**Non-security note (worth knowing before ship):** `image_to_video` is **not** in `LEDGER_SYNC_NODE_TYPES` (`src/hooks/useCanvasStudio.ts:221`), so `useCanvasExecute` never attaches a `node_run_id` for it. The `ImageToVideoInspector` Veo submit therefore lands in the **legacy** branch of `canvas-execute`, which 422s (`Tier indisponível`) on any model outside `ALLOWED_VIDEO_MODELS`. The new Veo branch is currently reachable only by a direct API call that includes `node_run_id` — i.e. the feature is dead from the UI until that set includes `image_to_video`.
