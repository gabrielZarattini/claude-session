**No high-confidence security vulnerabilities were newly introduced by these changes.**

I reviewed all four work-streams (PAT issuance UI, Plugin Zip, ops scripts, cost caps) against the specified categories — input validation/injection, authn/authz, crypto/secrets, code execution, data exposure — and found nothing meeting the ≥0.7 confidence bar for actual exploitability.

Key verifications that ruled out the candidate vectors flagged in the review scope:

- **No PostgREST injection.** The `sub` interpolated into the new service-role REST queries (`resolvePlanTier` and `platformRunsToday` in `packages/vision-mcp-core/src/tools/deepsearch-run.ts:144-180`) is never attacker-controlled. It is sourced exclusively from `currentSub()` → `AsyncLocalStorage` → a verified identity (`server.ts:386`): either an ES256-JWKS-verified JWT `sub` (trimmed, non-empty-checked in `auth/identity.ts:70-75`) or the `user_id` DB column from a PAT row lookup (`auth/pat.ts:55`). Both new queries also wrap it in `encodeURIComponent`. The same pattern is already used by the pre-existing `resolveProviderKey`/`verifyPat` paths.

- **PAT generation uses secure randomness.** `useMcpTokens.ts:63` uses `crypto.getRandomValues` (32 bytes / 256 bits); `scripts/qa/mint-vision-pat.ts:36` uses Node `randomBytes(32)`. SHA-256 hashing (`useMcpTokens.ts:54`, `auth/pat.ts:16`) is correct and byte-identical client↔server↔ops, so only the hash is ever stored.

- **PAT verification cannot be forged or scope-bypassed.** Server-side verify is fail-closed, filters `revoked_at IS NULL` at the DB and expiry in-process, and derives both `sub` and `scopes` solely from the row. Per-tool `requireScope` (`server.ts:61`) gates each tool before any cost/effect, and the migration's `scopes_allowed` CHECK allowlists the closed vocabulary.

- **RLS prevents cross-tenant token writes.** The client `.insert` binds `user_id: user!.id`, and the `mcp_tokens_insert_own` policy enforces `user_id = auth.uid()` WITH CHECK (migration `20260615180000_vision_mcp_access_tokens.sql:38-39`), so a spoofed `user_id` is rejected DB-side. SELECT/UPDATE are equally `auth.uid()`-scoped; there is no DELETE policy.

- **No secret exposure.** Plaintext PATs are revealed once and never persisted; `.mcp.json` (both root and the plugin bundle) and the built zip use `${VISION_MCP_PAT}` env expansion with no literal secret. The new `validation_failed` payload (`server.ts:298-301`) exposes only static `field` values and hardcoded numeric-bound PT-BR messages — no sensitive data.

One non-security observation for completeness (not a vulnerability, and within the explicit DoS/rate-limit exclusion): the daily-cap check fails *open* on a transient count error (`deepsearch-run.ts:425-427`), which the code comments correctly characterize as a cost/abuse guard rather than an authorization gate — balance enforcement (HTTP 402) and per-job refund accounting remain authoritative regardless.
