## Threat-class-by-threat-class analysis

### 1. Privilege / authorization on the money-moving RPCs — SOUND

Both RPCs are SECURITY DEFINER (bypass RLS), so their EXECUTE grants are the entire perimeter against untrusted clients. Both are correctly locked:

- **`begin_autopilot_cycle`** (`20260620120200_begin_autopilot_cycle.sql:107-108`):
  ```
  REVOKE ALL ON FUNCTION public.begin_autopilot_cycle(uuid, uuid, int, int) FROM PUBLIC, anon, authenticated;
  GRANT EXECUTE ON FUNCTION public.begin_autopilot_cycle(uuid, uuid, int, int) TO service_role;
  ```
- **`finalize_autopilot_cycle`** (`20260620120300_finalize_autopilot_cycle.sql:69-70`): identical pattern, `(uuid, int, text)` signature.

An authenticated/anon PostgREST client cannot invoke either. The signature in the REVOKE/GRANT matches the `CREATE OR REPLACE` signature exactly (including the new defaulted args `p_planned_units` / `p_status`), so the grant lands on the right overload — no accidentally-ungated variant. I confirmed there is no blanket `GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA public`, no `ALTER DEFAULT PRIVILEGES`, and no later migration re-granting these two functions — the REVOKE/GRANT pair is the only authority. This is the exact lockdown the team applied to `award_mco_coins` / `add_user_score` / `finalize_vision_job`.

### 2. Cross-tenant debit / credit / read — SOUND

- **`begin_autopilot_cycle` plan load is tenant-scoped** (`...120200:52-58`): `WHERE id = p_plan_id AND user_id = p_user_id` + `IF NOT FOUND THEN RAISE`. A cross-tenant `p_plan_id` cannot leak another tenant's caps; it aborts. Because the function is service-role-only and the caller (autopilot-run) resolves `p_user_id` from the server-trusted plan row (not the request body, per header lines 15-16), there is no untrusted path to forge a mismatched `(p_plan_id, p_user_id)` pair anyway.
- **Balance read, daily-cap sum, cycle INSERT, and the `deduct_mco_coins` call all key on the same `p_user_id`** (`...120200:67, 79, 91-92, 98`). No path debits or reads a different tenant.
- **`finalize_autopilot_cycle`** derives `v_uid` from the claimed row (`...120300:48`) and credits that same `v_uid` (`:58`). It takes no `p_user_id`, so there is no caller-supplied tenant to spoof; and since it's service-role-only, a tenant can't reach it to finalize someone else's cycle.
- **Tenant-scoped composite FKs** enforce integrity at the schema layer: `autopilot_cycles(plan_id, user_id) → autopilot_plans(id, user_id)` (`...120100:35-36`) and `creative_metrics(cycle_id, user_id) → autopilot_cycles(id, user_id)` (`...120100:65-67`), each anchored by the matching `UNIQUE(id, user_id)` (`...120000:40`, `...120100:33`). A cycle can never point at another tenant's plan. FKs are integrity-only (not a read vector), and reads on all three tables are gated by `FOR SELECT USING (auth.uid() = user_id)`.

### 3. Mint / drain via the RPCs — SOUND

- **Negative-amount mint is blocked at three layers.** `begin_autopilot_cycle` rejects `p_projected_mco <= 0` (`...120200:43-46`); `finalize_autopilot_cycle` rejects `p_actual_mco < 0` (`...120300:32-34`); and both ultimately route money through `deduct_mco_coins` (positive-only, `secure_ledger_rpcs.sql:45`) and `add_mco_coins` (positive-only, `...:58` "Amount must be positive"). There is no negative-deduct path.
- **Refund cannot exceed spend (no refund-mint / double-spend).** Refund is `GREATEST(0, spend_mco - p_actual_mco)` (`...120300:44, 54`), additionally enforced by table CHECK `refunded_mco <= spend_mco` (`...120100:31`). If `p_actual_mco` overshoots `spend_mco`, refund clamps to 0. The credited `v_refund` can never exceed what `begin` pre-debited.
- **Refund replay / idempotency.** The claim is `UPDATE ... WHERE id = p_cycle_id AND status = 'running' RETURNING user_id` (`...120300:46-48`). A second call finds no `running` row → `v_uid IS NULL` → `RETURN {finalized:false}` no-op (`:50-51`), exactly mirroring `finalize_vision_job`'s claim-once guard. The status transition out of `'running'` and the `add_mco_coins` credit commit in one transaction, so there is no money-without-guard window.
- **TOCTOU on the daily cap.** `pg_advisory_xact_lock(hashtext(p_user_id::text))` is taken at `...120200:49` — *before* the plan load, balance read, daily-cap sum, cycle INSERT, and pre-debit (lines 52-99). Concurrent `begin` calls for the same tenant serialize, so two parallel cycles cannot both slip under the daily cap. The pre-debit additionally re-checks `mco_balance >= amount` under `FOR UPDATE` inside `deduct_mco_coins`, and a failure rolls back the cycle INSERT in the same transaction (no orphan debited cycle).

### 4. SQL injection — NONE (confirmed)

No dynamic SQL. There is no `EXECUTE`/`format()`/string-concatenation anywhere in the four files. All values flow as bound plpgsql variables. The jsonb context built in `begin`/`finalize` (`...120200:99`, `...120300:60-61`) uses `jsonb_build_object` with parameterized values.

### 5. RLS / search_path hardening — SOUND

- Both tables `ENABLE ROW LEVEL SECURITY` (`...120000:43`, `...120100:39`).
- `autopilot_plans`: SELECT/INSERT/UPDATE all gated `auth.uid() = user_id` (`...120000:45-50`), plus `RESTRICTIVE FOR DELETE USING (false)` (`:53-54`) — clients can never delete, even if a future permissive policy is added.

### 6. The composite FK ALTER on `creative_metrics` — no integrity bypass
