### FINDING 1 — HIGH — Cross-tenant private-object read via attacker-controlled storage signing in `auto-publish`

**File:** `supabase/functions/auto-publish/index.ts:110-126` (newly introduced FR-CP-003 block)

**Category:** Broken access control / IDOR — cross-tenant data exfiltration (FMEA-011 class)

**Description:**
The new block reads `post.metadata.reshape.content.{video_bucket, video_key, image_bucket, image_key}` and signs them with the **service-role** Storage client (which bypasses Storage RLS):

```ts
const signKey = async (bucket, key) => {
  ...
  const { data: signed } = await adminClient.storage.from(bucket).createSignedUrl(key, 21600);
  return signed?.signedUrl ?? null;
};
const vu = await signKey(c.video_bucket, c.video_key);   // bucket+key fully from post.metadata
```

The `bucket` and `key` are taken **verbatim** from `post.metadata`, with no ownership/path validation. Crucially, `scheduled_posts` RLS lets any authenticated user freely INSERT/UPDATE their **own** rows including the free-form `metadata` jsonb (no column restriction):

```sql
-- 20260402014040_...sql:172  metadata JSONB DEFAULT '{}'
-- :298  CREATE POLICY "Users can create posts" ... FOR INSERT WITH CHECK (auth.uid() = user_id);
-- :299  CREATE POLICY "Users can update own posts" ... FOR UPDATE USING (auth.uid() = user_id);
```

auto-publish picks up any row with `status='queued'` (which the user sets) and signs whatever bucket/key the attacker placed in metadata. The resulting 6h signed URL is passed as `content.video_url`/`content.image_url` into `publish-social`, which publishes the bytes to the attacker's own connected social account (IG REELS, FB, YouTube, Pinterest — confirmed at `publish-social/index.ts:159,167-168,247,374,463`). The bytes of any tenant's private object are thereby exfiltrated.

The private buckets reachable include `generated-images`, `generated-videos` (read-public but service can read all), `video-studio-assets`, `canvas-assets`, `vision-artifacts`, etc. Their RLS isolates objects by `(storage.foldername(name))[1] = auth.uid()`, but the service-role client ignores all of that.

**Why this is NEW:** Pre-patch (`git show HEAD:...auto-publish`), the bucket came from `content_library.metadata.storage_bucket` and the key from `content_library.media_url`, both resolved from a **content_library row filtered by the post's `campaign_id`** — i.e., server-derived rows, not raw user input. The patch replaces that with bucket+key taken directly from user-writable `scheduled_posts.metadata`.

**Concrete exploit:**
1. Tenant A (attacker) is a normal authenticated user with a connected Instagram/YouTube account.
2. A inserts a row into their own `scheduled_posts`: `{ user_id: A, status:'queued', scheduled_at: now, platform:'instagram', social_account_id: <A's account>, metadata: { reshape: { content: { text:'x', video_bucket:'video-studio-assets', video_key:'<victim_uuid>/<render>.mp4' } } } }`. (A can enumerate/guess victim keys, or target known buckets/paths; victim uid is discoverable.)
3. `auto-publish` cron fires, signs the victim's object with the service key, and publishes the victim's private video/image to A's Instagram — exfiltrating it.

**Fix recommendation:**
Do not sign an arbitrary bucket/key from `scheduled_posts.metadata`. Either:
- Resolve the asset from a server-trusted source keyed to the post owner — e.g., look up the `channel_variants` row by `metadata.reshape.channel_variant_id` AND `user_id = post.user_id`, then sign `asset_bucket`/`asset_key` from that row (the reshaper already writes these rows under the correct `user_id`); or
- At minimum, allowlist the bucket AND enforce that the object path's owner segment equals `post.user_id` (e.g., `key.startsWith(post.user_id + '/')`) before signing, and reject otherwise. Given storage layout `<uid>/<file>`, enforcing the leading-uid match closes the cross-tenant read.
