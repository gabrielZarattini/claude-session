## Security Review — Spaces Publish Variants (uncommitted `main`)

**Verdict: NO high-confidence (≥7) exploitable vulnerabilities introduced by this change.**

The change is a faithful mirror of the sealed `channel_variants` / `publish-channel-variant` pattern. Every tenant hard-bind that makes the reference pattern FMEA-011-safe is present and correct in the new seam. I traced each vector the brief asked me to scrutinize and confirmed it is closed.

### Cross-tenant asset-signing via the new `space_publish_variant_id` branch — SAFE

`auto-publish/index.ts:126-133` resolves the variant with `.eq("id", reshape.space_publish_variant_id).eq("user_id", post.user_id)`.

- `reshape.space_publish_variant_id` is attacker-controllable (a client can insert/update its own `scheduled_posts` row and fully control `metadata.reshape`).
- But `post.user_id` is **server-trusted**: I confirmed `scheduled_posts` INSERT RLS is `WITH CHECK (auth.uid() = user_id)` and UPDATE is `USING (auth.uid() = user_id)` (migration `20260402014040_...:298-299`). A client can only ever create/mutate a row bearing its own `user_id`; `publish-space-asset` (service role) sets `user_id = user.id`.
- Therefore a forged variant id belonging to another tenant fails the `.eq("user_id", post.user_id)` bind → `maybeSingle()` returns nothing → `attachAsset` receives `undefined` → no signing. Confirmed no leak.
- Crucially, the client-controlled `reshape.content` can only inject `text`/`thread` into the published payload; `native.video_url`/`native.image_url` are set **exclusively** by `attachAsset` from the server-resolved row (`auto-publish:115-145`). A metadata-injected `video_url` is ignored — the core FMEA-011 protection holds for the new branch.

### `asset_bucket`/`asset_key` pointing at another tenant's storage object — SAFE

`publish-space-asset:69-71` resolves the source from `creative_assets` with `.eq("id", sourceAssetId).eq("user_id", user.id)` and copies `storage_bucket`/`storage_key` from that owner row (`:92-93`) — never from the client body.

I verified the deeper question of whether a user can forge a `creative_assets` row whose `storage_key` points at another tenant's object (which would then be signed by the service role): **they cannot.** `creative_assets` has **no INSERT/UPDATE policy** for `authenticated`; the sole writer is `register_creative_asset` (SECURITY DEFINER, `REVOKE ... FROM PUBLIC, anon, authenticated` at migration `20260625120000_...:156`), and its `ON CONFLICT` carries a `WHERE creative_assets.user_id = EXCLUDED.user_id` guard against cross-tenant row hijack. So `storage_key` is genuinely server-controlled and owner-bound.

### Upsert onto another tenant's row — SAFE

`publish-space-asset:81-95` upserts with `user_id: user.id` and `onConflict: "user_id,source_asset_id,channel,surface"`. Because `user_id` is a component of the conflict key **and** is set to the authenticated caller, the upsert can only ever target the caller's own row. `source_asset_id` is itself owner-scoped, so the tuple is unreachable for another tenant.

### Idempotency-anchor cross-tenant collision — SAFE (and deliberately hardened)

The `UNIQUE (user_id, source_asset_id, channel, surface)` key is tenant-scoped by construction. The migration comment (`:15-19`) documents that they consciously rejected the ADR's `node_run_id` (a client-supplied canvas node string) precisely because a global unique on it risked a cross-tenant collision → second-insert DoS. Good call; no issue.

### `social_account_id` (a *difference* from the reference) — SAFE

Unlike `publish-channel-variant` (which forces `social_account_id: null`), `publish-space-asset:120` accepts a client-supplied `social_account_id` and it flows through `scheduled_posts` → `auto-publish:160` → `publish-social`. I checked `publish-social:65-72`: the account query is anchored on `.eq("user_id", userId)` (where `userId = post.user_id`, server-trusted) and `social_account_id` is only an *additional* `.eq("id", ...)` filter, never a replacement. A forged another-tenant `social_account_id` fails the `user_id` bind → `404 No active account`. So it cannot cause posting to a victim's connected account. This difference is harmless.

### Platform enum + scheduled_posts insert — SAFE

`platform` is allow-listed against `PLATFORMS` (`publish-space-asset:57`) and the enqueue uses `variant.platform`; RLS on `scheduled_posts` and the service-role insert keep `user_id` bound to the caller. No injection or privilege surface.
