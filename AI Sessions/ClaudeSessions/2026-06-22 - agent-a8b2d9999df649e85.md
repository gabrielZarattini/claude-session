## 3. Riscos cross-cutting entre os 3

- **BACKUP DE VOLUME/DB ANTES DE QUALQUER UM — pré-condição dura para todos.** Os três tocam, ou dependem de, `db_data`/`backend_logs`. O backup só vale se incluir o **`.env` (AES_KEY + JWT_SECRET)** cifrado e for **testado em round-trip de restauração+decifragem** (Fix A ressalva 1+6, Fix B ressalva 4). Sem `.env`, todo dump de chave é lixo, e isto invalida o rollback declarado tanto do Fix A quanto do Fix B.

- **Restart no save de Settings é o fio condutor de risco entre B e C.** `settingsController` faz `process.exit(0)` ~1s pós-save → reinicia o container. Isso afeta: (B) save concorrente na janela do backfill cria **DB-misto** CTR/GCM; (C) o restart pode **truncar a blacklist** e abrir janela de token revogado no boot. **Mitigação cruzada:** durante a janela do Fix B, travar Settings (HALT + bloqueio de save); no Fix C, exigir escrita atômica + load síncrono top-level antes de `app.listen`.

- **Cripto-migração (B) × save de Settings (C) × mask (B-A):** os três tocam o caminho `updateSettings`/`getSettingsDecrypted`. Se forem desenvolvidos em paralelo há risco de conflito no mesmo controller e de regredir as guardas anti-re-hash/re-encrypt (origem do incidente de senha 2026-06-09). **Sequenciar, não paralelizar** esses dois no mesmo controller; cada um passa por gate isolado.

- **Re-seed do floor para OFF é o pior cenário compartilhado A↔B.** Tanto um nuke acidental (A) quanto um boot abortado/restaurado errado (B) podem deixar o backend subir com **floor OFF = trading real liberado** ou com o **botão de pânico inalcançável**. A trava transversal é **`TRADING_HALT_HARD=true` no `.env`** durante qualquer operação destrutiva ou de migração — deve ser política operacional dura nos três.

- **Material de chave no disco:** Fix A acumula dumps com chaves cifradas + Fix B mantém o legado; ambos elevam a superfície de exfiltração se `backups/` não for 0700 + cifrado + com retenção definida. Decidir cifragem/retenção UMA vez, aplica aos dois.
