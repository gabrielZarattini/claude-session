## 1. Sumário honesto

O **landing-factory** é o módulo que transforma uma intenção comercial do tenant ("quero uma página que converta o produto X") em uma **landing page servida, publicada e continuamente auto-otimizada por um loop de CRO (Conversion Rate Optimization)**. A cunha (o wedge que justifica um módulo próprio) é precisamente essa: **não é "gerar um HTML bonito" — isso o Canvas Design já faz — é fechar o laço `gerar → publicar → instrumentar → medir funil → decidir → promover/reverter variante`, com a decisão ancorada em dados comportamentais reais (PostHog), sob governança per-tenant.**

**O que está PROVADO (fonte primária, Lei 1):**

- O substrato de geração de página existe e é soberano: o sidecar Open Design vendorizado (`canvas-design/open-design/`) roda **v0.10.0** (material: `package.json:3` `"version":"0.10.0"`, HEAD `0f5f4c2c`), Apache-2.0, e expõe um export de HTML por HTTP.
- A camada de instrumentação/decisão existe como produto open-source comercial-safe: **PostHog** (core **MIT Expat** exceto a pasta `ee/`; https://raw.githubusercontent.com/PostHog/posthog/master/LICENSE) expõe REST API completa (Query, Experiments, Feature Flags, Heatmaps, Session Recordings) suficiente para um loop de CRO autônomo.
- Toda a espinha de billing (mcoCoins), credenciais per-user (BYOK Vault-cifrado) e um sink de HTML servido (`publishWordpress`) **já existem no repo** e devem ser reusados, não reconstruídos.

**O que é INCERTO / precisa decisão explícita (nunca apresentado como pronto):**

- ⚠️ O "export HTML single-file, self-contained com assets inlinados" que a pesquisa de mercado descreveu é uma feature **v0.14.0/v0.15.0 upstream** — **NÃO existe no v0.10.0 vendorizado**. No código que roda hoje, o export inlina **apenas CSS/JS top-level**; `<img>`, `@font-face`, `@import`, `url()` **ficam como refs externas** (o próprio `inline-assets.ts` chama o bundling completo de "follow-up issue"). Uma landing com imagens **quebraria offline** sem uma camada própria de asset-bundling. → OTD.
- ⚠️ Uma **landing page NÃO é um `creative_asset`** (o spine é índice de blobs criativos: image/video/audio/design/article/template). O sink de HTML servido/interativo/endereçável que já existe é o nó `publishWordpress` (postType `page`); qualquer static-hosting soberano é net-new. → OTD.
- ⚠️ **BYOK PostHog + token de deploy-host NÃO existem em código** (grep `posthog|netlify` em `supabase/`+`src/` = 0). Só `meta_config` existe como precedente BYOK OAuth-style.
- ⚠️ O **gate de decisão do CRO** (baseline, MDE, significância, reverte-se-piora, e o gate humano→autônomo) é lógica do AGENTE — PostHog **não tem auto-revert**. O "95% de precisão antes de autônomo" é requisito MCORCH, **não** conceito PostHog, e **não tem benchmark** (o análogo mais próximo é o threshold Bayesiano de 95% chance-to-win, que é outra grandeza).
- ⚠️ O **alvo de deploy** (self-host+Cloudflare vs Netlify vs Vercel vs CF Pages) tem consequência de licença/ToS decisória e continua **indeciso**.

**Veredito de viabilidade**: o módulo é **construível e comercial-safe**, mas **não pode nascer sobre o export que a pesquisa assumiu** — o contrato real (v0.10.0) é mais pobre. O caminho honesto é: recabear o bridge para a rota HTTP real, decidir o alvo de deploy, e escrever a camada de asset-bundling + o SOP do loop de CRO antes de qualquer código.

### GATE DE SUPERSET vs `canvas-design` — é módulo novo ou emenda?

**Fronteira declarada (Lei 1 — o Open Design base JÁ é do `canvas-design`):**

O substrato Open Design (daemon `open-design`, `design_jobs`/`design_artifact_refs`, `design-bridge.ts`, iframe `design.mcorch.com`, BoK `docs/bok/canvas-design/`) **pertence integralmente ao `canvas-design`**. O landing-factory **NÃO reconstrói nada disso** — ele **consome** o mesmo daemon e o mesmo bridge.

**Veredito**: o landing-factory é **MÓDULO NOVO**, não emenda ao `canvas-design` — porque introduz **superfície que o `canvas-design` não modela e não é superset da sua**:

1. **Loop de CRO / PostHog** (instrumentação + Experiments + Feature Flags + decisão autônoma) — ausente por completo do `canvas-design`.
2. **Publish de PÁGINA servida** com ciclo de vida próprio (endereçável, versionada, com tráfego pago) — o `canvas-design` produz **artefatos criativos**, não páginas publicadas com funil.
3. **BYOK PostHog dual-key + deploy-host token** — credenciais que o `canvas-design` não possui.

**Onde o landing-factory EMENDA o `canvas-design` (contribuições upstream, não forks):**
- O recabeamento do `export` job para a rota HTTP (OTD-LF-001) e o upgrade do sidecar (OTD-LF-002) **beneficiam ambos** → devem ser feitos NO `canvas-design` (dono do bridge), consumidos pelo landing-factory.
- O asset-bundler (OTD-LF-003) pode viver como capacidade compartilhada do trilho de export.
