> 165	    const tickSize = parseFloat(symbol.tickSize);
> 166	    let newPrice, factor;
> 167	
> 168	    // OCO usa preços explícitos (TP em limitPrice, stop em stopPrice), igual aos tipos LIMIT.
> 169	    if (LIMIT_TYPES.includes(orderTemplate.type) || orderTemplate.type === 'OCO') {
> 170	        try {
> 171	            if (!isStopPrice) {
> 172	                if (parseFloat(orderTemplate.limitPrice)) return orderTemplate.limitPrice;
> 173	                newPrice = Function("MEMORY", "return " + getEval(orderTemplate.limitPrice))(MEMORY) * orderTemplate.limitPriceMultiplier;
> 174	            }
> 175	            else {
> 176	                if (parseFloat(orderTemplate.stopPrice)) return orderTemplate.stopPrice;
> 177	                newPrice = Function("MEMORY", "return " + getEval(orderTemplate.stopPrice))(MEMORY) * orderTemplate.stopPriceMultiplier;
> 178	            }
> 179	        }
> 180	        catch (err) {
> 181	            if (isStopPrice)

Validado por leitura do hot-path (`beholder.js`) + reprodução empírica das invariantes (carreguei os módulos puros e repliquei `invertCondition`/`testAutomations`/`evalDecision` verbatim da fonte).

## 1) MUST-FIX #1 (dois detectores desalinhados) — RESOLVIDO

- **`invertCondition` NÃO interfere na igualdade**: confirmado empiricamente. `invertCondition` (beholder.js:138-150) só age em condições que contêm o token `current`. As condições novas (`==='golden'`, `==='death'`, `!=='bear'`) não têm `current` → `condToInvert` é `undefined` → retorna `false`. A `evalCondition` montada é **idêntica** à condição original, sem cláusula `&& previous...` anexada. O double-check sumiu de fato; o job é o único detector de borda.
- **Dispara exatamente 1×/cruzamento, sem repetição intra-hora nem perda**: a transição (`prev!==undefined && above!==prev`) é o único caminho com `executeAutomations=true`. Entre crosses escreve `'none'` com `executeAutomations=false` → `updateMemory` retorna antes de `testAutomations` (beholder.js:863), logo **a escrita 'none' nunca re-dispara**. `smaCross` dropa a última vela (incompleta) → `above` não oscila intra-hora (provado: mutar a última vela para 1e6 não muda `above`).
- **Corrida 'golden'(exec=true) × 'none' do poll seguinte**: inexistente. Polls são serializados pela trava `running` (sem ciclos sobrepostos) e dentro do ciclo é tudo `await` sequencial. A 'none' é passiva. Não há outro writer de `TREND_CROSS`.
- **Golden dispara com id6 INATIVA (hoje)**: inerte. `findAutomations` só devolve quem está no BRAIN, e o BRAIN só indexa `isActive && !schedule` (beholder.js:35,77). Inativa ⇒ `testAutomations` retorna `false`; o sinal fica gravado mas não há ação. Correto.
- **Golden + regime vira bear no MESMO ciclo**: seguro **por ordem de escrita**. No loop, `REGIME` é gravado (linha 95, exec=false) ANTES de `TREND_CROSS` (linha 120, exec=true). Quando a id6 avalia no tick de `TREND_CROSS`, `MEMORY[REGIME]` já é `'bear'` → `==='golden' && bear!=='bear'(=false)` ⇒ **não compra**. Simulei: `golden+bear mesmo ciclo → buy=false`. Esta dependência de ordem é correta mas **frágil/implícita**: se alguém reordenar as duas escritas no loop, o gate passa a usar regime velho por 1 ciclo. (BAIXA — vale um comentário "REGIME deve ser escrito antes de TREND_CROSS".)

- **RESÍDUO (a sua pergunta) — RISCO REAL, não verificável daqui (MÉDIO):** se a v1 do `setup-trend.js` (nunca commitada; era arquivo de working-tree, agora sobrescrito — `git log` não tem histórico dele) **já foi executada** contra o DB testnet persistente, ela deixou na tabela `monitors` um CANDLES `BTCUSDT 1h indexes=SMA_50,SMA_200` que **continua subindo a cada boot** (o diff não tem DELETE nem reconciliação). Se carregarem o esquema velho, recriar (delete+setup) — o script sozinho não conserta.

## 3) Buracos novos do design de sinal

- **1º boot (TREND_CROSS undefined)**: fail-safe. `isChecked = indexes.every(MEMORY[ix]!=null)` (beholder.js:756) → `false` enquanto `TREND_CROSS_1h` não existe ⇒ não dispara. Provado.
- **'none' passivo entre crosses**: id6/id7 ficam `isChecked=true` (string definida) mas condição `false` (`'none'!=='golden'`). E como 'none' é exec=false, nem chega a `testAutomations`. OK.
- **Restart do job (ABOVE reset) — trade-off assimétrico (MÉDIO):** provei que NÃO dispara espúrio (1ª observação pós-restart só registra `ABOVE`, `prev=undefined`). **Porém o reverso: um cruzamento que ocorra DURANTE a janela de restart/redeploy é PERDIDO** (a 1ª leitura adota o estado atual sem comparar). Como ativar a id6/id7 exige redeploy/PATCH e o testnet reseta ~mensal, há janelas reais de restart. Para uma estratégia que dispara raríssimo (golden/death de 50/200 em 1h), **perder o único cross do ciclo é caro**. Mitigação recomendada: ao ativar, no boot reconstruir `ABOVE[symbol]` e comparar com o último estado conhecido persistido (ou logar o `above` inicial e exigir confirmação manual). Hoje, inativa, é inócuo.
- **`smaCross` dropando a última vela desalinha `above`?** Não em relação a si mesmo (consistente vela-fechada↔vela-fechada). **Mas diverge do `regime`**: `classifyRegime` calcula `belowFrac` sobre TODAS as velas (inclui a incompleta — regimeClassifier.js:40,54), enquanto `smaCross` dropa a última. São janelas diferentes do mesmo fetch. É intencional (o cross quer estabilidade intra-hora; o bear-gate tolera a barra parcial) e não causa bug, mas o `signals.aboveSMA200` do payload (close>SMA200, com vela incompleta) e o `sma.above` (SMA50>SMA200, vela fechada) **podem discordar momentaneamente** no painel — são métricas distintas. (BAIXA, só display.)
- **Gap de dados (`r.sma=null` transitório)**: o bloco inteiro é pulado, `ABOVE` intacto; ao voltar, uma transição genuína ainda dispara 1×. Cross "escondido" inteiramente dentro de um gap de 5min seria perdido, mas SMA 50/200 em 1h não faz ida-e-volta em 5min. OK.
- **SELL com `LAST_ORDER_QTY` (BAIXA, ativação):** se o golden for suprimido por bear e depois vier um death, a id7 (`LAST_ORDER_QTY`) chama `calcQty`→ `MEMORY[BTCUSDT:LAST_ORDER]`; sem compra prévia desta automação isso lança "no last order". Além disso `LAST_ORDER` é por símbolo e **compartilhado** com id2/id3 (reversão) — um death pode vender a quantidade do último trade da id3, não da entrada de trend. É o problema de COORDENAÇÃO que o próprio script já sinaliza; só não ative sem resolver sizing/coordenação.

## 4) M5 / M6

- **M6 (return no 409)**: CORRIGIDO. monitorsController.js:90 agora `return res.status(409)...`. Sem o return, o código caía em `insertMonitor` + `res.status(201)` ⇒ `ERR_HTTP_HEADERS_SENT` + monitor duplicado inserido. Fix correto.
- **M5 (REGIME nos indexes ao gatear id2/id3 por `!=='trend'`)**: é passo de ATIVAÇÃO, **ainda não feito** (correto — o setup-trend não toca id2/id3). A recomendação no script (setup-trend.js:112) está certa: incluir `REGIME` nos indexes de **AMBAS** id2/id3, senão fail-open. **Atenção factual:** a id2 **já tem** `BTCUSDT:REGIME` nos indexes (gate `!=='bear'` — HANDOFF), mas a **id3 NÃO tem REGIME nos indexes** (indexes só `BTCUSDT:RSI_14_1m`). Então ao adicionar `&& REGIME!=='trend'` à id3, é obrigatório também adicionar `REGIME` aos indexes da id3 (a id2 já está coberta) — senão a id3 fica com condição que referencia REGIME sem isChecked garantido para essa key e a coordenação falha silenciosamente. A recomendação do script ("AMBAS") cobre isso; só registre que na prática a id2 já está, a id3 está faltando.
- **id6 (BUY) já bota REGIME nos indexes?** SIM — setup-trend.js:105 passa `indexes=${KC},${KR}` (`TREND_CROSS_1h,REGIME`), então a trava `!=='bear'` é fail-safe (isChecked exige REGIME presente). Correto.
