# Security Review: `20260602160000_meta_social_disconnect_rpc.sql` + hook changes

## Verdict: NO high-confidence, newly-introduced vulnerability found.

The change is sound. The two RPCs correctly mirror the established `disconnect_wordpress()` pattern, and the row-id-keyed secret naming (the one structural difference vs. WordPress's user-id keying) is correctly defended by the same double-binding predicate. I walked each numbered concern to ground truth in the schema. Details below.

---

### Concern 1 — Cross-tenant row deletion (`disconnect_social(p_account_id)`): SAFE

The row is selected with `WHERE id = p_account_id AND user_id = v_uid` (= `auth.uid()`). A foreign or non-existent `p_account_id` leaves `v_row_id` NULL → the `IF v_row_id IS NULL THEN RETURN` short-circuits before any DELETE. The subsequent `DELETE ... WHERE id = v_row_id AND user_id = v_uid` is redundantly re-scoped. No cross-tenant deletion, and no information leak: the function returns `void` identically whether the id is foreign, non-existent, or simply not connected — the three cases are indistinguishable to the caller. `disconnect_meta()` takes no id at all (keyed purely on `auth.uid()` over `UNIQUE(user_id)`), so it is even tighter.

### Concern 2 — Cross-tenant Vault secret revocation (the critical one): SAFE

The Vault DELETE is double-bound: `WHERE id = <ref-uuid from caller's own row> AND name = '<prefix>_' || v_row_id::text`, where `v_row_id` is the **caller's own** row id (read from `meta_config_table`/`social_accounts_table WHERE user_id = auth.uid()`).

I traced the full "planted foreign reference" attack the prompt flagged:
1. An attacker can indeed plant an arbitrary UUID into their own token column via the masked view (confirmed: the encrypt trigger `trg_encrypt_*` treats a UUID-shaped value as an already-encrypted ref and leaves it as-is — `20260602140000` lines 252-267 / 291-307). So `v_*_ref` is attacker-controllable.
2. But the secret **name** in the predicate is rebuilt from `v_row_id` — the attacker's own row id. Both base tables declare `id UUID PRIMARY KEY` (verified: `meta_config` line 28, `social_accounts` line 83). So the attacker's own row id can **never** equal a victim's row id (PK uniqueness across the shared table). Since meta/social secret names are keyed by row id, the rebuilt name `meta_config_long_lived_token_<attacker-row-id>` can never collide with a victim's secret name `..._<victim-row-id>`. The `AND name = ...` clause therefore makes the DELETE a guaranteed no-op against any secret the caller doesn't own — even though the `id = ref-uuid` half would match.
3. Independently, the attack is also unreachable on the read side: to plant a victim's UUID the attacker must first *learn* it, but the raw Vault UUID ref is never exposed to any client. The masked views (`20260601000600`) mask token columns to `••••••••••••` and filter `WHERE auth.uid() = user_id`; SELECT on the base tables is REVOKED from `authenticated`; and the `decrypted_*` views are `GRANT SELECT ... TO service_role` only (REVOKE from anon/authenticated). So the attacker controls neither half of the predicate against a victim.

Note the attack against meta/social is *structurally weaker* than WordPress even before the name guard: WordPress shares one secret name per user (`..._<uid>`), whereas meta/social names embed a per-row UUID the attacker cannot know or reproduce for a victim. The name binding holds regardless.

### Concern 3 — One-time cleanup DELETE on `vault.secrets`: SAFE

- (a) **Over-delete of a LIVE secret?** No. The `NOT EXISTS (SELECT 1 FROM <base> WHERE id::text = right(s.name, 36))` guard preserves any secret whose owning row still exists. A live connection's secret is retained.
- (b) **Is `right(name, 36)` always the row UUID?** Yes, for every name the regex matches. The anchored regex `^<prefix>_<8-4-4-4-12>$` forces the name to end in exactly a canonical 36-char UUID with the prefix as a literal head; a canonical UUID is exactly 36 chars, so `right(name, 36)` is exactly that trailing UUID. The prefixes (`meta_config_long_lived_token_`, `meta_config_pages_`, `social_accounts_access_token_`, `social_accounts_refresh_token_`) contain no hex-UUID-shaped suffix that could shift the boundary, and the encrypt triggers only ever produce names of this exact `<prefix>_<NEW.id>` shape.
- (c) **Wrong-owner deletion / name injection?** No injection vector: secret names are server-generated by the triggers as `<static-prefix> || row.id::text` (a UUID) — clients never influence the name. The cleanup only removes secrets matching the four hard-coded prefixes whose row no longer exists; "ownership" is moot because an orphan has no owning row by definition.
- (d) **Coincidental regex match with a non-row suffix?** Would simply be a no-op delete of an orphan (NOT EXISTS is satisfied), which is the acceptable/intended outcome. It cannot delete a live secret because the only way a matched name maps to a surviving row is via the exact `id::text = right(name,36)` equality the guard checks.

Caveat (not a finding): the cleanup is one-time DDL-context DML scoped to the four prefixes; cross-prefix collision is impossible since each prefix is distinct and anchored.

### Concern 4 — SECURITY DEFINER + `SET search_path = ''`: SAFE

All references are schema-qualified: `public.meta_config_table`, `public.social_accounts_table`, `vault.secrets`, `auth.uid()`. Builtins `right()`, `now()`, `gen_random_uuid()` resolve from `pg_catalog`, which is always implicitly first on `search_path` and cannot be shadowed by a user schema. The `~` regex operator and `::uuid`/`::text` casts are catalog operators. No unqualified object reference exists → no search-path hijack surface. Matches the hardening precedent in `20260602140000` and `20260602150000`.

### Concern 5 — SQL injection / dynamic SQL: NONE

No `EXECUTE`, no string-built SQL.
