## (a) INSTAGRAM — como o mp4 é resolvido no servidor

Instagram **não tem API pública** para baixar mídia de posts arbitrários; a Graph API oficial só entrega mídia de contas que você mesmo administra via access token ([developers.facebook.com/docs/instagram-platform/reference/instagram-media](https://developers.facebook.com/docs/instagram-platform/reference/instagram-media/)). Serviços tipo sssinstagram falam com a **private/web API** que o próprio site instagram.com usa internamente. Há três caminhos observados:

**1. GraphQL web (sem cookie, o mais usado por downloaders):**
- Endpoint: `POST https://www.instagram.com/api/graphql` (também aparece como `https://www.instagram.com/graphql/query`)
- Corpo: `variables={"shortcode":"<SHORTCODE>"}` + `doc_id=<id>` + `lsd=<token>`
- Headers obrigatórios: `X-IG-App-ID`, `X-FB-LSD`, `X-ASBD-ID: 129477`, `Content-Type: application/x-www-form-urlencoded`
- Fonte com exemplo funcional (código real): [github.com/ahmedrangel/instagram-media-scraper](https://github.com/ahmedrangel/instagram-media-scraper). ⚠️ O `doc_id` desse repo (`10015901848480474`) e os do ScrapFly (post details `8845758582119845`; profile posts `9310670392322965`) **rotacionam a cada 2–4 semanas como medida anti-scraping** — são valores datados, não constantes ([scrapfly.io/blog/posts/how-to-scrape-instagram](https://scrapfly.io/blog/posts/how-to-scrape-instagram)).

**2. Magic param (exige cookie de sessão):**
- `GET https://www.instagram.com/p/{shortcode}?__a=1&__d=dis`
- Headers: `Cookie` (com `ds_user_id` + `sessionid`), `X-IG-App-ID`, `Sec-Fetch-Site: same-origin`
- Fonte: [github.com/ahmedrangel/instagram-media-scraper](https://github.com/ahmedrangel/instagram-media-scraper)

**3. `/api/v1/media/{media_id}/info/` (private mobile API — CONFIRMADO):**
- Path exato: `/api/v1/media/${mediaId}/info/`
- Parâmetros assinados: `media_id`, `_csrftoken`, `_uid`, `_uuid`, `igtv_feed_preview:false`
- **Requer sessão autenticada** (csrftoken + uid dos cookies). Fonte primária (código): [github.com/dilame/instagram-private-api …/media.repository.ts](https://github.com/dilame/instagram-private-api/blob/master/src/repositories/media.repository.ts)

**x-ig-app-id — valor conhecido:** `936619743392459` identifica a requisição como vinda do web app do Instagram. **Valor errado = 403 imediato.** Fontes: [scrapfly.io](https://scrapfly.io/blog/posts/how-to-scrape-instagram) e [github.com/dilame/instagram-private-api …/request.ts](https://github.com/dilame/instagram-private-api/blob/master/src/core/request.ts). ⚠️ É um app-id "web" reutilizado, não uma credencial sua — pode ser rotacionado pela Meta a qualquer momento.

**Onde está o URL do vídeo:** a resposta JSON traz `video_versions[]` (array de `{height, width, type, url}`) e `image_versions2`. O `url` aponta para `*.cdninstagram.com` / `scontent-*.fbcdn.net`. **Shortcode → media_id (necessário para o path `/api/v1/media/{id}/info`, NÃO para o GraphQL que aceita shortcode direto):**
- Algoritmo: base64 do media_id em base-10, alfabeto alternativo `-_`; decodifica big-endian → inteiro. O número resultante = campo **`pk`** (a parte antes do `_` no campo `id`). Fontes com implementação: [gist sclark39](https://gist.github.com/sclark39/9daf13eea9c0b381667b61e3d2e7bc11) e [gist ohld](https://gist.github.com/ohld/62c2090e43bc0b6cc5e73dcc72c45901).

## (d) Por que SERVER-SIDE contorna o "filtro de URL-assinada" de um cliente

Este é um argumento de **engenharia** (não uma citação externa), fundamentado nos fatos verificados acima:

1. A URL final do CDN (`cdninstagram`/`fbcdn`, `play_addr` do TikTok, format URL do YouTube) é um **GET HTTPS assinado comum**. A assinatura (`oe`/`oh`/`_nc_ohc` no IG) autentica **o recurso e a validade temporal**, não a origem do requisitante nem um contexto de browser. Qualquer cliente HTTP que apresente a URL dentro da janela `oe` recebe os bytes — comprovado pelo fato de bibliotecas server-side (instaloader, yt-dlp, granary) baixarem esses mp4s. Fonte da natureza da assinatura: [dev.to/alex97po](https://dev.to/alex97po/pre-signed-url-expiry-how-to-detect-when-your-media-urls-will-break-4g74).
2. O "filtro de URL-assinada de um cliente" (ex.: um contexto de app/browser que se recusa a deixar uma URL assinada transitar, ou onde a URL expira antes de ser usada) é **contornado porque a URL nunca precisa sair do servidor**: a edge function/container resolve o media-info, **imediatamente** faz o fetch dos bytes e re-hospeda em bucket próprio (no MCORCH, storage privado + signed URL owner-scoped — padrão já vivo, ver `docs/processes/private-bucket-asset-signing.md`). A URL efêmera do terceiro vive milissegundos dentro do processo do servidor; o cliente só vê a URL assinada **do nosso** bucket.
3. Isso resolve os dois problemas de uma vez: **(i)** a expiração `oe` deixa de importar (baixamos antes de expirar); **(ii)** a URL de terceiro nunca atravessa um contexto filtrado/instável.
4. **Casamento com a arquitetura MCORCH:** este é exatamente o padrão de edge function que já governa mídia no repo — e reforça a regra anti-SSRF existente: URL vinda do caller/terceiro DEVE passar por `fetchPublicUrl` (revalida cada salto 3xx), nunca `fetch` cru, senão um `302 → 169.254.169.254` alcança a rede interna (`supabase/functions/_shared/public-url.ts`).

`could_not_verify`: não há uma fonte externa única que enuncie "(d)" — é síntese dos fatos primários citados + arquitetura interna do repo.
