> 101	5. If the input is a JSON-RPC _request_, the server **MUST** either
> 102	   return `Content-Type: text/event-stream`, to initiate an SSE stream, or
> 103	   `Content-Type: application/json`, to return one JSON object. The client **MUST**
> 104	   support both these cases.
> 105	6. If the server initiates an SSE stream:
> 106	   - The server **SHOULD** immediately send an SSE event consisting of an event
> 107	     ID and an empty `data` field in order to prime the client to reconnect
> 108	     (using that event ID as `Last-Event-ID`).
> 109	   - After the server has sent an SSE event with an event ID to the client, the
> 110	     server **MAY** close the _connection_ (without terminating the _SSE stream_)
> 111	     at any time in order to avoid holding a long-lived connection. The client
> 112	     **SHOULD** then "poll" the SSE stream by attempting to reconnect.
> 113	   - If the server does close the _connection_ prior to terminating the _SSE stream_,
> 114	     it **SHOULD** send an SSE event with a standard [`retry`](https://html.spec.whatwg.org/multipage/server-sent-events.html#:~:text=field%20name%20is%20%22retry%22) field before
> 115	     closing the connection. The client **MUST** respect the `retry` field,
> 116	     waiting the given number of milliseconds before attempting to reconnect.
> 117	   - The SSE stream **SHOULD** eventually include a JSON-RPC _response_ for the
> 118	     JSON-RPC _request_ sent in the POST body.
> 119	   - The server **MAY** send JSON-RPC _requests_ and _notifications_ before sending the
> 120	     JSON-RPC _response_. These messages **SHOULD** relate to the originating client
> 121	     _request_.
> 122	   - The server **MAY** terminate the SSE stream if the [session](#session-management)
> 123	     expires.
> 124	   - After the JSON-RPC _response_ has been sent, the server **SHOULD** terminate the
> 125	     SSE stream.
> 126	   - Disconnection **MAY** occur at any time (e.g., due to network conditions).
> 127	     Therefore:
> 128	     - Disconnection **SHOULD NOT** be interpreted as the client cancelling its request.
> 129	     - To cancel, the client **SHOULD** explicitly send an MCP `CancelledNotification`.
> 130	     - To avoid message loss due to disconnection, the server **MAY** make the stream
> 131	       [resumable](#resumability-and-redelivery).
> 132	
> 133	### Listening for Messages from the Server
> 134	
> 135	1. The client **MAY** issue an HTTP GET to the MCP endpoint. This can be used to open an
> 136	   SSE stream, allowing the server to communicate to the client, without the client first
> 137	   sending data via HTTP POST.
> 138	2. The client **MUST** include an `Accept` header, listing `text/event-stream` as a
> 139	   supported content type.
> 140	3. The server **MUST** either return `Content-Type: text/event-stream` in response to
> 141	   this HTTP GET, or else return HTTP 405 Method Not Allowed, indicating that the server
> 142	   does not offer an SSE stream at this endpoint.
> 143	4. If the server initiates an SSE stream:
> 144	   - The server **MAY** send JSON-RPC _requests_ and _notifications_ on the stream.
> 145	   - These messages **SHOULD** be unrelated to any concurrently-running JSON-RPC
> 146	     _request_ from the client.
> 147	   - The server **MUST NOT** send a JSON-RPC _response_ on the stream **unless**
> 148	     [resuming](#resumability-and-redelivery) a stream associated with a previous client
> 149	     request.
> 150	   - The server **MAY** close the SSE stream at any time.
> 151	   - If the server closes the _connection_ without terminating the _stream_, it
> 152	     **SHOULD** follow the same polling behavior as described for POST requests:
> 153	     sending a `retry` field and allowing the client to reconnect.
> 154	   - The client **MAY** close the SSE stream at any time.
> 155	
> 156	### Multiple Connections
> 157	
> 158	1. The client **MAY** remain connected to multiple SSE streams simultaneously.
> 159	2. The server **MUST** send each of its JSON-RPC messages on only one of the connected
> 160	   streams; that is, it **MUST NOT** broadcast the same message across multiple streams.
> 161	   - The risk of message loss **MAY** be mitigated by making the stream
> 162	     [resumable](#resumability-and-redelivery).
> 163	
> 164	### Resumability and Redelivery
> 165	
> 166	To support resuming broken connections, and redelivering messages that might otherwise be
> 167	lost:
> 168	
> 169	1. Servers **MAY** attach an `id` field to their SSE events, as described in the
> 170	   [SSE standard](https://html.spec.whatwg.org/multipage/server-sent-events.html#event-stream-interpretation).
> 171	   - If present, the ID **MUST** be globally unique across all streams within that
> 172	     [session](#session-management)—or all streams with that specific client, if session
> 173	     management is not in use.
> 174	   - Event IDs **SHOULD** encode sufficient information to identify the originating
> 175	     stream, enabling the server to correlate a `Last-Event-ID` to the correct stream.
> 176	2. If the client wishes to resume after a disconnection (whether due to network failure
> 177	   or server-initiated closure), it **SHOULD** issue an HTTP GET to the MCP endpoint,
> 178	   and include the
> 179	   [`Last-Event-ID`](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-last-event-id-header)
> 180	   header to indicate the last event ID it received.
> 181	   - The server **MAY** use this header to replay messages that would have been sent
> 182	     after the last event ID, _on the stream that was disconnected_, and to resume the
> 183	     stream from that point.
> 184	   - The server **MUST NOT** replay messages that would have been delivered on a
> 185	     different stream.
> 186	   - This mechanism applies regardless of how the original stream was initiated (via
> 187	     POST or GET). Resumption is always via HTTP GET with `Last-Event-ID`.
> 188	
> 189	In other words, these event IDs should be assigned by servers on a _per-stream_ basis, to
> 190	act as a cursor within that particular stream.
> 191	
> 192	### Session Management
> 193	
> 194	An MCP "session" consists of logically related interactions between a client and a
> 195	server, beginning with the [initialization phase](/specification/2025-11-25/basic/lifecycle). To support
> 196	servers which want to establish stateful sessions:
> 197	
> 198	1. A server using the Streamable HTTP transport **MAY** assign a session ID at
> 199	   initialization time, by including it in an `MCP-Session-Id` header on the HTTP
> 200	   response containing the `InitializeResult`.
> 201	   - The session ID **SHOULD** be globally unique and cryptographically secure (e.g., a
> 202	     securely generated UUID, a JWT, or a cryptographic hash).
> 203	   - The session ID **MUST** only contain visible ASCII characters (ranging from 0x21 to
> 204	     0x7E).
> 205	   - The client **MUST** handle the session ID in a secure manner, see [Session Hijacking mitigations](/specification/2025-11-25/basic/security_best_practices#session-hijacking) for more details.
> 206	2. If an `MCP-Session-Id` is returned by the server during initialization, clients using
> 207	   the Streamable HTTP transport **MUST** include it in the `MCP-Session-Id` header on
> 208	   all of their subsequent HTTP requests.
> 209	   - Servers that require a session ID **SHOULD** respond to requests without an
> 210	     `MCP-Session-Id` header (other than initialization) with HTTP 400 Bad Request.
> 211	3. The server **MAY** terminate the session at any time, after which it **MUST** respond
> 212	   to requests containing that session ID with HTTP 404 Not Found.
> 213	4. When a client receives HTTP 404 in response to a request containing an
> 214	   `MCP-Session-Id`, it **MUST** start a new session by sending a new `InitializeRequest`
> 215	   without a session ID attached.
> 216	5. Clients that no longer need a particular session (e.g., because the user is leaving
> 217	   the client application) **SHOULD** send an HTTP DELETE to the MCP endpoint with the
> 218	   `MCP-Session-Id` header, to explicitly terminate the session.
> 219	   - The server **MAY** respond to this request with HTTP 405 Method Not Allowed,
> 220	     indicating that the server does not allow clients to terminate sessions.
> 221	
> 222	### Sequence Diagram

> 263	### Protocol Version Header
> 264	
> 265	If using HTTP, the client **MUST** include the `MCP-Protocol-Version:
> 266	<protocol-version>` HTTP header on all subsequent requests to the MCP
> 267	server, allowing the MCP server to respond based on the MCP protocol version.
> 268	
> 269	For example: `MCP-Protocol-Version: 2025-11-25`
> 270	
> 271	The protocol version sent by the client **SHOULD** be the one [negotiated during
> 272	initialization](/specification/2025-11-25/basic/lifecycle#version-negotiation).
> 273	
> 274	For backwards compatibility, if the server does _not_ receive an `MCP-Protocol-Version`
> 275	header, and has no other way to identify the version - for example, by relying on the
> 276	protocol version negotiated during initialization - the server **SHOULD** assume protocol
> 277	version `2025-03-26`.
> 278	
> 279	If the server receives a request with an invalid or unsupported
> 280	`MCP-Protocol-Version`, it **MUST** respond with `400 Bad Request`.
> 281	
> 282	### Backwards Compatibility
> 283	
> 284	Clients and servers can maintain backwards compatibility with the deprecated [HTTP+SSE
> 285	transport](/specification/2024-11-05/basic/transports#http-with-sse) (from
> 286	protocol version 2024-11-05) as follows:
> 287	
> 288	**Servers** wanting to support older clients should:
> 289	
> 290	- Continue to host both the SSE and POST endpoints of the old transport, alongside the
> 291	  new "MCP endpoint" defined for the Streamable HTTP transport.
> 292	  - It is also possible to combine the old POST endpoint and the new MCP endpoint, but
> 293	    this may introduce unneeded complexity.
> 294	
> 295	**Clients** wanting to support older servers should:
> 296	
> 297	1. Accept an MCP server URL from the user, which may point to either a server using the
> 298	   old transport or the new transport.
> 299	2. Attempt to POST an `InitializeRequest` to the server URL, with an `Accept` header as
> 300	   defined above:
> 301	   - If it succeeds, the client can assume this is a server supporting the new Streamable
> 302	     HTTP transport.
> 303	   - If it fails with the following HTTP status codes "400 Bad Request", "404 Not
> 304	     Found" or "405 Method Not Allowed":
> 305	     - Issue a GET request to the server URL, expecting that this will open an SSE stream
> 306	       and return an `endpoint` event as the first event.
> 307	     - When the `endpoint` event arrives, the client can assume this is a server running
> 308	       the old HTTP+SSE transport, and should use that transport for all subsequent
> 309	       communication.
> 310	
> 311	## Custom Transports
> 312	
> 313	Clients and servers **MAY** implement additional custom transport mechanisms to suit
> 314	their specific needs. The protocol is transport-agnostic and can be implemented over any
> 315	communication channel that supports bidirectional message exchange.
> 316	
> 317	Implementers who choose to support custom transports **MUST** ensure they preserve the
> 318	JSON-RPC message format and lifecycle requirements defined by MCP. Custom transports
> 319	**SHOULD** document their specific connection establishment and message exchange patterns
> 320	to aid interoperability.
> 321	
> ```

> 14	
> 15	```mermaid
> 16	sequenceDiagram
> 17	    participant Client

> 29	## Terminology
> 30	
> 31	This page uses the following terms for interoperability across protocol
> 32	revisions:
> 33	
> 34	- **Modern**: protocol versions that convey version, identity, and
> 35	  capabilities as per-request metadata (revision `2026-07-28` and later).
> 36	- **Legacy**: protocol versions that establish a session with an
> 37	  `initialize` handshake (`2025-11-25` and earlier).
> 38	- **Dual-era**: an implementation that supports both modern and legacy
> 39	  versions.
> 40	
> 41	## Protocol Version Negotiation
> 42	
> 43	Every request declares the protocol version it is using in its
> 44	[`_meta`](/specification/draft/basic/index#meta) field. On HTTP, this is
> 45	also carried in the
> 46	[`MCP-Protocol-Version` header](/specification/draft/basic/transports/streamable-http#protocol-version-header).
> 47	
> 48	If the server does not implement the requested version (whether the version
> 49	is unknown to the server, or is a known version the server has chosen not to
> 50	support), it **MUST** respond with an
> 51	[`UnsupportedProtocolVersionError`](/specification/draft/schema#unsupportedprotocolversionerror)
> 52	listing the versions it does support:
> 53	
> 54	```json
> 55	{
> 56	  "jsonrpc": "2.0",
> 57	  "id": 1,
> 58	  "error": {
> 59	    "code": -32004,
> 60	    "message": "Unsupported protocol version",
> 61	    "data": {
> 62	      "supported": ["2026-07-28", "2025-11-25"],
> 63	      "requested": "1900-01-01"
> 64	    }
> 65	  }
> 66	}
> 67	```
> 68	
> 69	The client **SHOULD** select a mutually supported version from the `supported`
> 70	list and retry the request, or surface an error to the user if no compatible
> 71	version exists.
> 72	
> 73	Servers **MUST** implement
> 74	[`server/discover`](/specification/draft/server/discover). Clients
> 75	**MAY** call it before sending any other requests to learn the server's
> 76	supported versions up front, but are not required to: a client is free to
> 77	invoke any RPC inline and handle `UnsupportedProtocolVersionError` if its
> 78	preferred version is not supported.

> 80	## Extension Negotiation
> 81	
> 82	Clients and servers can negotiate support for optional
> 83	[extensions](/docs/extensions/overview) beyond the core protocol. Extensions
> 84	are advertised in the `extensions` field of capabilities, which is a map of
> 85	extension identifiers to per-extension settings objects. Extension identifiers
> 86	**MUST** follow the [`_meta` key naming rules](/specification/draft/basic/index#meta),
> 87	with a mandatory prefix.
> 88	
> 89	The following is an example of a client that advertises the
> 90	[MCP Apps extension](/extensions/apps/overview) identified as `io.modelcontextprotocol/ui`:
> 91	
> 92	```json
> 93	{
> 94	  "capabilities": {
> 95	    "roots": {},
> 96	    "extensions": {
> 97	      "io.modelcontextprotocol/ui": {
> 98	        "mimeTypes": ["text/html;profile=mcp-app"]
> 99	      }
> 100	    }
> 101	  }
> 102	}
> 103	```
> 104	
> 105	An example of [Tasks extension](/extensions/tasks/overview) identified as `io.modelcontextprotocol/tasks`:
> 106	
> 107	```json
> 108	{
> 109	  "capabilities": {
> 110	    "tools": {},
> 111	    "extensions": {
> 112	      "io.modelcontextprotocol/tasks": {}
> 113	    }
> 114	  }
> 115	}
> 116	```
> 117	
> 118	Each extension specifies the schema of its settings object; an empty object
> 119	indicates support with no additional settings.
> 120	
> 121	If one party supports an extension but the other does not, the supporting
> 122	party **MUST** either revert to core protocol behavior or reject the request
> 123	with an appropriate error. Extensions **SHOULD** document their expected
> 124	fallback behavior.
> 125	
> 126	## Backward Compatibility with Initialization-Based Versions
> 127	
> 128	A server that wishes to support both [legacy](#terminology) clients (which
> 129	expect an `initialize` handshake) and [modern](#terminology) clients (which
> 130	use per-request metadata) **MAY** implement both behaviors.
> 131	
> 132	A client that needs to interoperate with both kinds of servers detects the
> 133	server's era with transport-specific mechanics, specified in the binding
> 134	pages:
> 135	
> 136	- [stdio](/specification/draft/basic/transports/stdio#backward-compatibility):
> 137	  probe with `server/discover` and fall back on any error that is not a
> 138	  recognized modern error.
> 139	- [Streamable HTTP](/specification/draft/basic/transports/streamable-http#backward-compatibility):
> 140	  attempt a modern request and inspect the body of a `400 Bad Request`
> 141	  before falling back.
> 142	
> 143	In both cases, a recognized modern JSON-RPC error (such as
> 144	[`UnsupportedProtocolVersionError`](/specification/draft/schema#unsupportedprotocolversionerror))
> 145	identifies a modern server: the client retries with a supported version
> 146	rather than falling back. Anything else identifies a legacy server.
> 147	
> 148	The era determination is a property of the server, not of an individual
> 149	request. Clients **SHOULD** cache the result for the lifetime of the server
> 150	process (stdio) or origin (HTTP), and **MAY** persist it across restarts of
> 151	the same server configuration, re-probing if the cached assumption later
> 152	fails.
> 153	
> 154	A server that supports only [modern](#terminology) versions **SHOULD** name
> 155	the protocol versions it supports in any error it returns to an `initialize`
> 156	request, on any transport: legacy clients have no fall-forward mechanism, and
> 157	this message may be the only diagnostic they can surface to users.
> 158

> 180	  legacy protocol version.

> 182	A dual-era server **MAY** serve both eras concurrently on the same endpoint
> 183	or process.

> 39	## Roles
> 40	
> 41	A protected _MCP server_ acts as an [OAuth 2.1 resource server](https://www.ietf.org/archive/id/draft-ietf-oauth-v2-1-13.html#name-roles),
> 42	capable of accepting and responding to protected resource requests using access tokens.
> 43	
> 44	An _MCP client_ acts as an [OAuth 2.1 client](https://www.ietf.org/archive/id/draft-ietf-oauth-v2-1-13.html#name-roles),
> 45	making protected resource requests on behalf of a resource owner.
> 46	
> 47	The _authorization server_ is responsible for interacting with the user (if necessary) and issuing access tokens for use at the MCP server.
> 48	The implementation details of the authorization server are beyond the scope of this specification. It may be hosted with the
> 49	resource server or a separate entity. The [Authorization Server Discovery section](#authorization-server-discovery)
> 50	specifies how an MCP server indicates the location of its corresponding authorization server to a client.

> 52	## Overview
> 53	
> 54	1. Authorization servers **MUST** implement OAuth 2.1 with appropriate security
> 55	   measures for both confidential and public clients.
> 56	
> 57	2. Authorization servers and MCP clients **SHOULD** support OAuth Client ID Metadata Documents
> 58	   ([draft-ietf-oauth-client-id-metadata-document-00](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-00)).
> 59	
> 60	3. Authorization servers and MCP clients **MAY** support the OAuth 2.0 Dynamic Client Registration
> 61	   Protocol ([RFC7591](https://datatracker.ietf.org/doc/html/rfc7591)).
> 62	
> 63	4. MCP servers **MUST** implement OAuth 2.0 Protected Resource Metadata ([RFC9728](https://datatracker.ietf.org/doc/html/rfc9728)).
> 64	   MCP clients **MUST** use OAuth 2.0 Protected Resource Metadata for authorization server discovery.
> 65	
> 66	5. MCP authorization servers **MUST** provide at least one of the following discovery mechanisms:
> 67	   - OAuth 2.0 Authorization Server Metadata ([RFC8414](https://datatracker.ietf.org/doc/html/rfc8414))
> 68	   - [OpenID Connect Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html)
> 69	
> 70	   MCP clients **MUST** support both discovery mechanisms to obtain the information required to interact with the authorization server.

> 72	## Authorization Server Discovery
> 73	
> 74	This section describes the mechanisms by which MCP servers advertise their associated
> 75	authorization servers to MCP clients, as well as the discovery process through which MCP
> 76	clients can determine authorization server endpoints and supported capabilities.
> 77	
> 78	### Authorization Server Location
> 79	
> 80	MCP servers **MUST** implement the OAuth 2.0 Protected Resource Metadata ([RFC9728](https://datatracker.ietf.org/doc/html/rfc9728))
> 81	specification to indicate the locations of authorization servers. The Protected Resource Metadata document returned by the MCP server **MUST** include
> 82	the `authorization_servers` field containing at least one authorization server.
> 83	
> 84	The specific use of `authorization_servers` is beyond the scope of this specification; implementers should consult
> 85	OAuth 2.0 Protected Resource Metadata ([RFC9728](https://datatracker.ietf.org/doc/html/rfc9728)) for
> 86	guidance on implementation details.
> 87	
> 88	Implementors should note that Protected Resource Metadata documents can define multiple authorization servers. The responsibility for selecting which authorization server to use lies with the MCP client, following the guidelines specified in
> 89	[RFC9728 Section 7.6 "Authorization Servers"](https://datatracker.ietf.org/doc/html/rfc9728#name-authorization-servers).
> 90	
> 91	### Protected Resource Metadata Discovery Requirements
> 92	
> 93	MCP servers **MUST** implement one of the following discovery mechanisms to provide authorization server location information to MCP clients:
> 94	
> 95	1. **WWW-Authenticate Header**: Include the resource metadata URL in the `WWW-Authenticate` HTTP header under `resource_metadata` when returning `401 Unauthorized` responses, as described in [RFC9728 Section 5.1](https://datatracker.ietf.org/doc/html/rfc9728#name-www-authenticate-response).
> 96	
> 97	2. **Well-Known URI**: Serve metadata at a well-known URI as specified in [RFC9728](https://datatracker.ietf.org/doc/html/rfc9728). This can be either:
> 98	   - At the path of the server's MCP endpoint: `https://example.com/public/mcp` could host metadata at `https://example.com/.well-known/oauth-protected-resource/public/mcp`
> 99	   - At the root: `https://example.com/.well-known/oauth-protected-resource`
> 100	
> 101	MCP clients **MUST** support both discovery mechanisms and use the resource metadata URL from the parsed `WWW-Authenticate` headers when present; otherwise, they **MUST** fall back to constructing and requesting the well-known URIs in the order listed above.
> 102	
> 103	MCP servers **SHOULD** include a `scope` parameter in the `WWW-Authenticate` header as defined in
> 104	[RFC 6750 Section 3](https://datatracker.ietf.org/doc/html/rfc6750#section-3)
> 105	to indicate the scopes required for accessing the resource. This provides clients with immediate
> 106	guidance on the appropriate scopes to request during authorization,
> 107	following the principle of least privilege and preventing clients from requesting excessive permissions.
> 108	
> 109	The scopes included in the `WWW-Authenticate` challenge **MAY** match `scopes_supported`, be a subset
> 110	or superset of it, or an alternative collection that is neither a strict subset nor
> 111	superset. Clients **MUST NOT** assume any particular set relationship between the challenged
> 112	scope set and `scopes_supported`. Clients **MUST** treat the scopes provided in the
> 113	challenge as authoritative for satisfying the current request. Servers **SHOULD** strive for
> 114	consistency in how they construct scope sets but they are not required to surface every dynamically
> 115	issued scope through `scopes_supported`.
> 116	
> 117	Example 401 response with scope guidance:
> 118	
> 119	```http
> 120	HTTP/1.1 401 Unauthorized
> 121	WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource",
> 122	                         scope="files:read"
> 123	```
> 124	
> 125	MCP clients **MUST** be able to parse `WWW-Authenticate` headers and respond appropriately to `HTTP 401 Unauthorized` responses from the MCP server.
> 126	
> 127	If the `scope` parameter is absent, clients **SHOULD** apply the fallback behavior defined in the [Scope Selection Strategy](#scope-selection-strategy) section.

> 130

> 141	For issuer URLs without path components (e.g., `https://auth.example.com`), clients **MUST** try:
> 142	
> 143	1. OAuth 2.0 Authorization Server Metadata: `https://auth.example.com/.well-known/oauth-authorization-server`

> 196	## Client Registration Approaches
> 197	
> 198	MCP supports three client registration mechanisms. Choose based on your scenario:
> 199	
> 200	- **Client ID Metadata Documents**: When client and server have no prior relationship (most common)
> 201	- **Pre-registration**: When client and server have an existing relationship
> 202	- **Dynamic Client Registration**: For backwards compatibility or specific requirements

> 208	3. Use Dynamic Client Registration as a fallback if the Authorization Server supports it (via `registration_endpoint` in OAuth Authorization Server Metadata)
> 209	4. Prompt the user to enter the client information if no other option is available

> 213	MCP clients and authorization servers **SHOULD** support OAuth Client ID Metadata Documents as specified in

> 215	This approach enables clients to use HTTPS URLs as client identifiers, where the URL points to a JSON document
> 216	containing client metadata. This addresses the common MCP scenario where servers and clients have

> 275	    Client->>Server: Authorization Request<br/>client_id=https://app.example.com/oauth/metadata.json<br/>redirect_uri=http://localhost:3000/callback
> 276	
> 277	    Server->>User: Authentication prompt
> 278	    User->>Server: Provides credentials
> 279	    Note over Server: Authenticates user
> 280	
> 281	    Note over Server: Detects URL-formatted client_id
> 282	
> 283	    Server->>Metadata: GET https://app.example.com/oauth/metadata.json
> 284	    Metadata-->>Server: JSON Metadata Document<br/>{client_id, client_name, redirect_uris, ...}
> 285	
> 286	    Note over Server: Validates:<br/>1. client_id matches URL<br/>2. redirect_uri in allowed list<br/>3. Document structure valid<br/>4. (Optional) Domain allowed via trust policy
> 287	
> 288	    alt Validation Success
> 289	        Server->>User: Display consent page with client_name
> 290	        User->>Server: Approves access
> 291	        Server->>Client: Authorization code via redirect_uri
> 292	        Client->>Server: Exchange code for token<br/>client_id=https://app.example.com/oauth/metadata.json
> 293	        Server-->>Client: Access token
> 294	        Client->>Resource: MCP requests with access token
> 295	        Resource-->>Client: MCP responses
> 296	    else Validation Failure
> 297	        Server->>User: Error response<br/>error=invalid_client or invalid_request
> 298	    end
> 299	
> 300	    Note over Server: Cache metadata for future requests<br/>(respecting HTTP cache headers)
> 301	```

> 303	#### Discovery
> 304	
> 305	Authorization servers advertise that they support clients using Client ID Metadata Documents by including the following property in their OAuth Authorization Server metadata:
> 306	
> 307	```json
> 308	{
> 309	  "client_id_metadata_document_supported": true
> 310	}
> 311	```
> 312	
> 313	MCP clients **SHOULD** check for this capability and **MAY** fall back to Dynamic Client Registration
> 314	or pre-registration if unavailable.
> 315	
> 316	### Preregistration
> 317	
> 318	MCP clients **SHOULD** support an option for static client credentials such as those supplied by a preregistration flow. This could be:
> 319	
> 320	1. Hardcode a client ID (and, if applicable, client credentials) specifically for the MCP client to use when
> 321	   interacting with that authorization server, or
> 322	2. Present a UI to users that allows them to enter these details, after registering an
> 323	   OAuth client themselves (e.g., through a configuration interface hosted by the
> 324	   server).
> 325	
> 326	### Dynamic Client Registration
> 327	
> 328	MCP clients and authorization servers **MAY** support the
> 329	OAuth 2.0 Dynamic Client Registration Protocol [RFC7591](https://datatracker.ietf.org/doc/html/rfc7591)
> 330	to allow MCP clients to obtain OAuth client IDs without user interaction.
> 331	This option is included for backwards compatibility with earlier versions of the MCP authorization spec.

> 333	## Scope Selection Strategy
> 334	
> 335	When implementing authorization flows, MCP clients **SHOULD** follow the principle of least privilege by requesting
> 336	only the scopes necessary for their intended operations. During the initial authorization handshake, MCP clients
> 337	**SHOULD** follow this priority order for scope selection:
> 338	
> 339	1. **Use `scope` parameter** from the initial `WWW-Authenticate` header in the 401 response, if provided
> 340	2. **If `scope` is not available**, use all scopes defined in `scopes_supported` from the Protected Resource Metadata document, omitting the `scope` parameter if `scopes_supported` is undefined.
> 341	
> 342	This approach accommodates the general-purpose nature of MCP clients, which typically lack domain-specific knowledge to make informed decisions about individual scope selection. Requesting all available scopes allows the authorization server and end-user to determine appropriate permissions during the consent process.
> 343	
> 344	This approach minimizes user friction while following the principle of least privilege.
> 345	The `scopes_supported` field is intended to represent the minimal set of scopes necessary
> 346	for basic functionality (see [Scope Minimization](/specification/2025-11-25/basic/security_best_practices#scope-minimization)),
> 347	with additional scopes requested incrementally through the step-up authorization flow steps
> 348	described in the [Scope Challenge Handling](#scope-challenge-handling) section.
> 349	
> 350	## Authorization Flow Steps
> 351	
> 352	The complete Authorization flow proceeds as follows:
> 353	
> 354	```mermaid
> 355	sequenceDiagram
> 356	    participant B as User-Agent (Browser)
> 357	    participant C as Client
> 358	    participant M as MCP Server (Resource Server)
> 359	    participant A as Authorization Server
> 360	
> 361	    C->>M: MCP request without token
> 362	    M->>C: HTTP 401 Unauthorized with WWW-Authenticate header
> 363	    Note over C: Extract resource_metadata URL from WWW-Authenticate
> 364	
> 365	    C->>M: Request Protected Resource Metadata
> 366	    M->>C: Return metadata
> 367	
> 368	    Note over C: Parse metadata and extract authorization server(s)<br/>Client determines AS to use
> 369	
> 370	    C->>A: GET Authorization server metadata endpoint
> 371	    Note over C,A: Try OAuth 2.0 and OpenID Connect<br/>discovery endpoints in priority order
> 372	    A-->>C: Authorization server metadata
> 373	
> 374	    alt Client ID Metadata Documents
> 375	        Note over C: Client uses HTTPS URL as client_id
> 376	        Note over A: Server detects URL-formatted client_id
> 377	        A->>C: Fetch metadata from client_id URL
> 378	        C-->>A: JSON metadata document
> 379	        Note over A: Validate metadata and redirect_uris
> 380	    else Dynamic client registration
> 381	        C->>A: POST /register
> 382	        A->>C: Client Credentials
> 383	    else Pre-registered client
> 384	        Note over C: Use existing client_id
> 385	    end
> 386	
> 387	    Note over C: Generate PKCE parameters<br/>Include resource parameter<br/>Apply scope selection strategy
> 388	    C->>B: Open browser with authorization URL + code_challenge + resource
> 389	    B->>A: Authorization request with resource parameter
> 390	    Note over A: User authorizes
> 391	    A->>B: Redirect to callback with authorization code
> 392	    B->>C: Authorization code callback
> 393	    C->>A: Token request + code_verifier + resource
> 394	    A->>C: Access token (+ refresh token)
> 395	    C->>M: MCP request with access token
> 396	    M-->>C: MCP response
> 397	    Note over C,M: MCP communication continues with valid token
> 398	```

> 400	## Resource Parameter Implementation
> 401	
> 402	MCP clients **MUST** implement Resource Indicators for OAuth 2.0 as defined in [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html)
> 403	to explicitly specify the target resource for which the token is being requested. The `resource` parameter:
> 404	
> 405	1. **MUST** be included in both authorization requests and token requests.
> 406	2. **MUST** identify the MCP server that the client intends to use the token with.
> 407	3. **MUST** use the canonical URI of the MCP server as defined in [RFC 8707 Section 2](https://www.rfc-editor.org/rfc/rfc8707.html#name-access-token-request).
> 408	
> 409	### Canonical Server URI
> 410	
> 411	For the purposes of this specification, the canonical URI of an MCP server is defined as the resource identifier as specified in
> 412	[RFC 8707 Section 2](https://www.rfc-editor.org/rfc/rfc8707.html#section-2) and aligns with the `resource` parameter in
> 413	[RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728).
> 414	
> 415	MCP clients **SHOULD** provide the most specific URI that they can for the MCP server they intend to access, following the guidance in [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707). While the canonical form uses lowercase scheme and host components, implementations **SHOULD** accept uppercase scheme and host components for robustness and interoperability.
> 416	
> 417	Examples of valid canonical URIs:
> 418	
> 419	- `https://mcp.example.com/mcp`
> 420	- `https://mcp.example.com`
> 421	- `https://mcp.example.com:8443`
> 422	- `https://mcp.example.com/server/mcp` (when path component is necessary to identify individual MCP server)
> 423	
> 424	Examples of invalid canonical URIs:
> 425	
> 426	- `mcp.example.com` (missing scheme)
> 427	- `https://mcp.example.com#fragment` (contains fragment)
> 428	
> 429	> **Note:** While both `https://mcp.example.com/` (with trailing slash) and `https://mcp.example.com` (without trailing slash) are technically valid absolute URIs according to [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986), implementations **SHOULD** consistently use the form without the trailing slash for better interoperability unless the trailing slash is semantically significant for the specific resource.
> 430	
> 431	For example, if accessing an MCP server at `https://mcp.example.com`, the authorization request would include:
> 432	
> 433	```
> 434	&resource=https%3A%2F%2Fmcp.example.com
> 435	```
> 436	
> 437	MCP clients **MUST** send this parameter regardless of whether authorization servers support it.
> 438	
> 439	## Access Token Usage
> 440	
> 441	### Token Requirements
> 442	
> 443	Access token handling when making requests to MCP servers **MUST** conform to the requirements defined in
> 444	[OAuth 2.1 Section 5 "Resource Requests"](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-5).
> 445	Specifically:
> 446	
> 447	1. MCP client **MUST** use the Authorization request header field defined in
> 448	   [OAuth 2.1 Section 5.1.1](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-5.1.1):
> 449	
> 450	```
> 451	Authorization: Bearer <access-token>
> 452	```
> 453	
> 454	Note that authorization **MUST** be included in every HTTP request from client to server,
> 455	even if they are part of the same logical session.
> 456	
> 457	2. Access tokens **MUST NOT** be included in the URI query string
> 458	
> 459	Example request:
> 460	
> 461	```http
> 462	GET /mcp HTTP/1.1
> 463	Host: mcp.example.com
> 464	Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
> 465	```
> 466	
> 467	### Token Handling
> 468	
> 469	MCP servers, acting in their role as an OAuth 2.1 resource server, **MUST** validate access tokens as described in
> 470	[OAuth 2.1 Section 5.2](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-5.2).
> 471	MCP servers **MUST** validate that access tokens were issued specifically for them as the intended audience,
> 472	according to [RFC 8707 Section 2](https://www.rfc-editor.org/rfc/rfc8707.html#section-2).
> 473	If validation fails, servers **MUST** respond according to
> 474	[OAuth 2.1 Section 5.3](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-5.3)
> 475	error handling requirements. Invalid or expired tokens **MUST** receive a HTTP 401
> 476	response.
> 477	
> 478	MCP clients **MUST NOT** send tokens to the MCP server other than ones issued by the MCP server's authorization server.
> 479	
> 480	MCP servers **MUST** only accept tokens that are valid for use with their
> 481	own resources.
> 482	
> 483	MCP servers **MUST NOT** accept or transit any other tokens.
> 484	
> 485	## Error Handling
> 486	
> 487	Servers **MUST** return appropriate HTTP status codes for authorization errors:
> 488	
> 489	| Status Code | Description  | Usage                                      |
> 490	| ----------- | ------------ | ------------------------------------------ |
> 491	| 401         | Unauthorized | Authorization required or token invalid    |
> 492	| 403         | Forbidden    | Invalid scopes or insufficient permissions |
> 493	| 400         | Bad Request  | Malformed authorization request            |
> 494	
> 495	### Scope Challenge Handling
> 496	
> 497	This section covers handling insufficient scope errors during runtime operations when
> 498	a client already has a token but needs additional permissions. This follows the error
> 499	handling patterns defined in [OAuth 2.1 Section 5](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-5)
> 500	and leverages the metadata fields from [RFC 9728 (OAuth 2.0 Protected Resource Metadata)](https://datatracker.ietf.org/doc/html/rfc9728).
> 501	
> 502	#### Runtime Insufficient Scope Errors
> 503	
> 504	When a client makes a request with an access token with insufficient
> 505	scope during runtime operations, the server **SHOULD** respond with:
> 506	
> 507	- `HTTP 403 Forbidden` status code (per [RFC 6750 Section 3.1](https://datatracker.ietf.org/doc/html/rfc6750#section-3.1))
> 508	- `WWW-Authenticate` header with the `Bearer` scheme and additional parameters:
> 509	  - `error="insufficient_scope"` - indicating the specific type of authorization failure
> 510	  - `scope="required_scope1 required_scope2"` - specifying the minimum scopes needed for the operation
> 511	  - `resource_metadata` - the URI of the Protected Resource Metadata document (for consistency with 401 responses)
> 512	  - `error_description` (optional) - human-readable description of the error
> 513	
> 514	**Server Scope Management**: When responding with insufficient scope errors, servers
> 515	**SHOULD** include the scopes needed to satisfy the current request in the `scope`
> 516	parameter.
> 517	
> 518	Servers have flexibility in determining which scopes to include:
> 519	
> 520	- **Minimum approach**: Include the newly-required scopes for the specific operation. Include any existing granted scopes as well, if they are required, to prevent clients from losing previously granted permissions.
> 521	- **Recommended approach**: Include both existing relevant scopes and newly required scopes to prevent clients from losing previously granted permissions
> 522	- **Extended approach**: Include existing scopes, newly required scopes, and related scopes that commonly work together
> 523	
> 524	The choice depends on the server's assessment of user experience impact and authorization friction.
> 525	
> 526	Servers **SHOULD** be consistent in their scope inclusion strategy to provide predictable behavior for clients.
> 527	
> 528	Servers **SHOULD** consider the user experience impact when determining which scopes to include in the
> 529	response, as misconfigured scopes may require frequent user interaction.
> 530	
> 531	Example insufficient scope response:
> 532	
> 533	```http
> 534	HTTP/1.1 403 Forbidden
> 535	WWW-Authenticate: Bearer error="insufficient_scope",
> 536	                         scope="files:read files:write user:profile",
> 537	                         resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource",
> 538	                         error_description="Additional file write permission required"
> 539	```
> 540	
> 541	#### Step-Up Authorization Flow
> 542	
> 543	Clients will receive scope-related errors during initial authorization or at runtime (`insufficient_scope`).
> 544	Clients **SHOULD** respond to these errors by requesting a new access token with an increased set of scopes via a step-up authorization flow or handle the errors in other, appropriate ways.
> 545	Clients acting on behalf of a user **SHOULD** attempt the step-up authorization flow. Clients acting on their own behalf (`client_credentials` clients)
> 546	**MAY** attempt the step-up authorization flow or abort the request immediately.
> 547	
> 548	The flow is as follows:
> 549	
> 550	1. **Parse error information** from the authorization server response or `WWW-Authenticate` header
> 551	2. **Determine required scopes** as outlined in [Scope Selection Strategy](#scope-selection-strategy).
> 552	3. **Initiate (re-)authorization** with the determined scope set
> 553	4. **Retry the original request** with the new authorization no more than a few times and treat this as a permanent authorization failure
> 554	
> 555	Clients **SHOULD** implement retry limits and **SHOULD** track scope upgrade attempts to avoid
> 556	repeated failures for the same resource and operation combination.
> 557	
> 558	## Security Considerations
> 559	
> 560	Implementations **MUST** follow OAuth 2.1 security best practices as laid out in [OAuth 2.1 Section 7. "Security Considerations"](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#name-security-considerations).
> 561	
> 562	### Token Audience Binding and Validation
> 563	
> 564	[RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html) Resource Indicators provide critical security benefits by binding tokens to their intended
> 565	audiences **when the Authorization Server supports the capability**. To enable current and future adoption:
> 566	
> 567	- MCP clients **MUST** include the `resource` parameter in authorization and token requests as specified in the [Resource Parameter Implementation](#resource-parameter-implementation) section
> 568	- MCP servers **MUST** validate that tokens presented to them were specifically issued for their use
> 569	
> 570	The [Security Best Practices document](/specification/2025-11-25/basic/security_best_practices#token-passthrough)
> 571	outlines why token audience validation is crucial and why token passthrough is explicitly forbidden.
> 572	
> 573	### Token Theft
> 574	
> 575	Attackers who obtain tokens stored by the client, or tokens cached or logged on the server can access protected resources with
> 576	requests that appear legitimate to resource servers.
> 577	
> 578	Clients and servers **MUST** implement secure token storage and follow OAuth best practices,
> 579	as outlined in [OAuth 2.1, Section 7.1](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-7.1).
> 580	
> 581	Authorization servers **SHOULD** issue short-lived access tokens to reduce the impact of leaked tokens.
> 582	For public clients, authorization servers **MUST** rotate refresh tokens as described in [OAuth 2.1 Section 4.3.1 "Token Endpoint Extension"](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-4.3.1).
> 583	
> 584	### Communication Security
> 585	
> 586	Implementations **MUST** follow [OAuth 2.1 Section 1.5 "Communication Security"](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-1.5).
> 587	
> 588	Specifically:
> 589	
> 590	1. All authorization server endpoints **MUST** be served over HTTPS.
> 591	1. All redirect URIs **MUST** be either `localhost` or use HTTPS.
> 592	
> 593	### Authorization Code Protection
> 594	
> 595	An attacker who has gained access to an authorization code contained in an authorization response can try to redeem the authorization code for an access token or otherwise make use of the authorization code.
> 596	(Further described in [OAuth 2.1 Section 7.5](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-7.5))
> 597	
> 598	To mitigate this, MCP clients **MUST** implement PKCE according to [OAuth 2.1 Section 7.5.2](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-7.5.2) and **MUST** verify PKCE support before proceeding with authorization.
> 599	PKCE helps prevent authorization code interception and injection attacks by requiring clients to create a secret verifier-challenge pair, ensuring that only the original requestor can exchange an authorization code for tokens.
> 600	
> 601	MCP clients **MUST** use the `S256` code challenge method when technically capable, as required by [OAuth 2.1 Section 4.1.1](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-4.1.1).
> 602	
> 603	Since OAuth 2.1 and PKCE specifications do not define a mechanism for clients to discover PKCE support, MCP clients **MUST** rely on authorization server metadata to verify this capability:
> 604	
> 605	- **OAuth 2.0 Authorization Server Metadata**: If `code_challenge_methods_supported` is absent, the authorization server does not support PKCE and MCP clients **MUST** refuse to proceed.
> 606	
> 607	- **OpenID Connect Discovery 1.0**: While the [OpenID Provider Metadata](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderMetadata) does not define `code_challenge_methods_supported`, this field is commonly included by OpenID providers. MCP clients **MUST** verify the presence of `code_challenge_methods_supported` in the provider metadata response. If the field is absent, MCP clients **MUST** refuse to proceed.
> 608	
> 609	Authorization servers providing OpenID Connect Discovery 1.0 **MUST** include `code_challenge_methods_supported` in their metadata to ensure MCP compatibility.
> 610	
> 611	### Open Redirection
> 612	
> 613	An attacker may craft malicious redirect URIs to direct users to phishing sites.
> 614	
> 615	MCP clients **MUST** have redirect URIs registered with the authorization server.
> 616	
> 617	Authorization servers **MUST** validate exact redirect URIs against pre-registered values to prevent redirection attacks.
> 618	
> 619	MCP clients **SHOULD** use and verify state parameters in the authorization code flow
> 620	and discard any results that do not include or have a mismatch with the original state.
> 621	
> 622	Authorization servers **MUST** take precautions to prevent redirecting user agents to untrusted URI's, following suggestions laid out in [OAuth 2.1 Section 7.12.2](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13#section-7.12.2)
> 623	
> 624	Authorization servers **SHOULD** only automatically redirect the user agent if it trusts the redirection URI. If the URI is not trusted, the authorization server MAY inform the user and rely on the user to make the correct decision.
> 625	
> 626	### Client ID Metadata Document Security
> 627	
> 628	When implementing Client ID Metadata Documents, authorization servers **MUST** consider the security implications
> 629	detailed in [OAuth Client ID Metadata Document, Section 6](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-00#name-security-considerations).
> 630	Key considerations include:
> 631	
> 632	#### Authorization Server Abuse Protection
> 633	
> 634	The authorization server takes a URL as input from an unknown client and fetches that URL.
> 635	A malicious client could use this to trigger the authorization server to make requests to arbitrary URLs,
> 636	such as requests to private administration endpoints the authorization server has access to.
> 637	
> 638	Authorization servers fetching metadata documents **SHOULD** consider
> 639	[Server-Side Request Forgery (SSRF)](https://developer.mozilla.org/docs/Web/Security/Attacks/SSRF) risks, as described in [OAuth Client ID Metadata Document: Server Side Request Forgery (SSRF) Attacks](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-00#name-server-side-request-forgery).
> 640	
> 641	#### Localhost Redirect URI Risks
> 642	
> 643	Client ID Metadata Documents cannot prevent `localhost` URL impersonation by themselves. An attacker can claim to be any client by:
> 644	
> 645	1. Providing the legitimate client's metadata URL as their `client_id`
> 646	2. Binding to the any `localhost` port, and providing that address as the redirect_uri
> 647	3. Receiving the authorization code via the redirect when the user approves
> 648	
> 649	The server will see the legitimate client's metadata document and the user will see the legitimate client's name, making attack detection difficult.
> 650	
> 651	Authorization servers:
> 652	
> 653	- **SHOULD** display additional warnings for `localhost`-only redirect URIs
> 654	- **MAY** require additional attestation mechanisms for enhanced security
> 655	- **MUST** clearly display the redirect URI hostname during authorization
> 656	
> 657	#### Trust Policies
> 658	
> 659	Authorization servers **MAY** implement domain-based trust policies:
> 660	
> 661	- Allowlists for trusted domains (for protected servers)
> 662	- Accept any HTTPS `client_id` (for open servers)
> 663	- Reputation checks for unknown domains
> 664	- Restrictions based on domain age or certificate validation
> 665	- Display the CIMD and other associated client hostnames prominently to prevent phishing
> 666	
> 667	Servers maintain full control over their access policies.
> 668	
> 669	### Confused Deputy Problem
> 670	
> 671	Attackers can exploit MCP servers acting as intermediaries to third-party APIs, leading to [confused deputy vulnerabilities](/specification/2025-11-25/basic/security_best_practices#confused-deputy-problem).
> 672	By using stolen authorization codes, they can obtain access tokens without user consent.
> 673	
> 674	MCP proxy servers using static client IDs **MUST** obtain user consent for each dynamically
> 675	registered client before forwarding to third-party authorization servers (which may require additional consent).
> 676	
> 677	### Access Token Privilege Restriction
> 678	
> 679	An attacker can gain unauthorized access or otherwise compromise an MCP server if the server accepts tokens issued for other resources.
> 680	
> 681	This vulnerability has two critical dimensions:
> 682	
> 683	1. **Audience validation failures.** When an MCP server doesn't verify that tokens were specifically intended for it (for example, via the audience claim, as mentioned in [RFC9068](https://www.rfc-editor.org/rfc/rfc9068.html)), it may accept tokens originally issued for other services. This breaks a fundamental OAuth security boundary, allowing attackers to reuse legitimate tokens across different services than intended.
> 684	2. **Token passthrough.** If the MCP server not only accepts tokens with incorrect audiences but also forwards these unmodified tokens to downstream services, it can potentially cause the ["confused deputy" problem](#confused-deputy-problem), where the downstream API may incorrectly trust the token as if it came from the MCP server or assume the token was validated by the upstream API. See the [Token Passthrough section](/specification/2025-11-25/basic/security_best_practices#token-passthrough) of the Security Best Practices guide for additional details.
> 685	
> 686	MCP servers **MUST** validate access tokens before processing the request, ensuring the access token is issued specifically for the MCP server, and take all necessary steps to ensure no data is returned to unauthorized parties.
> 687	
> 688	A MCP server **MUST** follow the guidelines in [OAuth 2.1 - Section 5.2](https://www.ietf.org/archive/id/draft-ietf-oauth-v2-1-13.html#section-5.2) to validate inbound tokens.
> 689	
> 690	MCP servers **MUST** only accept tokens specifically intended for themselves and **MUST** reject tokens that do not include them in the audience claim or otherwise verify that they are the intended recipient of the token. See the [Security Best Practices Token Passthrough section](/specification/2025-11-25/basic/security_best_practices#token-passthrough) for details.
> 691	
> 692	If the MCP server makes requests to upstream APIs, it may act as an OAuth client to them. The access token used at the upstream API is a separate token, issued by the upstream authorization server. The MCP server **MUST NOT** pass through the token it received from the MCP client.
> 693	
> 694	MCP clients **MUST** implement and use the `resource` parameter as defined in [RFC 8707 - Resource Indicators for OAuth 2.0](https://www.rfc-editor.org/rfc/rfc8707.html)
> 695	to explicitly specify the target resource for which the token is being requested. This requirement aligns with the recommendation in
> 696	[RFC 9728 Section 7.4](https://datatracker.ietf.org/doc/html/rfc9728#section-7.4). This ensures that access tokens are bound to their intended resources and
> 697	cannot be misused across different services.
> 698
