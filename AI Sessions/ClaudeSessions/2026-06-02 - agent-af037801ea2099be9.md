### 2. Guard logic / NULL semantics — correct and fail-safe.
`IS DISTINCT FROM` is the right operator (a plain `<>` would evaluate to UNKNOWN when `auth.uid()` is NULL and fail to block). For a no-JWT/anon caller, `auth.role()` is NULL → `NULL IS DISTINCT FROM 'service_role'` = TRUE, and any non-null `NEW.user_id` is distinct from NULL `auth.uid()` → guard fires (blocks). The only pass-through for a non-service caller is a genuine own-row write. Strictly more restrictive than the pre-guard state.

### 3. `SET search_path = ''` leaves no hijackable reference.
All table refs are schema-qualified (`public.*_table`); `auth.uid()`/`auth.role()` are `auth.`-qualified; `gen_random_uuid()`, `to_jsonb()`, `now()` resolve from `pg_catalog` (always implicitly searched first, immune to the empty search_path); `••••••••••••` are string literals, not identifiers. This is hardening (closes the definer search_path vector), matching the `20260602140000` precedent.

### 4. UPDATE branch `user_id = NEW.user_id` — reassignment now blocked.
A non-service caller reaching UPDATE must satisfy `NEW.user_id = auth.uid()`, so `user_id` can only be set to their own uid; cross-tenant reassignment is no longer possible. To reach the branch at all, the definer view's WHERE (`auth.uid() = user_id`) must already match OLD. `UNIQUE(user_id)` on `meta_config_table` further prevents collisions.

### 5. DELETE branch has NO guard — and correctly so. No cross-tenant delete.
`DELETE FROM <table> WHERE id = OLD.id`: `OLD` is sourced from the masked **definer view**, whose WHERE (`auth.uid() = user_id OR service_role`) filters row visibility for DELETE/UPDATE/SELECT (unlike INSERT). An authenticated caller's `DELETE ... WHERE id=<victim>` matches zero rows in the view → the INSTEAD OF trigger never fires for a foreign row. Authenticated has no direct DML grant on the base tables (verified: `REVOKE SELECT` in `20260601000600`, no compensating GRANT), so the only delete path is the row-filtered view. The asymmetry (guard on INSERT/UPDATE, none on DELETE) is exactly right — INSERT is the only operation a view's WHERE does not constrain — and is consistent with the unguarded DELETE branch in the `user_api_keys` precedent.

### Production-safety claim verified
Every credential writer matches the migration's assertion: `social-auth-callback` (sole social INSERT), `refresh-social-token`, `publish-meta`, `sync-meta-ads`, `self-heal` all use `SB_SECRET_KEY` (service_role → exempt); the only client paths are `useMetaConfig` `.insert({ user_id: user!.id, ... })` (own row) / `.update().eq('id', status.id)` (own row), and `useSocialAccounts` never inserts/updates client-side (delete only). No legitimate non-service path writes `user_id <> auth.uid()`, so the guard blocks only the attack.

Net: the migration is a correct, fail-closed hardening of a real pre-existing gap, with no newly-introduced vulnerability. Recommend approval.
