# QA Gate — Fix de segurança/estabilidade (incidente settings.password 401)

Escopo: working tree (não commitado) de `backend/src/repositories/settingsRepository.js` e `frontend/src/private/Settings/Settings.js`. Rastreio frontend→backend→login validado contra os arquivos reais.

## Achado central: o caso "salvar sem trocar senha" agora preserva o hash — CONFIRMADO em duas frentes

Há **defesa em profundidade**, e cada camada sozinha já mata o incidente:

1. Frontend (`Settings.js:43`): `if (!newPassword.trim()) delete payload.password;` — o campo `#password` é `onChange`-only (não tem `defaultValue`), então no estado inicial `settings.password` é `undefined` → `newPassword=''` → chave deletada → PATCH sai SEM `password`.
2. Backend (`settingsRepository.js:51`): `typeof newSettings.password === 'string' && ...trim().length > 0` — mesmo que o front mande `password: ""` ou `" "`, o `bcrypt.hashSync` não roda e o hash atual é preservado.

Reforço decisivo do design: `settingsController.getSettings` (linhas 8-11) faz `delete plainSettings.password` e `delete plainSettings.secretKey` antes do `res.json`. **A UI nunca recebe o hash nem o secret** — logo `settings.password`/`settings.secretKey` no estado React só existem se o usuário (ou autofill) digitar. Isso fecha a origem do incidente na raiz.

## Paridade login ↔ hash (senhas com espaço): CORRETA

- Backend hasheia o valor BRUTO: `bcrypt.hashSync(newSettings.password)` (linha 52) — `trim()` só decide vazio, não muta o valor.
- Login (`authController.js:7,11`): `const password = req.body.password` cru → `bcrypt.compareSync(password, settings.password)`. **Não trima.**
- Não existe middleware global de trim/sanitize (só `express.json()` em `app.js:35`).

Conclusão: uma senha `"  abc  "` é hasheada como `"  abc  "` e o login a compara como `"  abc  "`. Paridade exata, sem o clássico bug "salvei com espaço e não consigo logar". O comentário no código (linhas 49-50) descreve corretamente o comportamento.

## VEREDITO por arquivo

### `backend/src/repositories/settingsRepository.js` — **PASS**
A guarda `typeof === 'string' && .trim().length > 0` (linhas 51 e 69) é a correção certa e é **fail-safe**: trata `undefined`, `null`, `""`, `" "` e tipos não-string (ex.: `password: 0`/`password: []` via cliente malicioso) todos como "não mexer". É a camada que protege QUALQUER cliente do PATCH (UI, curl, futuro MCP), não só o front corrigido — esse é o ponto forte e o motivo de o backend ser a defesa primária.

- [INFO] `accessKey` (linha 60) segue o padrão truthy antigo `if (newSettings.accessKey && ...)`. Não foi alterado e não precisa: como a UI não recebe o `accessKey`? — recebe sim (`getSettings` só deleta password/secretKey), e tem `defaultValue={settings.accessKey}` no front. Mas `accessKey` não é hasheado/encriptado (é guardado em claro), então um re-save idêntico é inócuo. Sem regressão.
- [INFO] Sem transação/optimistic-lock — `getSettings` → mutações → `save()`. Pré-existente, fora do escopo deste fix, sem piora.

### `frontend/src/private/Settings/Settings.js` — **PASS COM RESSALVAS**
A lógica de payload (linhas 31-44) e os `autoComplete` (98/104/208) estão corretos. Ressalvas todas de severidade baixa, nenhuma bloqueante:

- [BAIXA] **`delete payload.secretKey` NÃO quebra a troca legítima de secret key.** Fluxo de troca: usuário digita no `#secretKey` → `onChange` seta `settings.secretKey` → `payload.secretKey` é truthy → `.trim()` passa → chave PRESERVADA no PATCH → backend re-encripta (linha 69). O `delete` só dispara quando o campo está vazio/só-espaço, que é exatamente o save de outra seção. Correto. (Caveat conhecido: secret key com espaços nas pontas seria encriptada com os espaços — mas secrets Binance são hex/base64 sem espaço, e isso é simétrico no boot do exchange, então não quebra auth.)
- [BAIXA] **Autofill que preenche password E confirmPassword com o MESMO valor passa a validação e a senha É trocada.** Cenário: gerenciador injeta a senha salva nos dois campos `autoComplete="new-password"`. `newPassword===confirm` (linha 35) → validação passa; `newPassword.trim()` é truthy → `delete` NÃO ocorre → PATCH leva `password` → backend re-hasheia. Se for a MESMA senha do login, é inócuo (re-hash do mesmo valor; login segue 200). O `autoComplete="new-password"` é a mitigação padrão e reduz muito a chance de o navegador autopreencher, mas browsers/gerenciadores podem ignorá-lo. Risco residual aceitável e muito menor que o incidente (que disparava com QUALQUER save de QUALQUER seção, inclusive sem o usuário ver o campo).
- [BAIXA] **`onFormSubmit` não chama `event.preventDefault()`.** Como os botões são `type="button"` (linhas 111/169/215), não há submit nativo — sem regressão. Mas `event` está na assinatura e não é usado; cosmético.
- [BAIXA] **Estado pós-save fica "sujo" com a senha digitada.** Após trocar a senha, `settings.password` continua no estado React. Um segundo clique em "Save" (em qualquer seção, sem recarregar) re-hasheia a mesma senha de novo. Idempotente do ponto de vista de login (mesmo valor → login segue OK), mas re-hash redundante. Não derruba ninguém. Limpar `settings.password`/`secretKey` e os inputs no sucesso seria o ideal.
- [INFO] `secretKey` usa `autoComplete="off"` enquanto password usa `new-password`. Diferença intencional e razoável (secret não é credencial de login do browser); `off` é menos confiável que `new-password` contra gerenciadores, mas o backend é a rede de segurança.
