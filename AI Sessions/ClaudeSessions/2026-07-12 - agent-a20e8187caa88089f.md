## Security Review: youtube-data + YouTube Studio changes

**Verdict: No HIGH-confidence, newly-introduced, concretely-exploitable vulnerabilities found.**

I read `youtube-data/index.ts`, the sibling `refresh-social-token/index.ts`, the `social-auth-init` youtube-branch diff, `useYouTubeStudio.ts`, and scanned `YouTubeStudioPage.tsx`. Walking through each of the five scrutiny points:

**1. Owner-scoped account resolution — SAFE.** The account is resolved server-side (`youtube-data/index.ts:114-120`) as `decrypted_social_accounts` filtered by `.eq("user_id", user.id)` where `user.id` comes from `userClient.auth.getUser()` (JWT-validated, lines 102-106). The `user_id` filter is the tenant boundary and is load-bearing given the service-role client bypasses RLS. No request-body field can redirect resolution to another tenant's row — the body only controls `action` and query params, never the `user_id`/`id` used to select the account. No path reads another tenant's row or token.

**2. Token never leaked to client or logged — SAFE.** The decrypted `access_token` is used only inside `gfetch` as an `Authorization` header (line 160). None of the response bodies (`channel`, `videos`, `categories`, metrics) contain the token or the `account` object. `console.error("youtube-data error:", err)` (line 232) logs only the caught exception, not the token. `googleError` echoes Google's `error.message` (line 76), which does not contain the token.

**3. Injection into URL/host/query — NOT reportable.** Base hosts are fixed constants (`YT_DATA`, `YT_ANALYTICS`, lines 19-20). Every user-controlled field reaches only the path/query, and is properly encoded: `regionCode`, `uploadsPlaylistId`, `pageToken` via `encodeURIComponent` (lines 176, 193-194); `metrics`, `startDate`, `endDate` via the `URLSearchParams` constructor; `dimensions`, `videoId` (as `filters=video==...`), `sort`, `maxResults` via `params.set()` (lines 219-223) — all of which percent-encode `&`, `=`, `?`, `#`. HOST and PROTOCOL are never user-controllable. Per the review's own rule (path/query-only SSRF is not reportable), nothing here qualifies. All body fields are `typeof === "string"`/`"number"` guarded, so no object-type bypass.

**4. Internal refresh call passes only the caller's own row — SAFE.** `ensureFreshToken` (lines 47-53) calls `refresh-social-token` with `social_account_id: account.id`, and `account.id` is the row already resolved by `user_id = user.id`. Even though the service-role bearer makes `refresh-social-token` treat it as an internal call (bypassing its own ownership check), the id it operates on is owner-scoped by construction. A user cannot trigger a refresh of another tenant's account. The post-refresh re-read (lines 54-58) is also `.eq("id", account.id)` — owner-scoped.

**5. Scope gate is UX, not the authz boundary — correctly layered.** The `youtube_scope_missing` gate (lines 132-151) produces an actionable reconnect CTA, but ownership is enforced independently by the `user_id` filter regardless of scope. Removing/bypassing the scope gate would not grant cross-tenant access.

**Frontend:** `YouTubeStudioPage.tsx` is display-only — no `dangerouslySetInnerHTML`/`innerHTML`/`eval`. The two `href` interpolations (`https://youtube.com/watch?v=${v.id}` and `https://youtube.com/${channel.snippet.customUrl}`) have a hardcoded `https://youtube.com/` prefix, so the scheme cannot be coerced to `javascript:`; values are the user's own channel/video data. Missing `rel="noopener"` on `target="_blank"` is a hardening nit (browsers default to noopener now) and is explicitly excluded.

**social-auth-init diff:** The change only broadens the YouTube OAuth scope set (readonly, upload, force-ssl, yt-analytics[-monetary].readonly). Scopes are `encodeURIComponent`-wrapped into a fixed Google auth URL; the signed HMAC `state` binding `userId` to the flow is unchanged. This is a product/consent-surface decision (broader granted permissions), not a code vulnerability — and destructive write scopes are not reachable through the read-only `youtube-data` proxy at all.

Nothing rises to ≥7 confidence. The new code faithfully mirrors the established per-user credential-resolution and server-side-token pattern of `refresh-social-token`.
