**VULNERABILITY ANALYSIS:**

**Claimed Issue:** A `billing_admin` role user can UPDATE the `owner_user_id` column in the organizations table, effectively hijacking organization ownership.

**Policy in Question (lines 112-114):**
```sql
CREATE POLICY org_admin_update ON public.organizations FOR UPDATE TO authenticated
  USING (public.org_role(id) IN ('owner','billing_admin'))
  WITH CHECK (public.org_role(id) IN ('owner','billing_admin'));
```

**The Critical Flaw:**

This policy does NOT restrict WHICH COLUMNS can be updated. The `UPDATE` permission is blanket — it permits updates to ANY column including `owner_user_id`. The `org_role()` function call checks:
1. **USING clause** (row visibility for update): "Can I see/access this row?" → billing_admin passes
2. **WITH CHECK clause** (post-update validation): "After my update, will my role still be appropriate?" → billing_admin passes

**Exploit Path - REAL AND EXPLOITABLE:**

Assume:
- Legitimate owner: `user_uuid_A` (has role='owner' in organization_members)
- Attacker billing_admin: `user_uuid_B` (has role='billing_admin' in organization_members)
- Organization: `org_uuid`

**Step 1:** Attacker (billing_admin) executes:
```sql
UPDATE public.organizations
SET owner_user_id = 'user_uuid_B'
WHERE id = 'org_uuid';
```

**RLS Evaluation:**
- **USING check** for auth.uid() = user_uuid_B:
  - `org_role('org_uuid')` queries: `SELECT m.role FROM organization_members m WHERE org_id='org_uuid' AND user_id='user_uuid_B' AND seat_active=true`
  - Returns: `'billing_admin'` ✓ (passes IN ('owner','billing_admin'))
  
- **WITH CHECK** (post-update):
  - `org_role('org_uuid')` still queries organization_members (NOT the updated organizations table)
  - Still returns: `'billing_admin'` ✓ (passes IN ('owner','billing_admin'))
  - The UPDATE succeeds because RLS only checks membership, not the owner_user_id field

**Step 2:** Attacker is now `organizations.owner_user_id`:
- Organizations table now has: `id='org_uuid', owner_user_id='user_uuid_B', ...`
- Attacker's membership row: `org_id='org_uuid', user_id='user_uuid_B', role='billing_admin'`

**Step 3:** Attacker can now escalate to sole control:
- Delete the legitimate owner from organization_members:
  ```sql
  DELETE FROM public.organization_members
  WHERE org_id = 'org_uuid' AND user_id = 'user_uuid_A';
  ```
  - This passes `orgmem_admin_write` policy because billing_admin is in ('owner','billing_admin')

**Step 4:** Attacker is now the de-facto owner:
- Controls the organization via billing_admin role in organization_members
- AND is listed as owner_user_id in organizations table
- The `org_owner_delete` policy (line 115-116) checks `org_role(id) = 'owner'`, but org_role() only checks membership, not owner_user_id
- Even if code elsewhere relies on owner_user_id as a trust boundary, the attacker has hijacked it

**The Root Cause:**

The `org_admin_update` policy is too permissive. It allows UPDATE with no column-level restrictions. In Postgres RLS, there is no built-in column-level security at the policy level—this requires application logic or trigger-based constraints.

The policy should either:
1. Use a trigger to prevent owner_user_id from being changed by non-owner roles, OR
2. Exclude billing_admin from UPDATE permission entirely (only owner updates), OR
3. Use a GRANT-based column restriction (GRANT UPDATE (name, plan_tier, ...) but NOT owner_user_id)

**Verification:**

The exploit is:
- **Real:** The code demonstrates no column-level restrictions on UPDATE
- **Exploitable:** A billing_admin with membership can successfully execute the UPDATE
- **High-Impact:** Results in full organization takeover (ownership hijack + ability to remove legitimate owner)
- **CVSS:** ~8.8 (High) — Privilege Escalation via Authorization Bypass; requires attacker to be a billing_admin member first but then gains owner status

**Confidence: 9/10**

The only reason not 10/10: Supabase's documentation mentions column-level security is possible via fine-grained controls, but from the code shown here, no such controls are implemented. This is a concrete, exploitable vuln in the migration as written.
