## Workflow

Follow this escalation pattern:

1. **Search** - No specific URL yet. Find pages, answer questions, discover sources.
2. **Scrape** - Have a URL. Extract its content directly.
3. **Map + Scrape** - Large site or need a specific subpage. Use `map --search` to find the right URL, then scrape it.
4. **Crawl** - Need bulk content from an entire site section (e.g., all /docs/).
5. **Interact** - Scrape first, then interact with the page (pagination, modals, form submissions, multi-step navigation).

| Need                        | Command               | When                                                      |
| --------------------------- | --------------------- | --------------------------------------------------------- |
| Find pages on a topic       | `search`              | No specific URL yet                                       |
| Get a page's content        | `scrape`              | Have a URL, page is static or JS-rendered                 |
| Find URLs within a site     | `map`                 | Need to locate a specific subpage                         |
| Bulk extract a site section | `crawl`               | Need many pages (e.g., all /docs/)                        |
| AI-powered data extraction  | `agent`               | Need structured data from complex sites                   |
| Interact with a page        | `scrape` + `interact` | Content requires clicks, form fills, pagination, or login |
| Download a site to files    | `download`            | Save an entire site as local files                        |

For detailed command reference, run `firecrawl <command> --help`.

**Scrape vs interact:**

- Use `scrape` first. It handles static pages and JS-rendered SPAs.
- Use `scrape` + `interact` when you need to interact with a page, such as clicking buttons, filling out forms, navigating through a complex site, infinite scroll, or when scrape fails to grab all the content you need.
- Never use interact for web searches - use `search` instead.

**Avoid redundant fetches:**

- `search --scrape` already fetches full page content. Don't re-scrape those URLs.
- Check `.firecrawl/` for existing data before fetching again.

## 1. O mecanismo — por que foto animada lê como pessoa e Veo lê como personagem

### 1.1 A diferença técnica que gera a diferença perceptual

| | **Geração de humano do zero** (Veo 3.1, Kling, Sora, Seedance) | **Animação de frame real** (OmniHuman, HeyGen IV, Hedra, D-ID) | **Lip-sync sobre vídeo real** (sync.so, LatentSync, MuseTalk) |

### 1.2 Por que a resolução pior ainda ganha — a explicação

**[INFERÊNCIA]** Três razões, em ordem de peso:

1. **Procedência fotográfica sobrevive à compressão.** Ruído de sensor, aberração de lente, assimetria facial real, poros, fios soltos, iluminação suja — são o "certificado de origem" que o sistema visual humano usa. Downscale para 512px **degrada** esses sinais mas não os **substitui por sinais falsos**. Um modelo generativo, ao contrário, entrega uma imagem 1080p limpa cujos sinais de baixo nível são estatisticamente *errados* — e o cérebro não lê isso como "baixa qualidade", lê como "não é uma pessoa".
2. **O vale da estranheza é um detector de *inconsistência*, não de *fidelidade*.** Um desenho não incomoda; um humano 97% correto incomoda. Geração do zero coloca o output exatamente na faixa 95-99% em todos os eixos ao mesmo tempo. Animação de foto trava a identidade em 100% (é literalmente a foto) e deixa o erro concentrado num único eixo (movimento) — que o espectador perdoa como "vídeo ruim", não como "não é gente".
3. **Drift temporal.** Geração do zero re-sintetiza a identidade a cada frame; micro-variações acumulam. Animação de frame real re-ancoram na mesma referência sempre. **[FATO]** O paper do OmniHuman-1.5 posiciona exatamente esse eixo: usa um design chamado *"Pseudo Last Frame"* para resolver conflitos entre modalidades e sustentar **vídeos de mais de um minuto** com movimento dinâmico ([arXiv:2508.19209, consultado 2026-08-12](https://arxiv.org/abs/2508.19209)).

### 1.3 Implicação direta para o MCORCH

> **Pare de tentar fazer o Veo *gerar* o apresentador. Use o Veo para o que ele é bom — o mundo ao redor — e produza o apresentador a partir de um frame real do dono.**

O Veo 3.1 já está no rail para b-roll/cena. Ele é um **gerador de mundo**, e o rosto humano é o pior caso possível para gerador de mundo, porque é o objeto que o público mais treinou a vida inteira a julgar. A escada correta:

```

                              (OmniHuman / sync / HeyGen IV)
        +
      Veo 3.1  →  cenário, b-roll, inserts             (onde alucinação coerente é OK)
        +
      MONTAR   →  camadas, UI, gráficos, marcas        (0 mco, determinístico)
```

### 5.2 Melhor caminho SELF-HOST

**Veredito honesto: hoje, não existe — e o bloqueio é hardware, não licença.**

**[FATO]** `nvidia-smi: NOT FOUND` · `no /dev/nvidia*` · `aarch64` · 4 vCPU · 24 GB RAM. Verificado neste host em 2026-08-12.

Toda a família (LatentSync, MuseTalk, EchoMimic, Hallo, InfiniteTalk, Wan-S2V) exige **CUDA + GPU NVIDIA**. O truque que funcionou para o matte (`u2net` em `onnxruntime` CPU puro) **não se transporta**: um U²-Net de 168 MiB rodando num frame é outra ordem de grandeza que um DiT de vídeo com áudio.

**Se e quando houver GPU, a escada é:**

| Se o orçamento de GPU for… | Escolha | Por quê |
|---|---|---|
| **4–8 GB** (GTX 1650 / RTX 3050) | **MuseTalk** | MIT no repo, openrail-m nos pesos, 4 GB verificado, tempo real-ish |
| **12–16 GB** (RTX 4060 Ti 16G / A4000) | **EchoMimicV3** | **Apache-2.0 no repo E nos pesos**, 12 GB, AAAI 2026, mantido em 2026 |
| **24 GB** (RTX 4090) | **InfiniteTalk** | Apache-2.0 ponta-a-ponta, duração **ilimitada**, image→video E **video→video** (= mesmo mecanismo do sync.so, self-host) |
| **80 GB** (A100/H100) | **Wan2.2-S2V-14B** | Apache-2.0 puro, cinematográfico, 480/720P |

**[INFERÊNCIA] O alvo self-host correto é o InfiniteTalk numa RTX 4090** — Apache-2.0 nos dois níveis, 7.615★, push de maio/2026, e o modo **video-to-video** replica exatamente a estratégia vencedora do §5.1 (lip-sync sobre footage real do dono) com **US$ 0 de API por render**, na mesma doutrina do motor MONTAR e do Qwen3-TTS. Isso é uma decisão de CapEx, e deveria ser tratada como tal — não como escolha de modelo.

**Regra de higiene inegociável (Lei 1):** nenhum motor entra no rail sem que **repo E pesos** tenham licença comercial verificada **separadamente**. Esta pesquisa achou três casos em que elas divergem (MuseTalk MIT/openrail-m, LatentSync Apache/openrail++, EchoMimic v1-v2 Apache/**sem licença nos pesos**) e três venenos (Sonic CC-BY-NC-SA, Wav2Lip non-commercial, HunyuanVideo-Avatar sem validade na UE/UK/Coreia).
